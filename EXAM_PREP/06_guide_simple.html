📖 Guide Simple — Lumina Pro

Ce guide explique tout en langage simple. Chaque fonctionnalité est expliquée comme si tu n'avais jamais programmé — avec des analogies du quotidien pour bien comprendre.
🗂️ Qu'est-ce que Lumina Pro ?
C'est comme un tableau blanc avec des post-its. Chaque post-it = une tâche. Tu les déplaces de colonne en colonne (À faire → En cours → Terminé). La différence : tout ça est dans un navigateur web, plusieurs personnes peuvent travailler dessus en même temps.

Les 3 grandes parties du projet

1
Le Front-end = ce que tu VOIS dans le navigateur. Le tableau kanban, les formulaires, les boutons. Fichiers : login.html, index.html, les fichiers CSS et JS.
2
Le Back-end = le "cerveau" invisible. Le serveur Node.js qui reçoit les demandes, vérifie les droits, et parle à la base de données. Fichiers : server.js, routes/, middleware/.
3
La Base de données = le "tiroir" où tout est stocké. MySQL avec 5 tables : utilisateurs, tâches, colonnes, logs, notifications.
🔐 Comment la connexion fonctionne
C'est comme un badge d'entrée dans un immeuble. Tu présentes ton badge (email + mot de passe), le portier vérifie (bcrypt), et te donne un laissez-passer valable 24h (JWT). À chaque porte tu montres ce laissez-passer sans re-présenter ton badge.

Les étapes détaillées

1
Tu saisies email + mot de passe dans le formulaire et cliques sur "Connexion"
2
JavaScript envoie ces données au serveur (POST /api/auth/login) via fetch()
3
Le serveur cherche l'email dans la base de données (SELECT * FROM users WHERE email = ?)
4
bcrypt compare ton mot de passe avec le hash stocké — sans jamais "décrypter" le hash
5
Si c'est bon : le serveur génère un JWT avec jwt.sign() et l'envoie en réponse
6
JavaScript stocke ce token dans localStorage — il sera utilisé pour toutes les prochaines requêtes
7
La page se redirige automatiquement vers index.html (le kanban)

C'est quoi localStorage ?

localStorage c'est comme un petit carnet dans ton navigateur. On peut y écrire des choses qui restent même si tu fermes l'onglet. Dans Lumina, on y écrit le token JWT pour ne pas avoir à se reconnecter à chaque page. 
// Écrire dans localStorage
localStorage.setItem('token', 'eyJhbGciOiJ...');

// Lire depuis localStorage
const token = localStorage.getItem('token');

// Tout effacer (déconnexion)
localStorage.clear();
🔒 c'est quoi bcrypt ?
Imagine un moulin à café très lent. Tu mets ton mot de passe dedans, il ressort sous forme de "café moulu" (le hash). Personne ne peut remettre le café dans le grain. Le truc : même avec un mot de passe identique, le résultat est différent à chaque fois (grâce au sel).

Hachage ≠ Chiffrement

✅ Hachage (ce qu'on fait)

On transforme le mot de passe en une suite de caractères irréversible. Impossible de retrouver l'original. C'est ce que fait bcrypt.

❌ Chiffrement (ce qu'on NE fait PAS)

On transforme les données d'une façon réversible avec une clé. Si quelqu'un vole la clé, il peut tout décrypter. Mauvais pour les mots de passe.

Le "sel" aléatoire

Le sel c'est comme ajouter une pincée de sel différente dans chaque plat. Même si deux utilisateurs ont le même mot de passe "123456", leurs hashs seront complètement différents. Ça rend les attaques par listes précalculées inutiles. 
// Deux utilisateurs avec le même mot de passe "azerty"
// Mais des hashs différents grâce au sel :
$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LPVhrNpFVK  ← user 1
$2b$10$Xy9pKlMnBvQw3RsTUaZmHfKjPqWe1Xy8n37ghLjmPo2QrStUvWx  ← user 2
🎫 C'est quoi un JWT ?
C'est comme un ticket de concert avec hologramme. Le ticket montre qui tu es (nom, siège). L'hologramme garantit que personne ne l'a falsifié. La sécurité peut vérifier le ticket sans appeler l'organisateur.

Les 3 parties d'un JWT

eyJhbGciOiJIUzI1NiJ9      ← Partie 1 : Header (algorithme)
.eyJpZCI6MSwicm9sZSI6ImFkbWluIn0   ← Partie 2 : Payload (tes infos)
.SflKxwRJSMeKKF2QT4fwpMeJf36       ← Partie 3 : Signature (le "hologramme")
Partie 2 décodée : { "id": 1, "role": "admin", "exp": 1735689600 }
→ visible par tout le monde (c'est juste du Base64)
→ mais IMPOSSIBLE à modifier sans casser la signature

Comment c'est vérifié côté serveur

1
Le front envoie le token dans le header : Authorization: Bearer eyJ...
2
Le middleware verifyToken extrait le token du header
3
jwt.verify() recalcule la signature → si ça correspond, c'est valide
4
Les infos du token (id, role) sont mises dans req.user pour la suite
📡 C'est quoi authFetch() ?
fetch() c'est comme envoyer une lettre. authFetch() c'est la même chose mais avec une enveloppe timbrée avec ton badge automatiquement. Tu n'as pas à coller le timbre à chaque lettre — c'est fait automatiquement.

Ce que fait authFetch — ligne par ligne

async function authFetch(url, options = {}) {

  // 1. On récupère le token sauvegardé lors de la connexion
  const token = localStorage.getItem('token');

  // 2. On prépare les en-têtes de la requête
  options.headers = {
    'Content-Type': 'application/json',  // ← dit "j'envoie du JSON"
    'Authorization': `Bearer ${token}`,    // ← le badge JWT
  };

  // 3. On envoie vraiment la requête (comme fetch() normal)
  const response = await fetch(url, options);

  // 4. Si le serveur dit "token expiré" → on déconnecte et on redirige
  if (response.status === 401) {
    localStorage.clear();
    window.location.href = 'login.html';
  }

  return response; // 5. On retourne la réponse du serveur
}

Pourquoi pas utiliser fetch() directement ?

Sans authFetch(), il faudrait réécrire Authorization: Bearer ${token} dans chaque requête fetch. Il y en a 13 dans Lumina. Si le format change un jour, il faut changer 13 endroits. Avec authFetch(), on change qu'un seul endroit. C'est le principe DRY (Don't Repeat Yourself).
🛡️ C'est quoi escapeHTML() ?
Imagine que quelqu'un écrit un faux billet de banque et le met dans ta caisse. escapeHTML() c'est le vérificateur de billets : il détecte les "billets dangereux" (scripts) et les rend inoffensifs avant de les afficher.

Le problème XSS concret

❌ Titre de tâche malveillant

<script>alert('Je vole ton token: ' + localStorage.getItem('token'))</script>

Sans protection, ce script s'exécuterait dans ton navigateur ET dans celui de tous tes collègues !

✅ Après escapeHTML()

&lt;script&gt;alert('Je vole ton token: ' + localStorage.getItem('token'))&lt;/script&gt;

Le navigateur affiche ce texte tel quel. Jamais exécuté.

Les 5 remplacements importants

1
& → &amp; — remplacé EN PREMIER pour ne pas "double-échapper" les autres
2
< → &lt; — neutralise l'ouverture d'une balise HTML ou script
3
> → &gt; — neutralise la fermeture d'une balise
4
" → &quot; — empêche de "s'échapper" d'un attribut HTML (onclick="...")
5
' → &#39; — idem avec les apostrophes
📋 Comment le kanban s'affiche
Imagine que tu as une liste de post-its et une liste de colonnes. Tu dois trier les post-its dans leurs colonnes. C'est exactement ce que fait renderBoard().

Les étapes du chargement

1
Page chargée → DOMContentLoaded → vérification du token (si absent → login)
2
fetchTasks() → deux requêtes : GET /api/columns + GET /api/tasks
3
renderBoard(colonnes, tâches) → pour chaque colonne, on filtre les tâches qui lui appartiennent
4
.filter() → garde seulement les tâches dont id_col = l'ID de la colonne courante
5
.map() → transforme chaque tâche en morceau de HTML
6
.join('') → colle tous les morceaux en une seule chaîne
7
innerHTML → on injecte le HTML généré dans la page → le kanban apparaît

Pourquoi fetchTasks() est appelée après chaque action ?

Après avoir créé, modifié ou déplacé une tâche, on relance fetchTasks() pour resynchroniser l'affichage avec la base de données. Sinon tu verrais une version obsolète. C'est simple et fiable.
🗃️ Les requêtes SQL importantes
SQL c'est le langage pour parler à la base de données. C'est comme donner des ordres en français mais avec des règles précises.

Les 4 opérations CRUD

-- C = Create (créer)
INSERT INTO tasks (title, priority, id_col) VALUES ('Fix bug', 'high', 1);

-- R = Read (lire)
SELECT tasks.*, users.name AS assigned_name
FROM tasks
LEFT JOIN users ON tasks.id_assigned = users.id
ORDER BY tasks.id_col, tasks.created_at;

-- U = Update (modifier)
UPDATE tasks SET title = 'Fix bug login' WHERE id = 5;

-- D = Delete (supprimer)
DELETE FROM tasks WHERE id = 5;

LEFT JOIN — pourquoi pas INNER JOIN ?

INNER JOIN : montre seulement les tâches qui ont un utilisateur assigné.
LEFT JOIN : montre toutes les tâches, même celles sans utilisateur assigné.

Dans Lumina on utilise LEFT JOIN pour que les tâches "non assignées" apparaissent quand même.

ON DELETE CASCADE vs SET NULL

CASCADE — colonnes

Si tu supprimes la colonne "À faire" → toutes ses tâches sont automatiquement supprimées aussi. Comme vider une corbeille avec tout son contenu.

SET NULL — utilisateurs

Si tu supprimes un utilisateur → ses tâches restent mais id_assigned passe à NULL. Les tâches deviennent "non assignées".

⏳ C'est quoi async/await ?
Imagine que tu commandes une pizza. Tu n'attends pas debout devant la porte 30 minutes — tu vas faire autre chose et tu reviens quand la sonnette sonne. await c'est "attends que la pizza arrive avant de passer à l'étape suivante", sans bloquer tout le reste.

Sans async/await (difficile à lire)

// Ancien style avec .then() — difficile à suivre
fetch('/api/tasks')
  .then(response => response.json())
  .then(tasks => { afficherKanban(tasks); })
  .catch(err => { console.log(err); });

Avec async/await (style Lumina)

// Beaucoup plus lisible — comme du code normal mais asynchrone
async function fetchTasks() {
  try {
    const response = await authFetch('/api/tasks'); // ← attend la réponse
    const tasks = await response.json();           // ← attend le JSON parsé
    afficherKanban(tasks);
  } catch (err) {
    alert("Erreur de connexion");
  }
}

Que se passe-t-il si on oublie await ?

Sans await, la variable contient une Promise (une promesse) au lieu des vraies données. C'est comme si tu essayais de manger la promesse d'une pizza au lieu de la pizza. Ça plante.
🚦 C'est quoi un middleware ?
C'est comme un vigile à l'entrée d'une boîte de nuit. Toutes les personnes (requêtes) passent devant lui. Il peut laisser passer (next()), refuser (res.status(401)), ou tamponner le passeport (req.user = ...) avant de laisser entrer.

L'ordre des middlewares dans server.js

1
cors() → "Es-tu d'une origine autorisée ?" → autorise toutes les origins
2
express.json() → "Je lis le body JSON de ta requête" → remplit req.body
3
req.db = db → "Je t'attache la connexion à la base de données" → disponible dans toutes les routes
4
verifyToken → "Ton badge JWT est valide ?" → si oui, next(), si non, 401/403
5
La route → enfin, la logique métier s'exécute (lire/écrire en BDD)
🌐 C'est quoi une API REST ?
C'est comme un restaurant avec un menu. Chaque plat = un endpoint. Tu commandes (méthode HTTP) un plat précis (URL) et le cuisinier (serveur) te l'apporte (réponse JSON).

Les 4 méthodes = les 4 actions possibles

GET
Lire → "Donne-moi les tâches" → GET /api/tasks
POST
Créer → "Crée une nouvelle tâche" → POST /api/tasks
PUT
Modifier → "Change le titre de la tâche 5" → PUT /api/tasks/5
DEL
Supprimer → "Supprime la tâche 5" → DELETE /api/tasks/5

Les codes de réponse

200 = "Tout va bien" · 201 = "Créé avec succès" · 400 = "Ta requête est mal formée" · 401 = "Tu n'es pas connecté" · 403 = "Tu n'as pas le droit" · 500 = "Erreur du serveur"
