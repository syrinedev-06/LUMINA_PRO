1 — Introduction

Ce dossier présente Lumina Pro, projet réalisé en solo dans le cadre de la Formation DWWM 2025/2026 à La Plateforme_ pour l'obtention du Titre Professionnel Développeur Web et Web Mobile.

Il retrace l'ensemble de la démarche, de la conception à la mise en service locale : analyse du besoin, choix techniques, modélisation de la base de données, implémentation du front-end et du back-end, sécurisation de l'application.

Lumina Pro est une application web de gestion de tâches collaborative basée sur la méthode Kanban : un tableau à colonnes personnalisables permet à une équipe de suivre l'avancement de ses missions, avec deux niveaux de droits (administrateur / utilisateur).

Le projet couvre l'ensemble des compétences attendues sur les deux activités du référentiel : développement front-end et back-end d'une application web sécurisée.

3 — Fondation conceptuelle et direction du projet

3.1 Présentation générale

Lumina Pro est une plateforme web dont l'objectif est de permettre à une petite équipe de :

  • visualiser ses tâches sous forme de tableau Kanban à colonnes personnalisables ;
  • assigner des tâches aux membres de l'équipe et suivre leur priorité ;
  • distinguer deux profils : administrateur (gestion de l'équipe et des colonnes) et utilisateur (gestion de ses tâches).

3.2 Besoins et objectifs de l'application

Remplacer un suivi de tâches informel (messages, tableurs) par un outil centralisé, simple et sécurisé, où chaque membre voit l'état d'avancement du travail collectif en un coup d'œil, sans avoir à gérer une solution SaaS tierce complexe.

3.3 User Stories

Utilisateur

  • En tant qu'utilisateur, je veux m'inscrire et me connecter afin d'accéder à mon espace de travail.
  • En tant qu'utilisateur, je veux créer, modifier et déplacer mes tâches entre les colonnes pour suivre mon avancement.
  • En tant qu'utilisateur, je veux voir les membres de l'équipe afin de savoir qui est assigné à quoi.
  • En tant qu'utilisateur, je veux consulter des statistiques (répartition des tâches par priorité) pour avoir une vue d'ensemble.

Administrateur

  • En tant qu'administrateur, je veux créer, renommer et supprimer des colonnes pour adapter le tableau au workflow de l'équipe.
  • En tant qu'administrateur, je veux gérer les comptes utilisateurs (voir la liste, supprimer un compte).
  • En tant qu'administrateur, je veux effectuer toutes les actions disponibles pour un utilisateur standard.

3.4 MVP (Minimum Viable Product)

Le périmètre retenu pour la version initiale, effectivement livrée :

  • authentification sécurisée (JWT + bcrypt) ;
  • CRUD complet des tâches et des colonnes ;
  • gestion des rôles admin / utilisateur ;
  • vue équipe et page statistiques ;
  • documentation API interactive (Swagger).

Les fonctionnalités avancées (journal d'audit exposé en API, drag & drop natif) sont traitées en évolutions futures — le module de journal d'audit existe déjà en ébauche de code mais n'est pas branché à ce jour (voir encadré en section 6). Un système de notifications avait été envisagé puis retiré volontairement du périmètre (commit « Suppression complète du système de notifications »), pour concentrer l'effort sur le cœur Kanban.

3.5 Cahier des charges

Exigences fonctionnelles — Un visiteur peut s'inscrire et se connecter. Un utilisateur connecté gère ses tâches (créer / modifier / déplacer / supprimer), consulte l'équipe et les statistiques. Un administrateur gère en plus les colonnes et les comptes utilisateurs.

Exigences techniques — Application consommant une API REST sécurisée par JWT ; mots de passe hachés (bcrypt) et jamais stockés en clair ; requêtes SQL préparées ; interface responsive desktop/mobile.

Exigences non-fonctionnelles — Accessibilité (sémantique HTML5, attributs ARIA, contrastes, focus clavier — RGAA 4.1.2 / WCAG 2.1) ; sécurité (CORS, isolation des secrets dans .env) ; documentation (README, Swagger).

4 — Environnement et architecture technique

4.1 Environnement de développement

Développement sous Windows 11 avec Visual Studio Code comme IDE, XAMPP pour le serveur MySQL local, Node.js pour le back-end. Script LANCER_LUMINA.bat automatisant le démarrage de MySQL, du serveur Node et l'ouverture du navigateur.

4.2 Choix techniques

CôtéTechnologies
Front-endHTML5, CSS3 (8 modules), JavaScript ES6+ vanilla (aucun framework)
Back-endNode.js, Express 5.2.1
Base de donnéesMySQL 8 (via mysql2)
Sécuritéjsonwebtoken 9.0.3, bcrypt 6.0.0, cors 2.8.6, dotenv
Documentationswagger-ui-express
VersioningGit + GitHub

Choix assumé de JavaScript vanilla (sans framework front) et d'un accès direct aux données depuis les routes Express (sans ORM), dans un but pédagogique : comprendre le fonctionnement de chaque couche sans l'abstraction d'une bibliothèque tierce.

4.3 Architecture applicative

Architecture client-serveur en trois couches : front-end statique servi par Express (express.static), API REST back-end, base de données MySQL. Contrairement à un découpage MVC strict, la logique métier de ce projet reste volontairement légère : chaque fichier de routes/ contient directement ses requêtes SQL (pas de couche controller/model séparée), ce qui convient à la taille du projet mais serait à faire évoluer sur une application plus grande (voir roadmap).

Un middleware d'application (req.db = db) injecte la connexion MySQL dans chaque requête, et un middleware dédié (verifyToken) protège les routes sensibles en vérifiant le jeton JWT.

4.4 Versioning et workflow Git

Projet versionné en continu sur GitHub (syrinedev-06/LUMINA_PRO), avec des commits fréquents et explicites (ex. « Découpage modulaire de kanban.js en kanban.js, columns.js et tasks.js »). Le développement s'est fait directement sur la branche main, sans branches de fonctionnalités séparées — un choix simple adapté à un projet solo, mais qui serait à faire évoluer vers un vrai workflow de branches (feature/, fix/) sur un projet en équipe.

Le fichier .gitignore exclut node_modules/ et les fichiers de logs. Le fichier .env n'est jamais versionné ; .env.example sert de modèle de configuration pour un autre développeur.

5.2 Charte graphique

Identité visuelle bâtie autour d'un dégradé rose/fuchsia (#d63384) associé à un bleu-violet foncé (#302b63), sur fond clair pour la lisibilité. Police système (Segoe UI) pour la cohérence multi-plateforme et de bons contrastes texte/fond.

5.3 Maquettes et responsive

Interface pensée desktop-first puis adaptée mobile via media queries : sidebar fixe sur desktop, masquée et accessible par un bouton hamburger sous 900px, colonnes Kanban en défilement horizontal sur mobile.

6 — Conception du back-end

6.1 Base de données — méthode MERISE

Modélisation en trois étapes : MCD (entités et associations), MLD (tables, clés primaires/étrangères, règles de cardinalité), MPD (implémentation MySQL). Le script database/schema.sql reflète exactement les trois tables réellement créées par server.js au démarrage — users, columns, tasks — sans rien documenter que le code ne crée pas vraiment.

Choix de périmètre assumé : un module de journal d'audit (routes/logs.js) et un module de statistiques serveur (routes/stats.js) ont été ébauchés puis volontairement laissés de côté pour garder un cœur applicatif simple et entièrement maîtrisé (voir roadmap). Un système de notifications avait aussi été envisagé puis retiré du périmètre en cours de projet (voir section 3.4) pour la même raison.

7 — Implémentation du front-end

7.1 Architecture et logique d'affichage

L'application est structurée en pages HTML classiques (login.html, index.html) plutôt qu'en Single Page Application : chaque page charge ses modules JS dédiés (auth.js, kanban.js, tasks.js, columns.js, team.js, profile.js, ui.js), avec api.js centralisant les appels réseau via une fonction authFetch() qui ajoute systématiquement le header Authorization: Bearer <token>.

7.2 Esthétique, accessibilité et performances

CSS découpé en 8 fichiers thématiques (variables, layout, kanban, responsive, forms/modals, composants, scrollbar, auth/profil) pour la maintenabilité. Attributs ARIA sur les éléments interactifs, contrastes vérifiés, navigation clavier — détail exhaustif dans le cahier de tests d'accessibilité RGAA dédié.

7.3 Sécurité et robustesse du front

Le front-end n'étant jamais fiable pour la sécurité, toute donnée utilisateur affichée dans le DOM (titre de tâche, description, nom) passe par une fonction d'échappement HTML avant insertion, pour neutraliser un risque XSS si un contenu malveillant était saisi dans un champ texte libre :

// frontend/js/api.js — escapeHTML()
function escapeHTML(str) {
  const div = document.createElement('div')
  div.textContent = str
  return div.innerHTML
}

La sécurité réelle (prévention de l'injection SQL) reste assurée côté serveur par les requêtes préparées — jamais par une validation front-end seule.

8 — Implémentation du back-end

8.1 Architecture et logique métier

server.js initialise Express, configure les middlewares globaux (cors, express.json, service des fichiers statiques du front), établit la connexion MySQL et crée automatiquement les tables si elles n'existent pas (mécanisme d'auto-réparation au démarrage). Il monte ensuite les routes :

app.use('/api/auth', require('./routes/auth'));
app.use('/api/users', verifyToken, require('./routes/users'));
app.use('/api/tasks', verifyToken, require('./routes/tasks'));
app.use('/api/columns', verifyToken, require('./routes/columns'));

8.2 Logique métier : construction dynamique des requêtes UPDATE

Le frontend peut envoyer n'importe quelle combinaison de champs à modifier sur une tâche (déplacement = seul id_col, édition complète = tous les champs). La route PUT /api/tasks/:id construit dynamiquement la clause SET pour éviter de dupliquer la logique :

let sql = "UPDATE tasks SET ";
const params = [];
if (title) { sql += "title = ?, "; params.push(title); }
if (id_col) { sql += "id_col = ?, "; params.push(id_col); }
// ...
sql = sql.slice(0, -2) + " WHERE id = ?";
params.push(req.params.id);

8.3 Sécurité et intégrité des données

Les routes /api/users, /api/tasks et /api/columns sont protégées par le middleware verifyToken. La suppression d'une colonne entraîne, grâce à la contrainte ON DELETE CASCADE, la suppression automatique des tâches associées — un effet de bord assumé pour éviter les tâches orphelines.

La suppression d'une tâche (DELETE /api/tasks/:id) vérifie en plus la propriété de la ressource pour éviter une faille IDOR (Insecure Direct Object Reference) : un utilisateur standard ne peut supprimer que les tâches qui lui sont assignées, un administrateur peut supprimer n'importe quelle tâche. Cette règle est appliquée côté serveur (pas seulement en masquant le bouton côté front) :

// backend/routes/tasks.js — DELETE /:id
req.db.query("SELECT id_assigned FROM tasks WHERE id = ?", [req.params.id], (err, results) => {
  const isOwner = results[0].id_assigned === req.user.id;
  if (req.user.role !== 'admin' && !isOwner) {
    return res.status(403).json({ error: "Vous ne pouvez supprimer que vos propres tâches." });
  }
  // ... suppression
});

10 — Sécurité de l'application

10.1 Système d'authentification

Hachage bcrypt — coût de hachage (salt rounds) de 10, appliqué à l'inscription :

const hashedPassword = await bcrypt.hash(password, 10);

JWT — à la connexion, après vérification par bcrypt.compare, un jeton signé est émis (payload id + role, expiration 24h) :

const token = jwt.sign({ id: user.id, role: user.role }, SECRET_KEY, { expiresIn: '24h' });

Le middleware verifyToken vérifie la présence du header Authorization: Bearer <token>, valide la signature (jwt.verify) et injecte les données décodées dans req.user avant de laisser passer la requête.

10.2 Protections mises en place

RisqueProtection
Injection SQLRequêtes préparées avec placeholders ? sur toutes les routes
XSSescapeHTML() avant toute insertion de contenu utilisateur dans le DOM
Mots de passeHachage bcrypt irréversible, sel aléatoire unique par utilisateur
CSRFToken JWT transmis en header Authorization, jamais en cookie
IDOR (suppression de tâche)Vérification côté serveur que l'utilisateur est propriétaire de la tâche ou admin avant suppression
CORSMiddleware cors() activé (ouvert en développement, à restreindre à l'origine du front en production)
Points d'amélioration identifiés : la clé JWT_SECRET a une valeur de repli codée en dur dans le code (|| "LUMINA_SECRET_2025_2026") si le fichier .env est absent — à supprimer en production pour forcer l'usage exclusif de la variable d'environnement. Aucun rate limiting n'est en place sur /api/auth (protection anti brute-force à ajouter, voir roadmap).

11 — Accessibilité, SEO et RGPD

11.1 Accessibilité

Démarche conforme au RGAA 4.1.2 / WCAG 2.1 : attributs aria-label/role sur les boutons icônes, navigation clavier, contrastes vérifiés, <label> associé à chaque champ. Un cahier de tests d'accessibilité dédié a été rédigé et exécuté manuellement (voir cahier_tests_accessibilite.html).

11.2 SEO

HTML5 sémantique (structure de titres cohérente, balises appropriées). L'application étant un outil interne derrière authentification, l'indexation par les moteurs de recherche n'est pas un enjeu prioritaire — le soin porté au HTML sémantique sert avant tout l'accessibilité.

11.3 RGPD

Données collectées strictement minimales : nom, email, mot de passe (haché). Aucune donnée sensible. Aucune transmission à des tiers. Suppression de compte possible par un administrateur. Variables sensibles (JWT_SECRET) isolées dans .env, non versionné.

12.3 Jeu d'essai

Anomalie corrigée : seed.js insérait initialement les mots de passe de test en clair (sans bcrypt.hash()), et un rôle 'utilisateur' invalide au regard de l'ENUM réel ('admin'/'user') ainsi que des priorités de tâches ('urgent'/'important'/'normal') invalides au regard de l'ENUM réel ('high'/'medium'/'low') — trois erreurs qui auraient fait échouer silencieusement ou bruyamment le seeding et la connexion des comptes de démonstration. 13 — Déploiement de l'application

13.1 Préparation de l'environnement

L'application est composée d'un serveur Node.js/Express exposant une API REST et servant directement les fichiers statiques du front-end (pas d'étape de build). Un serveur MySQL (XAMPP) doit être démarré ; les tables du cœur applicatif sont créées automatiquement au premier lancement du serveur.

13.2 Configuration

La configuration repose sur un fichier .env non versionné (modèle fourni par .env.example), contenant la clé JWT_SECRET. Les dépendances s'installent via npm install, le serveur démarre avec npm start. Le script LANCER_LUMINA.bat automatise l'ensemble (MySQL → serveur Node → ouverture du navigateur) pour un lancement en un clic.

13.3 Mise en ligne et exploitation

À ce jour, le projet tourne exclusivement en local (XAMPP + Node), sans conteneurisation ni hébergement distant. C'est un choix assumé plutôt qu'un oubli : les pistes de mise en production (hébergement mutualisé type O2Switch ou VPS, HTTPS obligatoire, Docker) sont identifiées en roadmap plutôt que prétendues faites.

14 — Roadmap et évolutions futures

  • Brancher les modules déjà écrits mais non montés : journal d'audit (routes/logs.js) et statistiques serveur (routes/stats.js).
  • Ajouter une suite de tests automatisés (Jest + Supertest) sur l'authentification et le CRUD des tâches.
  • Supprimer la valeur de repli codée en dur pour JWT_SECRET et ajouter un rate limiting sur /api/auth (anti brute-force).
  • Introduire une séparation formelle routes / controllers / models pour préparer la montée en complexité de l'application.
  • Conteneuriser l'application avec Docker et documenter un déploiement en environnement distant (HTTPS, variables d'environnement de production).
  • Drag & drop natif pour le déplacement des tâches (actuellement via boutons directionnels, un choix pris pour simplifier l'UI et le code).

15 — Conclusion

Lumina Pro a permis de mettre en pratique l'ensemble des compétences du référentiel DWWM sur un projet mené en solo, du cahier des charges à l'implémentation d'une API REST sécurisée : modélisation MERISE, authentification JWT et hachage bcrypt, requêtes préparées, accessibilité RGAA, documentation Swagger.

Le projet est présenté avec une exigence de transparence : les limites connues (modules non branchés, absence de tests automatisés, anomalie du jeu de seed, environnement local uniquement) sont documentées plutôt que masquées, ce qui constitue en soi une démonstration de rigueur professionnelle et une base claire pour les évolutions futures.
