1. Architecture générale — Comment tout est connecté

Lumina Pro est une application web avec une architecture séparée en deux parties qui communiquent via une API REST.

Ce que tu dis au jury :

"Mon application suit une architecture client-serveur. Le frontend en Vanilla JavaScript communique avec le backend Node.js/Express via des requêtes HTTP. Toutes les routes protégées passent par un middleware JWT qui vérifie l'identité de l'utilisateur avant d'autoriser l'accès aux données."

2. Base de données — Structure des tables

Les tables sont créées automatiquement au premier démarrage du serveur (dans server.js).

Table users

Créée dans server.js au démarrage
CREATE TABLE IF NOT EXISTS users (
    id       INT AUTO_INCREMENT PRIMARY KEY,
    name     VARCHAR(255) NOT NULL,
    email    VARCHAR(255) UNIQUE NOT NULL,  -- email unique = pas de doublons
    password VARCHAR(255) NOT NULL,           -- stocke le HASH bcrypt, jamais le vrai mot de passe
    role     ENUM('admin', 'user') DEFAULT 'user'
)

Table columns

CREATE TABLE IF NOT EXISTS columns (
    id       INT AUTO_INCREMENT PRIMARY KEY,
    title    VARCHAR(255) NOT NULL,
    position INT DEFAULT 0  -- pour l'ordre d'affichage gauche→droite
)

Table tasks

CREATE TABLE IF NOT EXISTS tasks (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    title       VARCHAR(255) NOT NULL,
    description TEXT,
    priority    ENUM('high', 'medium', 'low') DEFAULT 'medium',
    id_assigned INT,                               -- peut être NULL (tâche non assignée)
    id_col      INT,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (id_col) REFERENCES columns(id) ON DELETE CASCADE
    -- ON DELETE CASCADE = si on supprime une colonne, toutes ses tâches sont supprimées aussi
)

ON DELETE CASCADE — c'est quoi ?

Si tu supprimes la colonne "À faire", toutes les tâches qui étaient dans cette colonne sont supprimées automatiquement par MySQL. Pas de tâches orphelines (sans colonne).

UNIQUE sur email — c'est quoi ?

MySQL refuse d'insérer deux utilisateurs avec le même email. Si tu essaies, le serveur répond une erreur 500 avec le message "L'email existe peut-être déjà".

Colonnes par défaut créées automatiquement

-- Si la table colonnes est vide au démarrage :
INSERT INTO columns (title, position)
VALUES ('À faire', 1), ('En cours', 2), ('Terminé', 3)
Q : Pourquoi tu n'utilises pas ON DELETE SET NULL sur id_col ?
Parce que une tâche sans colonne n'aurait aucun sens dans un Kanban. J'ai choisi CASCADE pour que quand on supprime une colonne, ses tâches soient supprimées aussi. C'est une décision de design volontaire — l'admin est averti par la confirmation avant suppression.

3. server.js — Le cœur du backend

Ligne par ligne

backend/server.js
const express = require('express');
// Express = framework pour créer des serveurs web en Node.js

const cors = require('cors');
// CORS = autorise le navigateur (port 5500) à parler au serveur (port 3000)
// Sans cors(), le navigateur bloquerait toutes les requêtes → "Cross-Origin Error"

const verifyToken = require('./middleware/security');
// Notre gardien JWT — vérifie le token avant chaque route privée

const app = express();

app.use(cors());
// Applique CORS sur toutes les routes

app.use(express.json());
// Permet de lire req.body (le JSON envoyé par le frontend)
// Sans ça, req.body serait undefined

// Middleware pour attacher la connexion DB à chaque requête
app.use((req, res, next) => {
    req.db = db;   // toutes les routes peuvent faire req.db.query()
    next();          // passe à la route suivante
});

// Route PUBLIQUE (pas de vérification JWT)
app.use('/api/auth', require('./routes/auth'));

// Routes PROTÉGÉES (verifyToken s'exécute avant chaque requête)
app.use('/api/users',   verifyToken, require('./routes/users'));
app.use('/api/tasks',   verifyToken, require('./routes/tasks'));
app.use('/api/columns', verifyToken, require('./routes/columns'));

app.listen(3000);

Qu'est-ce qu'un middleware ?

C'est une fonction qui s'exécute entre la requête du client et la réponse du serveur. Elle reçoit (req, res, next). Si elle appelle next() → on continue. Si elle appelle res.json() → on s'arrête là.

Dans Lumina Pro : verifyToken est un middleware. Si le token est valide → next(). Si non → res.status(401) et on s'arrête.

4. Sécurité — JWT + bcrypt (les deux plus importantes)

4.1 — verifyToken (middleware/security.js)

C'est le gardien de toutes les routes privées. Il vérifie chaque token avant de laisser passer.

backend/middleware/security.js — expliqué ligne par ligne
function verifyToken(req, res, next) {

    // 1. Lire le header "Authorization" de la requête
    const authHeader = req.headers['authorization'];
    // Exemple de valeur : "Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."

    // 2. Vérifier que le header existe ET commence par "Bearer "
    if (!authHeader || !authHeader.startsWith('Bearer ')) {
        return res.status(401).json({ error: "Token manquant" });
        // 401 = "tu n'es pas connecté" (non authentifié)
    }

    // 3. Extraire juste le token (après "Bearer ")
    const token = authHeader.split(' ')[1];
    // "Bearer abc123".split(' ') → ["Bearer", "abc123"] → on prend [1]

    try {
        // 4. Vérifier la signature + la date d'expiration
        const decoded = jwt.verify(token, "LUMINA_SECRET_2024");
        // Si le token est faux ou expiré → exception → va dans catch

        // 5. Attacher les infos de l'utilisateur à la requête
        req.user = decoded;
        // decoded = { id: 1, role: 'admin', iat: 17..., exp: 17... }
        // Les routes suivantes peuvent lire req.user.id ou req.user.role

        next(); // ✅ Token valide → on continue

    } catch (error) {
        return res.status(403).json({ error: "Token invalide ou expiré" });
        // 403 = "tu es connu mais interdit" (authentifié mais pas autorisé)
    }
}

401 vs 403 — la différence

  • 401 = token absent ou mal formaté → "Qui es-tu ?"
  • 403 = token présent mais invalide/expiré → "Je te connais mais non"

Ce que contient le token décodé

{
  id: 1,
  role: "admin",
  iat: 1720000000,  // créé le
  exp: 1720086400   // expire le (24h après)
}

4.2 — bcrypt.hash et bcrypt.compare (routes/auth.js)

Utilisateur tape "Lumina1!"
→
bcrypt.hash("Lumina1!", 10)
→
"$2b$10$xK9mP..." (hash)
→
Stocké en BDD
backend/routes/auth.js — INSCRIPTION
// Le mot de passe arrive en clair dans req.body.password
const hashedPassword = await bcrypt.hash(password, 10);
// 10 = le nombre de "rounds" (cycles de hachage)
// Plus le nombre est grand, plus c'est lent → 10 est le compromis standard
// bcrypt ajoute automatiquement un SEL aléatoire = jamais 2 hash identiques

const sql = "INSERT INTO users (name, email, password) VALUES (?, ?, ?)";
req.db.query(sql, [name, email, hashedPassword]);
// On stocke hashedPassword (jamais le mot de passe en clair !)
backend/routes/auth.js — CONNEXION
// 1. Chercher l'utilisateur par email
const sql = "SELECT * FROM users WHERE email = ?";
req.db.query(sql, [email], async (err, results) => {

    const user = results[0];

    // 2. Comparer le mot de passe saisi avec le hash en BDD
    const isMatch = await bcrypt.compare(password, user.password);
    // bcrypt.compare("Lumina1!", "$2b$10$xK9mP...") → true ou false
    // On ne peut PAS retrouver le mot de passe depuis le hash (irréversible)

    if (!isMatch) return res.status(401).json({ error: "Mauvais identifiants" });

    // 3. Créer le token JWT
    const token = jwt.sign(
        { id: user.id, role: user.role },  // payload = données dans le token
        "LUMINA_SECRET_2024",               // clé secrète pour signer
        { expiresIn: '24h' }               // durée de vie
    );

    // 4. Renvoyer le token au frontend
    res.json({ token, user: { id, name, email, role } });
});
Q : Pourquoi bcrypt et pas MD5 ou SHA256 ?
MD5 et SHA256 sont rapides — un attaquant peut tester des millions de mots de passe par seconde. bcrypt est volontairement lent grâce au "cost factor" de 10. Même avec le hash, une attaque brute force prendrait des années. De plus bcrypt intègre un sel aléatoire unique par mot de passe, ce qui rend les "rainbow tables" inutiles.
Q : Qu'est-ce que le sel (salt) dans bcrypt ?
C'est une chaîne aléatoire que bcrypt génère et ajoute au mot de passe avant de le hacher. Résultat : même si deux utilisateurs ont le même mot de passe "123456", leurs hashs en base seront totalement différents. bcrypt.hash() le génère automatiquement, on n'a pas à le gérer soi-même.
Q : Qu'est-ce qu'un JWT ? Que contient-il ?
JSON Web Token = 3 parties séparées par des points :
header.payload.signature
• Header : algorithme utilisé (HS256)
• Payload : données (id, role, date expiration)
• Signature : hash(header+payload+clé_secrète) — garantit que personne n'a modifié le token
Dans Lumina Pro le payload contient { id: 1, role: "admin" } et il expire après 24h.

6. Routes des tâches (routes/tasks.js)

GET /api/tasks — Récupérer toutes les tâches

SELECT tasks.*, users.name as assigned_name
FROM tasks
LEFT JOIN users ON tasks.id_assigned = users.id
ORDER BY id_col ASC, created_at DESC

LEFT JOIN — pourquoi pas INNER JOIN ?

INNER JOIN n'affiche que les lignes qui correspondent des deux côtés. Si une tâche n'est pas assignée (id_assigned = NULL), INNER JOIN la ferait disparaître. LEFT JOIN garde toutes les tâches et met NULL dans assigned_name si personne n'est assigné.

ORDER BY — pourquoi deux colonnes ?

  • id_col ASC : groupe les tâches par colonne
  • created_at DESC : dans chaque colonne, les plus récentes en haut

POST /api/tasks — Créer une tâche

// Si aucune colonne fournie → cherche la 1ère colonne existante
const findColSql = "SELECT id FROM columns ORDER BY position ASC LIMIT 1";

// Ensuite insère la tâche avec des ? (requête préparée = anti-injection SQL)

req.db.query(sql, [title, description, priority, targetCol, id_assigned || null]);

PUT /api/tasks/:id — Modifier OU déplacer une tâche

La même route sert pour modifier le titre/description ET pour déplacer une tâche (changer id_col). La requête SQL est construite dynamiquement selon ce qui est envoyé.

// Construction dynamique du UPDATE
let sql = "UPDATE tasks SET ";
let params = [];

if (title)      { sql += "title = ?, ";       params.push(title); }
if (id_col)     { sql += "id_col = ?, ";      params.push(id_col); }
// ... etc

sql = sql.slice(0, -2); // enlève la dernière virgule ", "
sql += " WHERE id = ?";
params.push(taskId);

// Exemple de résultat quand on déplace une tâche :
// "UPDATE tasks SET id_col = ? WHERE id = ?"  params = [3, 7]
Q : Qu'est-ce qu'une requête préparée ? Pourquoi l'utiliser ?
Une requête préparée utilise des ? comme espaces réservés. Le driver mysql2 remplace les ? par les vraies valeurs en les échappant automatiquement. Cela empêche l'injection SQL. Exemple sans requête préparée : si un utilisateur met ' OR '1'='1 dans le titre, une requête non protégée pourrait retourner toutes les tâches. Avec les ?, mysql2 échappe les guillemets et l'attaque échoue.

renderBoard() — filter, map, join expliqués

function renderBoard(columns, tasks) {
    columns.forEach(col => {

        // filter() → garde seulement les tâches de cette colonne
        const colTasks = tasks.filter(t => t.id_col === col.id);
        // Exemple : tasks = [{id:1, id_col:2}, {id:2, id_col:3}]
        // Pour la colonne 2 → filtre garde seulement {id:1, id_col:2}

        // map() → transforme chaque tâche en HTML
        // join('') → colle tous les morceaux HTML sans virgule
        const html = colTasks.map(task => `
            <div class="task-card">
                <h5>${escapeHTML(task.title)}</h5>
                // escapeHTML() = protection XSS sur chaque donnée affichée
            </div>
        `).join('');
    });
}
Q : Pourquoi utiliser filter().map().join() ?
C'est un pattern fonctionnel JavaScript :
• filter() : sélectionne les tâches de la bonne colonne
• map() : transforme chaque objet tâche en chaîne HTML
• join('') : concatène tous les morceaux en une seule chaîne sans virgule
C'est plus lisible et concis qu'une boucle for classique avec une variable accumulatrice.

10. api.js — authFetch() et escapeHTML()

authFetch() — le wrapper fetch avec JWT

frontend/js/api.js
async function authFetch(url, options = {}) {
    // 1. Lire le token dans le tiroir du navigateur
    const token = localStorage.getItem('token');

    // 2. Créer les headers si absents
    if (!options.headers) options.headers = {};

    // 3. Ajouter le token dans le header Authorization
    if (token) {
        options.headers['Authorization'] = `Bearer ${token}`;
    }
    // Résultat : chaque requête envoyée a le header :
    // Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

    // 4. Ajouter Content-Type si on envoie du JSON
    if (options.body && typeof options.body === 'string') {
        options.headers['Content-Type'] = 'application/json';
    }

    const response = await fetch(url, options);

    // 5. Si le token est expiré → déconnexion automatique
    if (response.status === 401) {
        localStorage.clear();
        window.location.href = 'login.html';
        throw new Error("Session expirée");
    }

    return response;
}

Pourquoi créer cette fonction ? (principe DRY)

DRY = Don't Repeat Yourself. Sans authFetch(), on devrait copier-coller le header Authorization dans chaque fetch() du projet (kanban.js, tasks.js, columns.js, team.js...). En centralisant dans authFetch(), si on change le format du token, on ne modifie qu'à un seul endroit.

escapeHTML() — protection XSS

function escapeHTML(str) {
    if (!str) return '';
    return str.toString()
        .replace(/&/g,  '&amp;')   // &  → &amp;
        .replace(/</g,  '&lt;')    // <  → &lt;   (empêche les balises HTML)
        .replace(/>/g,  '&gt;')    // >  → &gt;
        .replace(/"/g,  '&quot;')  // "  → &quot;
        .replace(/'/g,  '&#39;');  // '  → &#39;
}
Q : Comment fonctionne une attaque XSS ? Comment tu t'en protèges ?
Sans protection, si un utilisateur crée une tâche avec le titre <script>alert('volé!')</script>, ce code s'exécuterait dans le navigateur de chaque utilisateur qui voit le tableau — et pourrait voler leurs tokens JWT via localStorage.getItem('token').

Ma fonction escapeHTML() transforme les < en &lt; et > en &gt;. Ainsi le navigateur affiche le texte tel quel au lieu de l'interpréter comme du code. J'applique escapeHTML() sur tous les titres, descriptions et noms affichés dans renderBoard() et showTeam().

11. Questions jury — Réponses prêtes à dire

Questions sur le code

Q : Explique-moi le flux de connexion de A à Z.
1. L'utilisateur saisit email + mot de passe dans login.html
2. auth.js envoie une requête POST /api/auth/login avec ces données en JSON
3. Le serveur cherche l'email dans la table users
4. Si trouvé, bcrypt.compare() compare le mot de passe saisi avec le hash stocké
5. Si correspondance : jwt.sign() crée un token avec l'id et le rôle, expire dans 24h
6. Le serveur renvoie { token, user }
7. Le frontend stocke le token dans localStorage
8. L'utilisateur est redirigé vers index.html (le kanban)
Q : Comment fonctionne ton système de rôles ?
Il y a deux rôles : admin et user. Le rôle est stocké dans la table users (ENUM). Lors du login, le rôle est inclus dans le payload du JWT. Côté frontend, on lit localStorage.getItem('user') et on cache ou affiche l'onglet Équipe selon le rôle. Mais cette vérification frontend n'est que visuelle — la vraie sécurité est côté serveur : verifyToken s'exécute avant chaque route et place req.user. Un utilisateur qui essaierait de forcer l'accès à /api/users en manipulant le frontend recevrait quand même une erreur 403 du serveur.
Q : Qu'est-ce qu'une API REST ?
REST = Representational State Transfer. C'est un style d'architecture pour des API. Les principes : chaque ressource a une URL unique (/api/tasks), les opérations utilisent les méthodes HTTP (GET=lire, POST=créer, PUT=modifier, DELETE=supprimer), le serveur est stateless (sans état = il ne mémorise pas les sessions, le token JWT porte toutes les infos). Dans Lumina Pro j'ai 4 ressources : auth, tasks, columns, users.
Q : C'est quoi CORS et pourquoi tu en as besoin ?
CORS = Cross-Origin Resource Sharing. Par sécurité, les navigateurs bloquent les requêtes JavaScript vers un domaine/port différent de celui de la page. Mon frontend tourne sur le port 5500 (Live Server) et mon backend sur le port 3000. Sans app.use(cors()), toutes les requêtes fetch() seraient bloquées par le navigateur avec une erreur "blocked by CORS policy". Le middleware cors() ajoute des headers HTTP qui autorisent cette communication.
Q : Qu'est-ce que async/await ?
JavaScript est mono-thread — une seule chose à la fois. Quand on fait une requête réseau (fetch), ça prend du temps. async/await permet d'attendre le résultat sans bloquer toute la page. "async" devant une fonction dit qu'elle peut contenir des opérations asynchrones. "await" met en pause juste cette fonction (pas le reste) jusqu'à recevoir le résultat. C'est plus lisible que les callbacks ou les .then().catch().
Q : Quelle est la différence entre le frontend et le backend ?
Le frontend est ce que l'utilisateur voit et avec quoi il interagit — HTML, CSS, JavaScript dans le navigateur. Il ne doit jamais être considéré comme sécurisé car l'utilisateur peut modifier le code JS dans les devtools. Le backend tourne sur le serveur, hors d'atteinte de l'utilisateur. C'est lui qui fait la vraie vérification de sécurité (token JWT, droits d'accès, validation des données). Dans Lumina Pro : le frontend cache l'onglet Équipe aux non-admins, mais c'est le backend qui empêche réellement un non-admin d'accéder aux données utilisateurs.
Q : Tu aurais pu faire quoi de mieux en production ?
Plusieurs choses :
1. Mettre la clé secrète JWT dans un fichier .env (jamais hardcodée dans le code)
2. Utiliser HTTPS pour que les tokens soient chiffrés en transit
3. Stocker le JWT dans un cookie HttpOnly au lieu de localStorage (résistant au XSS)
4. Ajouter du rate limiting (express-rate-limit) pour bloquer les attaques brute-force
5. Vérifier le rôle admin côté serveur avant les suppressions d'utilisateurs
6. Ajouter une validation plus stricte des données d'entrée (longueur, format)
Q : C'est quoi un token JWT structurellement ?
Un JWT est une chaîne en 3 parties séparées par des points : header.payload.signature
Les trois parties sont encodées en Base64.
• Header : {"alg":"HS256","typ":"JWT"}
• Payload : {"id":1,"role":"admin","iat":172...,"exp":172...}
• Signature : HMACSHA256(base64(header)+"."+base64(payload), clé_secrète)
La signature garantit l'intégrité : si quelqu'un modifie le payload pour se donner le rôle admin, la signature ne correspond plus et jwt.verify() lève une erreur.
Q : Explique le principe MVC dans ton projet.
MVC = Model-View-Controller. Dans Lumina Pro :
• Model = la base de données MySQL (structure des tables, données)
• View = les fichiers HTML/CSS + les fonctions JS qui génèrent le HTML (renderBoard)
• Controller = les routes Express (tasks.js, columns.js, auth.js) qui reçoivent les requêtes, interrogent la BDD et renvoient les données
C'est une architecture qui sépare les responsabilités pour garder le code organisé.
Q : Comment as-tu géré la relation entre tâches et colonnes ?
J'ai utilisé une clé étrangère (FOREIGN KEY) : la colonne id_col dans la table tasks fait référence à la colonne id de la table columns. Cela garantit qu'une tâche ne peut pas référencer une colonne qui n'existe pas. J'ai ajouté ON DELETE CASCADE pour que si une colonne est supprimée, toutes ses tâches le soient aussi automatiquement — évitant des données orphelines.

Q : Pourquoi Vanilla JS et pas React/Vue ?
Choix délibéré pour ce projet : maîtriser les fondamentaux avant les frameworks. Vanilla JS m'a obligée à comprendre le DOM, les événements, les requêtes fetch, le cycle de vie d'une page. Les frameworks comme React rajoutent une couche d'abstraction au-dessus de ces mécanismes. Pour une application de cette taille, Vanilla JS reste lisible et performant sans les contraintes d'un build system.

12. Résumé express — Ce qu'il faut savoir par cœur

Fichiers clés backend

  • js/tasks.js — editTask + moveTask

Mécanismes de sécurité

  • SQL Injection Requêtes préparées avec ?
  • XSS escapeHTML() sur tout le HTML généré
  • Auth JWT dans header Authorization
  • Passwords bcrypt hash (10 rounds + salt)
  • Session Token expire après 24h

Codes HTTP à connaître

  • 200 — OK
  • 201 — Created (après POST)
  • 400 — Bad Request (données manquantes)
  • 401 — Unauthorized (token absent)
  • 403 — Forbidden (token invalide/expiré)
  • 500 — Internal Server Error

⚠️ Pièges à éviter à l'oral

  • Ne pas dire "ça crypte le mot de passe" — dire "ça le hache (hash)". bcrypt est irréversible, ce n'est pas du chiffrement.
  • Ne pas confondre 401 (non authentifié) et 403 (non autorisé)
  • Ne pas dire "le frontend vérifie le rôle" sans ajouter "mais c'est le backend qui fait la vraie sécurité"
  • Ne pas dire "le JWT est chiffré" — il est encodé en Base64 et signé, pas chiffré. N'importe qui peut lire le payload avec atob().
