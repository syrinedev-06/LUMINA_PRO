Pourquoi Lumina Pro ?
Besoin identifié : Les équipes ont besoin d'un outil simple et visuel pour organiser leur travail au quotidien, sans la complexité de solutions comme Jira ou Trello.
Fonctionnalités clés
  • Tableau Kanban avec colonnes personnalisables
  • Gestion des tâches (créer, modifier, déplacer, supprimer)
  • Authentification sécurisée JWT + bcrypt
  • Gestion d'équipe avec rôles admin/user
  • Système de logs pour l'audit des actions
  • Interface responsive adaptée mobile
  • Documentation API avec Swagger
Cibles utilisateurs

👑 Admin

Gère les colonnes, les utilisateurs et toutes les tâches

👤 Utilisateur

Crée et déplace des tâches, voit le kanban

RELATIONS

10
Clés étrangères et comportements
-- Supprimer un utilisateur → tâches restent (id_assigned = NULL) FOREIGN KEY (id_assigned) REFERENCES users(id) ON DELETE SET NULL -- Supprimer une colonne → ses tâches supprimées automatiquement FOREIGN KEY (id_col) REFERENCES columns(id) ON DELETE CASCADE
🔗

ON DELETE CASCADE

Si on supprime la colonne "À faire", toutes ses tâches sont supprimées automatiquement par MySQL — sans code supplémentaire.

🔓

ON DELETE SET NULL

Si on supprime un utilisateur, ses tâches restent mais id_assigned passe à NULL. Elles deviennent "non assignées".

LEFT JOIN vs INNER JOIN : Le GET /api/tasks utilise LEFT JOIN pour retourner toutes les tâches, même celles non assignées (id_assigned = NULL). Un INNER JOIN les ferait disparaître.

SÉCU­RITÉ

13
4 couches de protection
🔐

SQL Injection → Requêtes préparées

db.query("SELECT * FROM users WHERE email = ?", [email]) — les ? échappent automatiquement les valeurs malveillantes.

🛡️

XSS → escapeHTML()

Toute donnée affichée dans le DOM passe par escapeHTML() qui remplace < > & " ' par leurs entités HTML.

🔑

Mots de passe → bcrypt (10 rounds)

Hachage irréversible + sel aléatoire unique par mot de passe. Impossible de retrouver le mot de passe original même si la BDD est volée.

🚪

CSRF → JWT dans header Authorization

Le token dans localStorage n'est jamais envoyé automatiquement — contrairement aux cookies. Un site malveillant ne peut pas l'inclure dans ses requêtes forgées.

RÉALI­SATION PERSON­NELLE

16
authFetch() — Wrapper d'authentification
// frontend/js/api.js async function authFetch(url, options = {}) { const token = localStorage.getItem('token'); options.headers = { 'Content-Type': 'application/json', 'Authorization': `Bearer ${token}`, ...options.headers }; const response = await fetch(url, options); // Token expiré → redirection automatique vers le login if (response.status === 401) { localStorage.clear(); window.location.href = 'login.html'; } return response; }
Principe DRY : Sans authFetch(), chaque appel fetch devrait répéter l'en-tête Authorization. Une modification du format du token nécessiterait de changer des dizaines d'endroits.

RÉALI­SATION PERSON­NELLE

17
escapeHTML() — Protection XSS
// frontend/js/api.js — Neutralise les injections de scripts function escapeHTML(str) { if (!str) return ''; return str.toString() .replace(/&/g, "&amp;") .replace(/</g, "&lt;") .replace(/>/g, "&gt;") .replace(/"/g, "&quot;") .replace(/'/g, "&#39;"); }

❌ Sans protection

Titre : <script>alert('XSS')</script>

→ Le script s'exécute dans le navigateur de tous les visiteurs

✅ Avec escapeHTML()

&lt;script&gt;alert('XSS')&lt;/script&gt;

→ Affiché comme texte inoffensif

// backend/middleware/security.js function verifyToken(req, res, next) { const authHeader = req.headers['authorization']; // 1. Token absent → 401 Unauthorized if (!authHeader || !authHeader.startsWith('Bearer ')) { return res.status(401).json({ error: 'Token manquant' }); } const token = authHeader.split(' ')[1]; // extrait après "Bearer " try { // 2. Vérif signature + expiration → injecte req.user const decoded = jwt.verify(token, 'lumina_secret'); req.user = decoded; // { id: 1, role: 'admin', exp: ... } next(); } catch (err) { // 3. Token expiré ou falsifié → 403 Forbidden return res.status(403).json({ error: 'Token invalide' }); } }

BCRYPT

21
Hachage des mots de passe
// Inscription — hash irréversible avec sel aléatoire const hash = await bcrypt.hash(password, 10); // → "$2b$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LPVhrNpFVK" // Connexion — compare sans décrypter const match = await bcrypt.compare(password, user.password); // → true ou false

Hachage (bcrypt)

  • Irréversible — sens unique
  • Sel aléatoire unique par password
  • 10 rounds = lent intentionnellement
  • Même password = hash différent

Chiffrement (AES)

  • Réversible avec une clé
  • Pour les données à transmettre
  • Ne s'utilise PAS pour les passwords

POINT DE DIFFI­CULTÉ

23
Requête SQL dynamique (PUT /api/tasks)
Problème : Le frontend peut envoyer n'importe quelle combinaison de champs à modifier (titre seul, colonne seule, ou les deux). Comment construire une requête UPDATE flexible sans dupliquer le code ?
// Solution : construction dynamique du SET let sql = "UPDATE tasks SET "; const params = []; if (title !== undefined) { sql += "title = ?, "; params.push(title); } if (id_col !== undefined) { sql += "id_col = ?, "; params.push(id_col); } // slice(0,-2) → retire la virgule finale ", " sql = sql.slice(0, -2) + " WHERE id = ?"; params.push(id);

Cette approche permet à moveTask() (qui n'envoie que id_col) et au formulaire d'édition (qui envoie tous les champs) d'utiliser la même route PUT.
