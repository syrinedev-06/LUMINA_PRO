QCM Version Simplifiée

Version débutante 108 questions
Version simplifiée — pour mieux retenir ! Les mêmes questions que le QCM complet, mais avec des réponses courtes, claires et faciles à mémoriser. Des exemples concrets du projet Lumina pour que ce soit vivant. Clique sur une question pour voir la réponse.
Partie 1 — JavaScript de base
Q1 Qu'est-ce que async/await ? ▶

C'est une façon d'attendre le résultat d'une opération qui prend du temps (comme appeler un serveur), sans bloquer la page.

Imagine que tu commandes une pizza. Tu peux faire autre chose en attendant. Quand elle arrive, tu la récupères. C'est ça await.
Dans Lumina : on l'utilise dans fetchTasks() pour attendre la réponse du serveur avant d'afficher les tâches.
Q2 Que se passe-t-il si on oublie await devant authFetch() ? ▶

On reçoit une promesse non résolue au lieu des vraies données. C'est comme ouvrir une boîte vide.

Résultat : le kanban ne s'affiche pas, erreur dans la console.
Q3 Quelle est la différence entre localStorage et sessionStorage ? ▶

localStorage : reste même si tu fermes le navigateur. Lumina l'utilise pour garder le token JWT.

sessionStorage : effacé dès que tu fermes l'onglet.

Retenir : local = permanent, session = temporaire.
Q4 Pourquoi e.preventDefault() dans le formulaire de login ? ▶

Sans ça, le navigateur recharge la page en envoyant le formulaire à l'ancienne (méthode HTML classique). On perd tout.

preventDefault() = "arrête le comportement par défaut, je gère moi-même avec fetch."
Q5 Que fait .filter() dans renderBoard() ? ▶

Il trie les tâches par colonne. Pour chaque colonne, on garde uniquement les tâches dont l'id_col correspond à l'ID de la colonne.

Toutes les tâches → filtre → seulement celles de "À faire".
Q6 Quelle est la différence entre .map() et .forEach() ? ▶

.map() : transforme chaque élément et retourne un nouveau tableau.

.forEach() : fait une action sur chaque élément mais ne retourne rien.

Dans Lumina : .map() transforme les tâches en HTML. .forEach() parcourt les colonnes.
Q7 Pourquoi .join('') après .map() ? ▶

.map() retourne un tableau de morceaux HTML. .join('') les colle ensemble en une seule chaîne pour pouvoir l'injecter dans la page.

["<div>tâche1</div>", "<div>tâche2</div>"] → "<div>tâche1</div><div>tâche2</div>"
Q8 Qu'est-ce que les template literals (backticks) ? ▶

Des chaînes de caractères entourées de ` (backtick). Elles permettent d'insérer des variables directement avec ${variable}.

Avant : "Bonjour " + nom
Avec template literal : `Bonjour ${nom}`
Dans Lumina : utilisé partout pour générer le HTML du kanban.
Q9 Quelle est la différence entre == et === ? ▶

== : compare les valeurs en changeant le type si nécessaire. "5" == 5 → vrai !

=== : compare valeur ET type. "5" === 5 → faux.

Toujours utiliser === pour être sûr. Lumina l'utilise pour comparer les IDs.
Q10 Qu'est-ce que DOMContentLoaded ? ▶

C'est un événement qui dit : "la page HTML est entièrement chargée". On l'écoute pour être sûr que les boutons et formulaires existent avant d'y toucher en JS.

Si tu essaies d'accéder à un bouton avant qu'il existe dans la page → ça plante. DOMContentLoaded évite ça.
Partie 2 — Fetch API & HTTP
Q11 Les 4 méthodes HTTP principales ? ▶

GET → lire (récupérer les tâches)

POST → créer (nouvelle tâche)

PUT → modifier (déplacer une tâche)

DELETE → supprimer (effacer une tâche)

Moyen mnémotechnique : GPMD = Get/Post/Modify/Delete
Q12 Différence entre POST et PUT ? ▶

POST : crée quelque chose de nouveau. Chaque POST crée un nouvel élément.

PUT : modifie quelque chose qui existe déjà à un endroit précis.

POST = "ajouter une tâche". PUT = "modifier le titre de la tâche n°5".
Q13 Que signifient les codes HTTP 200, 201, 400, 401, 403, 500 ? ▶

200 = Succès

201 = Créé avec succès

400 = Mauvaise requête (données incorrectes)

401 = Non connecté

403 = Connecté mais accès refusé (token expiré)

500 = Erreur du serveur (bug côté serveur)

2xx = bien / 4xx = faute du client / 5xx = faute du serveur
Q14 Que contient l'en-tête Authorization ? ▶

Authorization: Bearer [ton token JWT]

C'est comme montrer ta carte d'identité à chaque requête. authFetch() l'ajoute automatiquement.

Bearer = porteur. Tu "portes" ton token pour prouver qui tu es.
Q15 Différence entre en-têtes (headers) et body ? ▶

Headers : informations sur la requête (qui tu es, quel format tu envoies). Comme l'enveloppe d'un colis.

Body : les vraies données envoyées. Comme le contenu du colis.

GET et DELETE n'ont pas de body. POST et PUT en ont un.
Q16 Pourquoi Content-Type: application/json ? ▶

C'est pour dire au serveur "ce que je t'envoie est du JSON". Sans ça, le serveur ne sait pas comment lire les données et req.body sera vide.

Q17 Que font JSON.stringify() et JSON.parse() ? ▶

JSON.stringify() : objet JavaScript → texte JSON. Pour envoyer des données.

JSON.parse() : texte JSON → objet JavaScript. Pour lire des données.

stringify = "empaqueter". parse = "déballer".
Q18 Que se passe-t-il si le serveur est éteint ? ▶

La requête échoue. Le catch dans fetchTasks() attrape l'erreur et affiche "Impossible de se connecter au serveur" en rouge.

Le try/catch empêche l'appli de planter silencieusement.
Q19 Différence entre CORS et Authorization ? ▶

CORS : règle du navigateur qui dit "ce site a-t-il le droit d'appeler ce serveur ?". cors() dans Express l'autorise.

Authorization : "est-ce que cet utilisateur est connecté ?"

CORS = droit du site. Authorization = droit de l'utilisateur.
Q20 Pourquoi l'API retourne du JSON ? ▶

JSON est le format standard des API web. Il est léger, lisible par les humains et compris nativement par JavaScript.

Tous les navigateurs et langages comprennent le JSON — c'est la "langue commune" du web.
Partie 3 — JWT & Authentification
Q21 Qu'est-ce qu'un JWT ? ▶

Un JWT (JSON Web Token) est un badge numérique en 3 parties séparées par des points :
Header (algorithme) . Payload (tes infos : id, rôle) . Signature (vérification)

Comme une carte d'identité : nom visible, mais impossible à falsifier sans le sceau officiel.
Q22 Différence entre JWT et session classique ? ▶

Session classique : le serveur stocke qui tu es en base de données. Il doit vérifier à chaque fois.

JWT : tout est dans le token. Le serveur vérifie juste la signature. Pas besoin de BDD.

JWT = le serveur se souvient pas de toi, mais ton badge contient tout.
Q23 Le payload JWT est visible mais pas falsifiable — pourquoi ? ▶

Le payload est encodé en Base64 (pas chiffré) → n'importe qui peut le lire. Mais la signature est faite avec une clé secrète. Si quelqu'un modifie le payload, la signature ne correspond plus → le serveur rejette le token.

Visible oui, modifiable non — sans la clé secrète.
Q24 Que se passe-t-il si le JWT expire ? ▶

Le serveur refuse la requête (erreur 403). Lumina redirige automatiquement vers la page de login.

Dans Lumina : tokens valables 24h. Après, il faut se reconnecter.
Q25 Pourquoi ne jamais mettre le mot de passe dans le payload JWT ? ▶

Le payload est lisible par tout le monde (Base64 décodable). Si le token est volé, le mot de passe serait exposé.

Dans le payload : seulement l'ID et le rôle. Jamais de mot de passe ou d'infos sensibles.
Q26 Que font jwt.sign() et jwt.verify() ? ▶

jwt.sign() : crée le token au moment de la connexion.

jwt.verify() : vérifie que le token est valide et non expiré à chaque requête.

sign = "tamponner la carte". verify = "contrôler la carte à l'entrée".
Q27 Pourquoi SECRET_KEY doit être dans un .env ? ▶

Si la clé secrète est dans le code et que le code est sur GitHub, n'importe qui peut fabriquer de faux tokens et usurper n'importe quel compte.

Le fichier .env n'est pas envoyé sur GitHub (.gitignore). La clé reste privée.
Q28 Que se passe-t-il si on supprime verifyToken ? ▶

Toutes les routes deviennent publiques. N'importe qui peut lire, créer, modifier et supprimer toutes les données sans être connecté.

L'API est entièrement ouverte — catastrophique en production.
Q29 Différence entre 401 et 403 dans verifyToken ? ▶

401 : "Vous n'êtes pas connecté" (pas de token).

403 : "Vous êtes connecté mais votre accès est refusé" (token expiré ou invalide).

401 = "Qui êtes-vous ?" | 403 = "Votre badge n'est plus valide."
Q30 Que contient req.user après verifyToken ? ▶

Les informations du token décodé : { id: 1, role: "admin" }

Les routes peuvent ensuite utiliser req.user.id pour savoir qui fait la requête.

Partie 4 — bcrypt & Mots de passe
Q31 Différence entre hachage et chiffrement ? ▶

Hachage : à sens unique, irréversible. On ne peut jamais retrouver l'original. Pour les mots de passe.

Chiffrement : réversible avec une clé. Pour les données à envoyer.

Pour les mots de passe : toujours hacher (pas besoin de lire le vrai mot de passe, juste vérifier).
Q32 Que fait bcrypt.hash(password, 10) ? ▶

Il transforme le mot de passe en une chaîne illisible (hash). Le 10 = nombre de fois que l'algorithme tourne. Plus c'est élevé, plus c'est lent et sécurisé.

"Lumina1!" → "$2b$10$abc123..." (chaîne illisible de 72 caractères)
Q33 Comment bcrypt.compare() fonctionne ? ▶

Il prend le mot de passe saisi par l'utilisateur, le hache avec le même sel que le hash stocké, et compare. Il retourne true ou false.

On ne "déchiffre" jamais le mot de passe — on compare deux hashes.
Q34 Pourquoi ne jamais stocker les mots de passe en clair ? ▶

Si la base de données est piratée, tous les mots de passe seraient visibles. Et les gens utilisent souvent le même mot de passe partout.

Avec bcrypt : même si la BDD est volée, les mots de passe restent illisibles.
Q35 Pourquoi pas MD5 ou SHA-1 pour les mots de passe ? ▶

MD5 et SHA-1 sont très rapides → un attaquant peut essayer des milliards de mots de passe par seconde. bcrypt est lentement conçu exprès pour rendre le bruteforce impossible.

Q36 Qu'est-ce qu'un sel (salt) dans bcrypt ? ▶

Une valeur aléatoire unique ajoutée à chaque mot de passe avant de le hacher. Ça garantit que deux personnes avec le même mot de passe auront des hashes différents.

Comme ajouter un ingrédient secret différent à chaque recette.
Partie 5 — Base de données SQL
Q37 Qu'est-ce qu'une clé primaire (PRIMARY KEY) ? ▶

Un identifiant unique pour chaque ligne d'une table. Dans Lumina : id INT AUTO_INCREMENT PRIMARY KEY. Chaque tâche a un ID unique créé automatiquement.

Q38 Qu'est-ce qu'une clé étrangère (FOREIGN KEY) ? ▶

Un champ qui pointe vers l'ID d'une autre table. Dans Lumina : id_col dans les tâches pointe vers l'ID d'une colonne.

Ça empêche de créer une tâche dans une colonne qui n'existe pas.
Q39 Différence entre ON DELETE CASCADE et ON DELETE SET NULL ? ▶

CASCADE : si on supprime une colonne → toutes ses tâches sont supprimées automatiquement.

SET NULL : si on supprime un utilisateur → les tâches restent mais leur id_assigned devient vide (NULL).

Q40 Pourquoi LEFT JOIN plutôt que INNER JOIN ? ▶

INNER JOIN : affiche seulement les lignes qui ont une correspondance des deux côtés → les tâches non assignées disparaissent !

LEFT JOIN : affiche toutes les tâches, même celles sans utilisateur assigné.

LEFT JOIN = "garde toutes les tâches, même sans assignation".
Q41 Qu'est-ce qu'une requête préparée et pourquoi protège-t-elle contre l'injection SQL ? ▶

On utilise des ? à la place des valeurs. Le driver MySQL traite les valeurs séparément → elles ne peuvent jamais devenir des instructions SQL.

Au lieu de : "WHERE email = '" + email + "'"
On écrit : "WHERE email = ?" avec [email] en paramètre.
Q42 Que fait SELECT MAX(position) FROM columns ? ▶

Retourne la valeur maximale du champ position. Utilisé pour calculer la position de la prochaine colonne (MAX + 1).

Q43 Pourquoi ORDER BY position ASC ? ▶

Sans tri, MySQL peut retourner les colonnes dans n'importe quel ordre. ORDER BY position ASC garantit qu'elles apparaissent toujours de gauche à droite dans le bon ordre.

Q44 Que signifie ENUM('high', 'medium', 'low') ? ▶

ENUM limite les valeurs possibles à une liste définie. Si on essaie de mettre 'critique', MySQL refuse. Ça garantit que la priorité est toujours l'une des 3 valeurs.

Q45 Différence entre VARCHAR(255) et TEXT ? ▶

VARCHAR(255) : texte court, max 255 caractères. Pour les titres, emails, noms.

TEXT : texte long. Pour les descriptions qui peuvent être longues.

Q46 Qu'est-ce que TIMESTAMP DEFAULT CURRENT_TIMESTAMP ? ▶

MySQL remplit automatiquement ce champ avec la date et heure actuelles quand on insère une ligne. Dans Lumina : created_at sur les tâches et les utilisateurs.

Q47 Que se passe-t-il si on supprime ON DELETE CASCADE sur id_col ? ▶

MySQL refusera de supprimer une colonne si elle a encore des tâches. On serait obligé de supprimer toutes les tâches manuellement avant.

Q48 Pourquoi ne jamais faire SELECT * sur la table users ? ▶

Ça retournerait aussi le champ password (même haché, c'est sensible). On sélectionne uniquement les champs nécessaires : id, name, email, role.

Q49 Qu'est-ce que req.params.id ? ▶

C'est la valeur dynamique dans l'URL. Dans DELETE /api/tasks/5, req.params.id = "5".

Le :id dans la route capture ce qui vient dans l'URL à cet endroit.
Q50 Comment fonctionne sql.slice(0, -2) dans le PUT tasks ? ▶

La requête SQL construite dynamiquement se termine par une virgule en trop (", "). .slice(0, -2) supprime les 2 derniers caractères pour avoir une requête SQL valide.

Partie 6 — Node.js & Express
Q51 Qu'est-ce qu'Express.js ? ▶

Un framework pour Node.js qui simplifie la création de serveurs web et d'APIs. C'est le cœur du back-end de Lumina.

Node.js = moteur. Express = la voiture toute montée.
Q52 Qu'est-ce qu'un middleware Express ? ▶

Une fonction qui s'exécute entre la réception d'une requête et l'envoi de la réponse. Elle reçoit (req, res, next) et peut modifier la requête ou l'arrêter.

Comme un agent de sécurité à l'entrée : il vérifie ton ticket avant de te laisser passer.
Q53 Dans quel ordre les middlewares s'exécutent-ils ? ▶

Dans l'ordre où ils sont déclarés dans le code. Pour Lumina : cors → express.json → injection BDD → verifyToken → route.

Q54 Que fait app.use('/api/tasks', verifyToken, require('./routes/tasks')) ? ▶

Pour toute requête vers /api/tasks : d'abord verifyToken vérifie le JWT. Si OK, la requête passe au fichier routes/tasks.js.

Q55 Différence entre app.use() et app.get() ? ▶

app.use() : répond à toutes les méthodes HTTP (GET, POST...). Utilisé pour les middlewares et routeurs.

app.get() : répond uniquement aux requêtes GET.

Q56 Que fait module.exports = router ? ▶

C'est la façon dont Node.js exporte un module pour qu'un autre fichier puisse l'importer avec require(). Sans ça, le routeur serait inaccessible.

Q57 Qu'est-ce que CORS et pourquoi est-il nécessaire ? ▶

Le navigateur bloque par défaut les requêtes vers un domaine/port différent. app.use(cors()) autorise le frontend (port 80) à appeler le backend (port 3000).

Sans cors() : "Blocked by CORS policy" dans la console.
Q58 Que se passe-t-il si on retire app.use(express.json()) ? ▶

req.body sera undefined pour toutes les requêtes POST/PUT. Les routes ne pourront pas lire les données envoyées.

Partie 7 — Sécurité Web (OWASP)
Q59 Qu'est-ce qu'une injection SQL ? ▶

Un attaquant écrit du code SQL dans un formulaire pour manipuler la base de données.

Email saisi : admin@lumina.com' OR '1'='1
→ donne accès à tous les comptes sans mot de passe !
Protection : requêtes préparées avec ?.
Q60 Qu'est-ce qu'une faille XSS ? ▶

Un attaquant injecte du JavaScript malveillant dans la page. Si on affiche le titre d'une tâche sans l'échapper, une tâche nommée <script>alert('piraté')</script> exécuterait du code !

Protection : escapeHTML() transforme les < en &lt; — inoffensif.
Q61 Qu'est-ce qu'une attaque CSRF ? ▶

Un site malveillant force ton navigateur à envoyer une requête à Lumina sans que tu le saches. Lumina est protégé car le JWT est dans le header Authorization — un site tiers ne peut pas y accéder.

Q62 Différence entre authentification et autorisation ? ▶

Authentification : "Qui es-tu ?" → login/mot de passe → JWT.

Autorisation : "As-tu le droit ?" → vérification du rôle (admin ou user).

Carte d'identité = authentification. Ticket VIP = autorisation.
Q63 Pourquoi cacher l'onglet "Équipe" côté frontend ne suffit pas ? ▶

N'importe qui peut appeler directement l'API avec Postman ou modifier le localStorage dans les DevTools. La vraie sécurité est toujours côté serveur.

Ce qu'on cache dans l'interface peut toujours être contourné. Vérifier côté serveur.
Q64 Qu'est-ce que le principe du "moindre privilège" ? ▶

Donner à chaque utilisateur uniquement les droits dont il a besoin. Un utilisateur normal ne peut pas supprimer d'autres comptes. Seul l'admin le peut.

Q65 Que sont les cookies HttpOnly et SameSite ? ▶

HttpOnly : le JavaScript ne peut pas lire ce cookie → protège contre le vol via XSS.

SameSite : le cookie n'est pas envoyé depuis d'autres sites → protège contre CSRF.

Lumina utilise localStorage (plus simple mais moins sécurisé). En production on préférerait des cookies HttpOnly.
Partie 8 — Architecture & Patterns
Q66 Qu'est-ce que l'architecture MVC ? ▶

Model : données (requêtes SQL, BDD).

View : affichage (HTML généré côté client).

Controller : logique entre les deux (fonctions JS comme renderBoard).

MVC = séparer ce qu'on affiche, ce qu'on stocke, et la logique du milieu.
Q67 Qu'est-ce qu'une API REST ? ▶

Une API qui utilise les méthodes HTTP (GET/POST/PUT/DELETE) sur des URLs précises pour faire des opérations sur des données. Répond en JSON.

/api/tasks + GET = lire les tâches. /api/tasks + POST = créer une tâche.
Q68 Pourquoi Lumina est-il divisé en 8 fichiers JS ? ▶

Principe de séparation des responsabilités : chaque fichier a un rôle précis. C'est plus facile à lire, maintenir et modifier sans tout casser.

Un seul gros fichier de 2000 lignes = cauchemar. 8 fichiers spécialisés = beaucoup mieux.
Q69 Qu'est-ce que le principe DRY ? ▶

Don't Repeat Yourself = ne pas copier-coller du code. Si la même chose est faite à plusieurs endroits, on la met dans une fonction.

Dans Lumina : authFetch() évite de réécrire le header JWT dans chaque fetch.
Q70 Qu'est-ce que Swagger ? ▶

Un outil de documentation d'API. Dans Lumina : accessible sur http://localhost:3000/api-docs. Permet de voir et tester tous les endpoints depuis le navigateur.

Partie 9 — Fonctionnalités de Lumina
Q71 Comment fonctionne la création d'une tâche de A à Z ? ▶

1. Clic "+" → modal s'ouvre
2. On remplit le formulaire
3. Clic "Enregistrer" → authFetch POST /api/tasks
4. Le serveur vérifie le JWT, insère en BDD, répond 201
5. Le frontend ferme le modal et recharge le kanban.

Q72 Comment fonctionne le déplacement d'une tâche ? ▶

Clic sur ⬅️ ou ➡️ → moveTask() → authFetch PUT /api/tasks/:id avec le nouvel id_col → serveur met à jour en BDD → kanban rechargé.

Q73 Comment fonctionne le renommage d'une colonne ? ▶

Clic ✏️ → prompt() demande le nouveau titre → authFetch PUT /api/columns/:id → BDD mise à jour → kanban rechargé.

Q74 Pourquoi fetchTasks() est appelée après chaque action ? ▶

Pour s'assurer que ce qu'on affiche est toujours synchronisé avec la base de données. Après chaque modification, on recharge les données réelles.

Q75 Pourquoi le profil ne fait pas de requête API ? ▶

Les infos de profil (nom, email, rôle) sont déjà dans le localStorage depuis la connexion. Pas besoin de redemander au serveur à chaque fois.

Q76 Que se passe-t-il côté BDD quand on supprime une colonne avec des tâches ? ▶

Grâce à ON DELETE CASCADE, MySQL supprime automatiquement toutes les tâches de la colonne en même temps. On n'a pas à le faire manuellement.

Q77 Comment Lumina assigne-t-il une tâche à la 1ère colonne par défaut ? ▶

Si aucune colonne n'est précisée, le serveur cherche la colonne avec la plus petite position (ORDER BY position ASC LIMIT 1) et l'utilise automatiquement.

Q78 Pourquoi la déconnexion ne "révoque" pas vraiment le JWT ? ▶

On supprime le token du localStorage mais le token reste techniquement valide 24h. Si quelqu'un l'a sauvegardé, il peut encore l'utiliser. Pour une vraie révocation il faudrait une blacklist côté serveur.

Q79 Comment les colonnes par défaut sont-elles créées au démarrage ? ▶

Au démarrage, le serveur vérifie si la table columns est vide. Si oui, il insère automatiquement "À faire", "En cours" et "Terminé". Ça ne se déclenche qu'une seule fois.

Q80 Comment loadUsers() remplit la liste déroulante ? ▶

Elle récupère la liste des utilisateurs de l'API, puis génère dynamiquement des <option> HTML pour chaque utilisateur. La valeur de chaque option est l'ID de l'utilisateur.

Partie 10 — CSS & Responsive
Q81 Comment fonctionne le responsive dans Lumina ? ▶

Via des media queries dans responsive.css. Sur mobile (< 900px), la sidebar se cache. Un bouton hamburger apparaît pour l'afficher/masquer.

Q82 Qu'est-ce que les variables CSS (--primary) ? ▶

Des variables définies une fois dans :root et réutilisées partout. Si on change --primary, la couleur change dans toute l'appli d'un seul coup.

Q83 Pourquoi les CSS sont-ils divisés en plusieurs fichiers ? ▶

Pour la lisibilité et la maintenance. Chaque fichier a un rôle (variables, layout, kanban, responsive...). style.css les importe tous avec @import.

Q84 Comment le mode sombre est-il géré ? ▶

Un toggle ajoute/retire la classe dark-mode sur le body. Le préférence est sauvegardée dans localStorage et appliquée dès le chargement de la page.

Partie 11 — Questions du jury
Q85 Qu'est-ce que vous referiez différemment ? ▶

• Mettre SECRET_KEY dans un .env
• Vérifier le rôle admin côté serveur pour /api/users
• Utiliser des cookies HttpOnly au lieu de localStorage
• Ajouter une validation plus stricte des données
• Utiliser HTTPS en production

Q86 Comment avez-vous géré la sécurité dans Lumina ? ▶

1. Injection SQL → requêtes préparées avec ?
2. XSS → escapeHTML() sur tout le contenu affiché
3. Authentification → JWT signé avec expiration 24h
4. Mots de passe → bcrypt (hachage irréversible)
5. CSRF → protection partielle via JWT dans le header

Q87 Expliquez la différence front-end / back-end dans Lumina. ▶

Front-end : ce que l'utilisateur voit dans son navigateur. HTML/CSS/JS. Fichiers : login.html, index.html, css/, js/.

Back-end : le serveur Node.js sur le port 3000. Gère l'auth, la BDD, la logique. Fichiers : server.js, routes/.

Q88 Pourquoi Node.js plutôt que PHP ? ▶

Node.js utilise JavaScript — le même langage que le front-end. C'est cohérent et ça évite de changer de langage. npm a un grand écosystème. Express est léger et flexible.

Q89 Qu'est-ce que le "Security by Design" ? ▶

Intégrer la sécurité dès le début, pas seulement après une attaque. Dans Lumina : les requêtes préparées, escapeHTML() et verifyToken ont été prévus dès la conception.

Q90 Qu'est-ce que l'OWASP Top 10 ? 3 vulnérabilités couvertes dans Lumina ? ▶

L'OWASP Top 10 est la liste des 10 failles web les plus courantes. Lumina couvre :

1. Injection SQL → requêtes préparées

2. XSS → escapeHTML()

3. Mots de passe faibles → bcrypt

Q91 Qu'est-ce que les propriétés ACID ? ▶

Atomicité : tout ou rien
Cohérence : données toujours valides
Isolation : les opérations ne se perturbent pas
Durabilité : données sauvegardées même en cas de panne

ACID = garanties que la BDD MySQL (InnoDB) respecte.
Q92 Qu'est-ce que la règle 3-2-1 de sauvegarde ? ▶

3 copies des données, sur 2 supports différents, dont 1 hors site (cloud, disque distant...).

Pour Lumina : code sur GitHub + local = 2 copies. La BDD devrait être sauvegardée avec mysqldump.
Q93 Qu'est-ce que le RGPD ? ▶

Règlement européen sur la protection des données personnelles. Pour Lumina : les mots de passe sont hachés ✅, les données peuvent être supprimées ✅. Mais il manque le consentement, la politique de confidentialité, etc.

Q94 Qu'est-ce qu'un MVP ? ▶

Minimum Viable Product : version minimale mais fonctionnelle d'un produit. Pour Lumina : kanban + tâches + auth JWT = MVP. Les notifications, paiements, etc. seraient pour plus tard.

Q95 Différence entre ESN, agence web et annonceur ? ▶

ESN : loue des développeurs à des clients (Capgemini, etc.)

Agence web : crée des sites pour des clients (projets à livrer)

Annonceur : entreprise qui développe ses propres produits en interne (startup, grande entreprise)

Q96 Qu'est-ce que la méthode Agile/Scrum ? ▶

Méthode de travail en petites étapes (sprints de 1-4 semaines). On livre une version fonctionnelle à chaque sprint. On s'adapte aux retours.

Pour Lumina solo : d'abord l'auth, puis le kanban, puis les colonnes dynamiques, etc. = approche itérative.
Q97 Qu'est-ce que Git et comment l'avez-vous utilisé ? ▶

Git est un outil de versionnage qui sauvegarde l'historique du code. J'ai utilisé GitHub pour stocker le code, avec des commits réguliers pour chaque fonctionnalité.

Q98 Qu'est-ce que Swagger et comment le lire ? ▶

Interface web de documentation d'API sur http://localhost:3000/api-docs. Chaque endpoint est listé avec ses paramètres, son body attendu et ses réponses possibles. On peut tester directement depuis le navigateur.

Q99 Qu'est-ce qu'un diagramme de séquence ? ▶

Un schéma qui montre l'ordre des échanges entre les différentes parties (navigateur, serveur, BDD) dans le temps. Utile pour expliquer comment fonctionne la connexion de A à Z.

Partie 12 — Questions pièges
Q101 Si on enlève le || dans const targetCol = id_col || cols[0].id ? ▶

Si id_col n'est pas fourni, targetCol sera undefined. La tâche sera créée sans colonne → erreur ou valeur NULL en BDD.

Le || dit : "utilise id_col si disponible, sinon prend la 1ère colonne".
Q102 Pourquoi return res.status(401) et pas juste res.status(401) ? ▶

Sans return, la fonction continue à s'exécuter après l'envoi de l'erreur et appelle quand même next() → la route protégée s'exécuterait malgré l'erreur !

return = arrêter immédiatement la fonction.
Q103 Pourquoi description !== undefined et pas juste if (description) ? ▶

Si quelqu'un envoie description: "" (vide intentionnellement), if (description) serait false et la description ne serait pas mise à jour. Avec !== undefined, on accepte même la valeur vide comme modification valide.

Q104 Que se passe-t-il si deux utilisateurs créent une colonne en même temps ? ▶

Les deux récupèrent le même MAX(position) → créent deux colonnes avec la même position → ordre du kanban imprévisible. C'est une race condition. Solution : utiliser une transaction SQL.

Q105 Pourquoi col.title.replace(/'/g, "\\'") dans renderBoard() ? ▶

Si le titre d'une colonne contient une apostrophe (ex: "L'équipe"), le HTML généré pour le onclick serait cassé : onclick="renameColumn(1, 'L'équipe')" → erreur JS. On échappe l'apostrophe pour éviter ça.

Q106 Que retourne authFetch() exactement ? ▶

authFetch() retourne l'objet Response, pas les données JSON. Il faut ensuite appeler await response.json() pour obtenir les vraies données.

Deux étapes : 1) attendre la réponse avec authFetch. 2) lire le contenu avec .json().
Q107 Pourquoi localStorage.getItem('user') retourne une chaîne ? ▶

Le localStorage ne stocke que des chaînes de texte. On sauvegarde l'objet avec JSON.stringify(), il faut le lire avec JSON.parse() pour retrouver un vrai objet JavaScript.

Q108 Que se passe-t-il si escapeHTML() reçoit null ? ▶

La première ligne if (!str) return '' gère ce cas. null est falsy donc la fonction retourne une chaîne vide au lieu de planter. C'est une vérification de sécurité défensive.
