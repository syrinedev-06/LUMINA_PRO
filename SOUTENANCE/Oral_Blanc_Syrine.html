❓ "Comment avez-vous configuré votre environnement de développement ?"
J'ai installé XAMPP pour avoir MySQL et phpMyAdmin, Node.js pour le serveur, et VS Code comme éditeur. J'ai initialisé un dépôt GitHub dès le début du projet avec git init et git remote add origin. Manipulation du DOM — Comment ça marche

Le DOM (Document Object Model) est la représentation de la page HTML en mémoire. JavaScript peut le modifier en temps réel : ajouter des éléments, en retirer, changer leur contenu ou leur style — sans recharger la page.
// Créer une carte de tâche et l'insérer dans une colonne const card = document.createElement('div'); card.className = 'task-card'; card.innerHTML = `<h4>${escapeHTML(task.title)}</h4>`; ← sécurité XSS column.appendChild(card); ← insérer dans le DOM
❓ "Comment fonctionne votre formulaire de création de tâche ?"
Le formulaire HTML contient les champs titre (obligatoire), description, priorité (liste déroulante), date d'échéance et assignation à un membre. À la soumission, JavaScript intercepte l'événement avec addEventListener('submit'...) et empêche le rechargement de page avec event.preventDefault(). Il vérifie que le titre n'est pas vide (validation côté client). Si tout est correct, il envoie les données en JSON au serveur via fetch(). Le serveur vérifie à nouveau que le titre existe (validation côté serveur) avant d'insérer en base. Si la création réussit, le tableau Kanban se recharge automatiquement.
❓ "Votre barre de recherche envoie-t-elle des requêtes au serveur ?"
Non. Les tâches sont chargées une seule fois au démarrage dans une variable JavaScript appelée allTasks. La barre de recherche utilise Array.filter() sur ce tableau déjà en mémoire — aucune requête réseau, aucun délai. C'est du filtrage côté client (client-side filtering). Si je voulais faire la recherche côté serveur, il faudrait envoyer GET /api/tasks?q=mot à chaque frappe — plus lent et plus de charge sur le serveur.
❓ "Comment fonctionne le menu mobile ?"
En dessous de 900px d'écran, le menu latéral est caché par défaut avec display:none en CSS. Un bouton burger ☰ apparaît à la place. Quand on clique dessus, JavaScript ajoute une classe CSS "sidebar-open" qui rend le menu visible. Un fond sombre semi-transparent apparaît derrière. L'utilisateur peut fermer le menu en cliquant sur ce fond, en cliquant sur le bouton ✕, ou en choisissant un élément du menu. aria-expanded est mis à jour pour les lecteurs d'écran.
❓ "C'est quoi async/await ?"
async/await est une façon d'écrire du code qui attend une réponse (comme une demande au serveur) sans bloquer tout le reste. Sans async/await, il faudrait chaîner des .then() ce qui devient vite illisible. Avec async/await, le code ressemble à du code normal même s'il attend : "await" dit "attends la réponse avant de continuer". Si quelque chose se passe mal, try/catch attrape l'erreur.

❓ "Qu'est-ce qu'une clé étrangère (FK) ?"
Une clé étrangère est un champ d'une table qui pointe vers l'identifiant d'une autre table, pour créer un lien entre elles. Dans tasks, le champ id_col est une clé étrangère qui pointe vers l'id de la table columns — ça dit "cette tâche est dans cette colonne". Si on supprime une colonne (ON DELETE CASCADE), MySQL supprime automatiquement toutes ses tâches liées. Sans clé étrangère, les tâches resteraient en base sans colonne valide — des données corrompues.
❓ "C'est quoi la normalisation ?"
Normaliser une base de données, c'est l'organiser pour éviter la répétition des données. Par exemple, au lieu d'écrire le nom de l'utilisateur dans chaque tâche (redondance), on note juste son identifiant (id_assigned) et on va chercher son nom dans la table users quand on en a besoin. Si l'utilisateur change de nom, on le modifie à un seul endroit — la tâche pointe toujours vers le bon enregistrement.
❓ "Comment vérifier la base dans phpMyAdmin ?"
phpMyAdmin est accessible via XAMPP à l'adresse http://localhost/phpmyadmin. Dans la liste des bases à gauche, lumina_pro apparaît avec ses 4 tables. On peut voir la structure de chaque table (onglet Structure), les données (onglet Parcourir), et les relations entre tables. C'est l'interface visuelle de MySQL — toutes les opérations que le code fait avec mysql2 peuvent être vues ici.

Requêtes préparées — Protection contre l'injection SQL

Une injection SQL, c'est quand un utilisateur malveillant écrit du code SQL dans un champ (ex: titre d'une tâche). Si le code n'est pas protégé, ce SQL s'exécute dans la base. Les requêtes préparées utilisent des "?" comme espaces réservés — la bibliothèque mysql2 insère les valeurs de façon sécurisée, sans jamais les interpréter comme du SQL.
// ❌ DANGEREUX (pas de requête préparée) : db.query("SELECT * FROM users WHERE email = '" + email + "'"); // Si email = "' OR 1=1 --" → retourne TOUS les utilisateurs ! // ✅ SÉCURISÉ (requête préparée) : db.query("SELECT * FROM users WHERE email = ?", [email]); // La valeur de email est traitée comme du texte, jamais comme du SQL

❓ "C'est quoi XSS et comment vous protégez-vous ?"
XSS (Cross-Site Scripting) : si un utilisateur écrit <script>alert('pirate')</script> dans le titre d'une tâche et qu'on affiche ce texte tel quel dans le HTML, le script s'exécute dans le navigateur de tous les autres utilisateurs. La protection : avant d'insérer du contenu utilisateur dans la page, la fonction escapeHTML() remplace les caractères dangereux — le < devient &lt; et s'affiche comme du texte normal au lieu de s'exécuter.
❓ "Comment gérez-vous les erreurs ?"
Chaque route Express vérifie les données reçues et renvoie un code HTTP adapté : 400 si des données obligatoires manquent (titre vide), 401 si le ticket JWT manque ou est expiré, 404 si une ressource n'existe pas, 500 si le serveur rencontre une erreur inattendue. Côté client, JavaScript vérifie si la réponse est ok et affiche un message d'erreur à l'utilisateur plutôt que de planter silencieusement.

🏗️ Point 7 — Architecture MVC

Ce que le formateur évalue : architecture MVC vanilla, routeur, affichage en boucles, validation côté serveur, gestion des erreurs, XSS.

Lumina Pro n'applique pas le MVC strict (Model/View/Controller séparés en 3 couches distinctes). Les routes contiennent directement les requêtes SQL. Voici comment répondre honnêtement et professionnellement.

C'est quoi MVC ?

MVC = Modèle / Vue / Contrôleur. C'est une façon d'organiser le code en 3 couches séparées :
— Modèle : tout ce qui touche à la base de données (les requêtes SQL)
— Vue : ce que l'utilisateur voit (le HTML affiché)
— Contrôleur : la logique au milieu (reçoit la demande, appelle le modèle, renvoie la vue)
L'avantage : si on change de base de données, on ne modifie que le Modèle. Si on change le design, on ne touche qu'à la Vue.

L'architecture de Lumina Pro (pas MVC strict)

Lumina Pro a une architecture en 3 couches, mais sans séparation Model/Controller stricte :

— Frontend (Vue) : fichiers HTML/CSS/JS dans /frontend
— Routes Express (Contrôleur) : /backend/routes/tasks.js, columns.js, etc. — les routes reçoivent les demandes et contiennent directement les requêtes SQL
— Base de données (Modèle implicite) : MySQL accessible via mysql2

Les requêtes SQL sont directement dans les routes au lieu d'être dans des fichiers Model séparés. C'est un choix adapté à la taille du projet (solo, 4 tables).
❓ "Votre application respecte-t-elle l'architecture MVC ?"
Lumina Pro a une architecture en couches : le frontend (HTML/CSS/JavaScript) est complètement séparé du backend (Node.js/Express). Le backend a ses routes organisées par ressource dans des fichiers séparés (tasks.js, columns.js, users.js). En revanche, je n'ai pas poussé jusqu'à une séparation stricte Model/Controller : les requêtes SQL sont directement dans les routes. C'est un choix assumé pour un projet solo de cette taille — créer des fichiers Model séparés aurait ajouté de la complexité sans bénéfice réel à ce stade. C'est identifié comme première évolution si l'application devait grandir ou accueillir une équipe.
❓ "C'est quoi un routeur ?"
Un routeur est le mécanisme qui fait correspondre une adresse URL et un type de demande HTTP à une fonction précise. Dans Express, quand le serveur reçoit GET /api/tasks, le routeur sait qu'il faut exécuter la fonction qui lit les tâches en base. Sans routeur, il faudrait une longue suite de if/else pour gérer chaque cas. Express.Router() crée un mini-routeur pour chaque ressource (tasks, columns, users) qui est ensuite monté dans le serveur principal.
❓ "Comment gérez-vous la validation côté serveur ?"
Chaque route vérifie les données reçues avant de les insérer en base. Par exemple, la route POST /api/tasks vérifie que le titre n'est pas vide : si (!title) return res.status(400).json({ error: "Le titre est obligatoire." }). La validation côté serveur est indispensable même si JavaScript la fait aussi côté client — un utilisateur malveillant peut contourner la validation JavaScript en envoyant des requêtes directement à l'API sans passer par le formulaire.

❓ "C'est quoi le TDD (Test Driven Development) ?"
Le TDD, c'est écrire les tests AVANT d'écrire le code. Étape 1 : écrire un test qui échoue (rouge). Étape 2 : écrire le minimum de code pour que le test passe (vert). Étape 3 : améliorer le code sans casser les tests (refactoring). L'avantage : on code exactement ce dont on a besoin, on a une suite de tests qui détecte les régressions automatiquement. Je n'ai pas pratiqué le TDD sur Lumina Pro — c'est une approche que j'identifie pour une prochaine version.
❓ "À quoi ressemblerait un test Jest sur votre API ?"
Avec Jest et Supertest, un test de connexion ressemblerait à :
describe('POST /api/auth/login') → it('doit retourner 200 et un token avec les bons identifiants') → on envoie la requête avec supertest, on vérifie que le status est 200 et que la réponse contient un champ token. Un deuxième test vérifie que de mauvais identifiants retournent 401. Ces tests s'exécutent automatiquement à chaque modification du code.

❓ "Vous avez utilisé Docker ?"

❓ "C'est quoi Docker concrètement ?"

L'avantage : ce conteneur fonctionne exactement pareil sur mon ordinateur, sur l'ordinateur d'un collègue, et sur un serveur en ligne. Fini le problème "ça marchait chez moi". Avec un docker-compose.yml, on peut démarrer l'application Node.js ET la base de données MySQL en une seule commande.
❓ "C'est quoi une migration de base de données ?"

Dans Lumina Pro, j'ai une migration automatique : au démarrage du serveur, il tente d'ajouter la colonne due_date avec ALTER TABLE. Si la colonne existe déjà (base d'une installation précédente), MySQL retourne une erreur ER_DUP_FIELDNAME que le serveur ignore gracieusement. Cela permet d'ajouter des fonctionnalités sans toucher aux données existantes.

🎤 Questions pièges — Ce que le formateur peut vraiment demander

❓ "Pourquoi Node.js et pas PHP ?"
PHP et Node.js permettent tous les deux de créer des API. J'ai choisi Node.js parce que je code en JavaScript côté client — avoir le même langage côté serveur m'a permis de progresser plus vite et d'éviter de gérer deux syntaxes différentes. Node.js avec Express est aussi très bien adapté aux API REST légères. Si le projet avait nécessité un CMS ou une intégration avec WordPress, PHP aurait été plus adapté.
❓ "Qu'est-ce que PDO ?"
PDO (PHP Data Objects) est l'équivalent PHP de mysql2 en Node.js. C'est une couche d'abstraction qui permet d'accéder à une base de données de façon sécurisée en PHP, avec des requêtes préparées. Dans Lumina Pro, j'utilise mysql2 pour Node.js, qui remplit exactement le même rôle : connexion à MySQL, requêtes préparées, gestion des résultats.
❓ "C'est quoi un SGBDR ?"
SGBDR = Système de Gestion de Base de Données Relationnelle. C'est le logiciel qui stocke, organise et gère les données en tables reliées entre elles. MySQL est un SGBDR. D'autres SGBDR : PostgreSQL, SQLite, Microsoft SQL Server. "Relationnelle" veut dire que les tables peuvent être liées entre elles par des clés étrangères — comme tasks reliée à columns via id_col.
❓ "Quelle est la différence entre authentification et autorisation ?"
L'authentification vérifie QUI tu es (connexion avec email + mot de passe). L'autorisation vérifie CE QUE tu peux faire (es-tu admin pour supprimer un utilisateur ?). Dans Lumina Pro : authentification via JWT (le ticket prouve ton identité), autorisation via le champ role dans le ticket (admin ou user détermine ce que tu peux faire).
❓ "Votre application est-elle en production ?"
Non, Lumina Pro tourne exclusivement en local sur XAMPP + Node.js. C'est un choix assumé plutôt qu'un oubli : pour une mise en production, il faudrait un VPS avec HTTPS, des variables d'environnement de production différentes de celles de développement, et idéalement Docker pour la cohérence des environnements. Ces étapes sont documentées dans ma roadmap comme améliorations prioritaires.
❓ "C'est quoi une API REST ?"
REST est un style d'architecture pour les API web. Une API REST utilise les méthodes HTTP standard (GET pour lire, POST pour créer, PUT pour modifier, DELETE pour supprimer) et des URLs qui représentent des ressources (/api/tasks = les tâches, /api/users = les utilisateurs). Chaque demande est indépendante — le serveur ne se souvient pas des demandes précédentes, c'est le client qui envoie toutes les informations nécessaires à chaque fois (y compris le token JWT).
❓ "Avez-vous utilisé Tailwind dans un autre projet ?"
Oui, j'ai découvert Tailwind CSS lors d'exercices pratiques pendant la formation. J'ai compris son principe : des classes utilitaires prédéfinies (flex, p-4, text-center...) qui évitent d'écrire du CSS personnalisé. Pour Lumina Pro, j'ai fait le choix du CSS pur pour maîtriser les fondamentaux — mais je suis capable d'utiliser Tailwind sur un projet qui le requiert.
❓ "Vous êtes débutante — comment avez-vous géré la difficulté ?"
J'ai procédé par étapes : d'abord la base de données et le serveur, puis l'interface, puis la sécurité. Quand je bloquais sur quelque chose, je cherchais dans la documentation officielle (MDN pour JavaScript, documentation Express, documentation mysql2). J'ai commis des erreurs — des secrets qui étaient codés en dur au début, des requêtes SQL qui n'étaient pas préparées — et j'ai corrigé chacune d'elles en comprenant pourquoi c'était un problème. Ces corrections sont tracées dans les commits Git.
