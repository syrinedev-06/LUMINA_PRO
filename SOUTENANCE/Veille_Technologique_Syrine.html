Définition — Qu'est-ce que la veille technologique ?

La veille technologique est le processus de surveillance régulière de l'actualité d'un domaine technique pour rester informé des nouvelles pratiques, outils, menaces ou standards. Pour un développeur web, c'est indispensable car le secteur évolue très vite : une bibliothèque peut devenir vulnérable, un standard peut être remplacé, une nouvelle pratique peut devenir incontournable.

🛡️ Sujet 1 — OWASP Top 10 et Lumina Pro

L'OWASP (Open Web Application Security Project) publie régulièrement une liste des 10 failles de sécurité web les plus dangereuses. J'ai appliqué cette liste à Lumina Pro pour identifier ce qui est protégé et ce qui reste à améliorer.

#Faille OWASPDans Lumina ProProtection appliquée
A01 Contrôle d'accès insuffisant (IDOR) ⚠️ Corrigé en cours de projet Vérification du rôle admin sur DELETE tasks et DELETE users. Vérification assignee pour supprimer sa propre tâche.
A02 Mauvaise configuration cryptographique ✅ Protégé bcrypt avec salt aléatoire (10 rounds). Jamais SHA1/MD5. Clé JWT dans .env.
A03 Injection (SQL, XSS, HTML) ✅ Protégé Requêtes préparées mysql2 (?) contre SQL injection. escapeHTML() contre XSS.
A07 Échecs d'authentification ✅ Protégé JWT + bcrypt.compare() résistant aux attaques temporelles. Message d'erreur générique (ne précise pas si c'est l'email ou le mot de passe).
A09 Logging insuffisant ✅ Partiel Table logs : toutes les opérations CRUD écrivent une entrée. Amélioration prévue : inclure l'IP et l'ID utilisateur dans les logs.

Ce que j'ai appris et appliqué grâce à cette veille

En lisant l'OWASP Top 10, j'ai découvert la faille IDOR (A01 — Broken Access Control) et j'ai réalisé que mon DELETE /api/tasks/:id original n'avait aucune vérification de propriété. J'ai corrigé le code pour ajouter une vérification du rôle (admin uniquement peut supprimer n'importe quelle tâche) ou de l'assignation (l'utilisateur peut supprimer sa propre tâche). Cette correction vient directement de ma veille OWASP.
Ce que OWASP recommande et que Lumina Pro n'a pas encore : rate limiting sur le login (limiter le nombre de tentatives pour éviter les attaques par force brute), HTTPS en production, cookies httpOnly à la place du localStorage pour le JWT. Ces points sont identifiés comme améliorations prioritaires.

🔑 Sujet 2 — Évolution des pratiques d'authentification

JWT : standard largement adopté mais débats en 2025

JWT (JSON Web Token) est aujourd'hui un standard de l'industrie pour l'authentification des API REST. Il est utilisé par des milliers d'applications. Mais en 2025, des développeurs expérimentés discutent de ses limites et des alternatives à considérer selon le contexte.

AspectJWT (ma solution)Sessions serveur (alternative)Cookies httpOnly (alternative)
Stockage localStorage (côté client) Base de données serveur Cookie navigateur (inaccessible par JS)
Risque XSS ⚠️ JWT lisible par JS malveillant ✅ Le token ne quitte pas le serveur ✅ httpOnly = inaccessible par JS
Révocation immédiate ❌ Impossible sans blacklist ✅ Suppression en base immédiate ✅ Suppression de session
Scalabilité ✅ Stateless, pas de DB pour vérifier ❌ Dépend de la DB à chaque requête ✅ Avec Redis/cache
Complexité ✅ Simple à implémenter Moyenne Plus complexe (CORS + SameSite)

Pourquoi j'ai quand même choisi JWT + localStorage

Pour Lumina Pro, JWT + localStorage est un choix adapté au contexte de formation : simple à implémenter, bien documenté, et suffisant pour démontrer les compétences DWWM. Le risque XSS est limité par escapeHTML() qui empêche l'injection de scripts malveillants. En production réelle avec des données sensibles, je recommanderait des cookies httpOnly + HTTPS — c'est ce que j'ai appris grâce à ma veille et que je mentionnerai dans ma roadmap.

Ce que j'ai appris : les nouvelles recommandations 2025

  • Durée d'expiration courte : Les bonnes pratiques recommandent des access tokens courts (15 min) + refresh tokens. Mon JWT expire en 24h — durée raisonnable pour un projet de gestion d'équipe.
  • Algorithme HS256 : Toujours utiliser HS256 ou RS256 — jamais l'algorithme "none" qui est une faille documentée de JWT.
  • Payload minimal : Ne stocker que l'ID et le rôle dans le payload JWT — jamais de données sensibles (email, mot de passe). C'est ce que fait Lumina Pro.

♿ Sujet 3 — Accessibilité web : vers WCAG 3.0

En 2025, le W3C (World Wide Web Consortium — organisation qui définit les standards du web) travaille sur WCAG 3.0, la prochaine version des règles d'accessibilité web. Ma veille sur ce sujet m'a directement influencé dans les choix de Lumina Pro.

WCAG 2.1 → WCAG 3.0 : les changements à venir

AspectWCAG 2.1 (actuel)WCAG 3.0 (en développement)
Système de notationNiveaux A / AA / AAAScore numérique 0-100 par fonctionnalité
Contraste des couleursRatio 4.5:1 pour le texte normalNouveau modèle APCA plus précis (tient compte de la taille, la police, le fond)
PortéeContenu webApplications mobiles, VR, IoT inclus
Tests cognitifsLimitésCritères pour les troubles cognitifs et neurologiques

Ce que j'ai appliqué dans Lumina Pro grâce à cette veille

  • 30 critères WCAG 2.1 niveau AA testés manuellement et documentés
  • Attributs aria-label sur tous les boutons sans texte visible
  • Navigation clavier complète (Tab, Entrée, Échap pour fermer les modales)
  • Contrastes vérifiés avec l'outil de contraste de Chrome DevTools
  • Dark mode (prefers-color-scheme) — recommandation émergente pour le confort visuel
  • Choix des flèches plutôt que le drag & drop — le drag & drop natif n'est pas accessible au clavier

🤖 Sujet 4 — L'IA générative dans le développement web

En 2025, les outils d'IA (GitHub Copilot, ChatGPT, Claude) sont devenus des assistants courants pour les développeurs. Ma veille sur ce sujet m'amène à une réflexion sur leur bonne utilisation.

Ce que j'ai observé et ma position

Les outils d'IA génèrent du code rapidement mais ne comprennent pas le contexte métier, ne testent pas, et peuvent introduire des failles de sécurité sans les signaler. L'utilisation responsable demande de toujours relire, comprendre et tester le code suggéré. Pour Lumina Pro, chaque fonctionnalité a été comprise et testée manuellement — pas copiée-collée sans vérification. La compréhension du code que j'ai réalisé me permet d'en expliquer chaque ligne.
Tendance 2025 : les entreprises cherchent des développeurs qui savent travailler avec l'IA (prompt engineering, revue de code généré) mais aussi comprendre et auditer ce que l'IA produit. La connaissance des fondamentaux (SQL, HTTP, sécurité) reste indispensable pour ne pas accepter du code vulnérable.

Conclusion personnelle

Cette veille technologique m'a permis de prendre conscience que le développement web ne s'arrête pas à "faire fonctionner le code". La sécurité, l'accessibilité et l'évolution des standards sont des préoccupations permanentes dans le métier. J'ai appliqué directement plusieurs recommandations dans Lumina Pro — notamment la protection contre les failles IDOR, le hachage des mots de passe avec bcrypt, et le choix de boutons accessibles plutôt que du drag & drop.

Je compte continuer cette veille dans mon activité professionnelle future, en consultant régulièrement les publications OWASP, les notes de version des technologies que j'utilise, et la communauté Dev.to. C'est pour moi une habitude de travail indispensable pour rester à jour dans un secteur qui évolue aussi vite que le développement web.

Compétence développée : Savoir identifier des sources fiables, filtrer l'information pertinente, et transformer une lecture technique en action concrète dans un projet — c'est ce que j'ai pratiqué tout au long de cette formation avec cette veille technologique.
