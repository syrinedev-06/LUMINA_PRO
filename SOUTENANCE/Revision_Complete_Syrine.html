🔒 Partie 1 — La Sécurité

bcrypt — Comment on protège les mots de passe

Quand tu crées un compte, ton mot de passe n'est jamais sauvegardé tel quel dans la base de données. bcrypt le transforme en une longue suite de lettres et chiffres impossibles à lire. Cette transformation ne peut pas être annulée — même le développeur ne peut pas retrouver le vrai mot de passe.
Ton mot de passe "chat123" est écrit sur une feuille. bcrypt la passe dans un broyeur. Ce qui ressort ressemble à "$2b$10$Xk8mN...". Impossible de recoller les morceaux. Quand tu te reconnectes, le nouveau "chat123" est broyé et on compare les deux résultats — s'ils sont pareils, c'est le bon mot de passe.
📄 Le code bcrypt (server.js)
const hash = await bcrypt.hash(password, 10);← broyer le mot de passe
// 10 = niveau de difficulté du broyage
const ok = await bcrypt.compare(password, hash);← vérifier à la connexion
// ok = true si le mot de passe est correct
🎤 "Pourquoi vous n'avez pas juste sauvegardé le mot de passe ?"
Si un pirate accède à la base de données, il ne voit que des suites de caractères incompréhensibles — jamais le vrai mot de passe. Même si la base est volée, les comptes restent protégés. bcrypt ajoute aussi un morceau aléatoire avant de broyer, donc deux personnes avec le même mot de passe auront des résultats différents en base.
🎤 "Pourquoi bcrypt et pas une autre méthode ?"
D'autres méthodes (comme MD5) sont trop rapides — un ordinateur puissant peut tester des milliards de combinaisons par seconde pour trouver le mot de passe. bcrypt est fait exprès pour être lent : tellement de calculs pour transformer un seul mot de passe que chercher le bon deviendrait impossible même avec un très bon ordinateur.

JWT — Le ticket de connexion

JWT veut dire "ticket numérique". Après connexion, le serveur crée ce ticket et le donne au navigateur. À chaque fois que l'utilisateur veut faire quelque chose (voir ses tâches, créer une tâche…), il montre ce ticket. Le serveur vérifie que le ticket est valide, et si oui, il répond. Le ticket expire après 24 heures.
C'est comme un bracelet de festival. À l'entrée (connexion), le staff (serveur) te donne un bracelet. Toute la journée, pour accéder aux scènes (les données), tu montres ton bracelet. Le staff vérifie juste que le bracelet n'est pas faux — il n'a pas besoin de te demander qui tu es à chaque fois.
📄 Le code JWT (server.js)
const token = jwt.sign(← créer le ticket
{ id: user.id, role: user.role },← ce qu'on met dedans
process.env.JWT_SECRET,← la clé secrète
{ expiresIn: '24h' }← expire en 24h
);
jwt.verify(token, process.env.JWT_SECRET);← vérifier le ticket
🎤 "Comment fonctionne le JWT dans votre application ?"
Quand l'utilisateur se connecte, le serveur vérifie les identifiants. Si c'est correct, il crée un ticket JWT avec l'identifiant et le rôle de l'utilisateur, et l'envoie au navigateur. Le navigateur le sauvegarde dans sa mémoire (localStorage). Ensuite, à chaque action, le ticket est envoyé avec la demande. Le serveur le vérifie grâce à une clé secrète — si quelqu'un a essayé de modifier le ticket, la vérification échoue.
🎤 "Que se passe-t-il si quelqu'un vole le ticket JWT ?"
Si quelqu'un vole le ticket, il peut se faire passer pour l'utilisateur jusqu'à ce que le ticket expire (24h chez nous). Pour réduire ce risque, on pourrait raccourcir la durée d'expiration ou stocker le ticket dans un espace que JavaScript ne peut pas lire — mais c'est plus compliqué à mettre en place.

Le filtre de sécurité (verifyToken)

C'est un "videur" placé devant chaque action protégée. Avant que la demande n'arrive, le videur vérifie le ticket. Si le ticket est valide → il laisse passer. Sinon → il renvoie une erreur "non autorisé" tout de suite.
📄 Le filtre de sécurité (server.js)
function verifyToken(req, res, next) {← le videur
const token = req.headers.authorization;← récupérer le ticket
if (!token) return res.status(401).json(...);← pas de ticket = refus
jwt.verify(token, SECRET);← vérifier le ticket
next();← ticket OK = laisser passer
}
🎤 "Toutes vos pages sont-elles protégées ?"
Non, pas toutes. La page de connexion et la page d'inscription sont libres — on ne peut pas demander un ticket pour se connecter puisqu'on n'en a pas encore. Toutes les autres actions (voir les tâches, créer, modifier, supprimer) passent par le filtre de sécurité et nécessitent un ticket valide.

📄 La structure des tableaux (MySQL)

🎤 "Expliquez le lien entre vos tableaux."
Une tâche appartient à une colonne (elle note l'identifiant de la colonne) et peut être assignée à un utilisateur (elle note l'identifiant de cet utilisateur). Ces liens s'appellent des clés étrangères. Si une colonne est supprimée, toutes ses tâches sont automatiquement supprimées aussi grâce à la règle ON DELETE CASCADE.

LEFT JOIN — Voir toutes les tâches même les non assignées

Imagine une liste de classe avec les notes. Sans LEFT JOIN (= INNER JOIN) : la liste ne montre que les élèves qui ont une note. Avec LEFT JOIN : la liste montre TOUS les élèves, et si un élève n'a pas de note, on écrit "aucune" à la place. Dans Lumina Pro, on veut voir TOUTES les tâches, même celles qui ne sont assignées à personne.
📄 La requête LEFT JOIN (server.js)
SELECT tasks.*, users.name← prendre les tâches + le nom
FROM tasks← tableau principal
LEFT JOIN users← relier avec les utilisateurs
ON tasks.id_assigned = users.id;← via l'identifiant
🎤 "Pourquoi LEFT JOIN ?"
Sans LEFT JOIN, si une tâche n'est assignée à personne, elle disparaît complètement — l'utilisateur ne la verrait plus dans le Kanban. LEFT JOIN retourne toutes les tâches, qu'elles soient assignées ou non. Pour les non-assignées, on affiche "Non assigné" à la place.

ON DELETE CASCADE — Suppression automatique

C'est comme supprimer un dossier sur l'ordinateur : tous les fichiers à l'intérieur sont supprimés en même temps automatiquement. Supprimer une colonne Kanban → toutes ses tâches disparaissent aussi, sans qu'on ait besoin d'écrire du code pour ça.
🎤 "Que se passe-t-il si vous supprimez une colonne ?"
MySQL supprime automatiquement toutes les tâches qui appartiennent à cette colonne. Sans cette règle, les tâches resteraient en base mais liées à une colonne qui n'existe plus — des tâches perdues qui peuvent faire planter l'application.

ENUM — Liste de valeurs autorisées

ENUM est une règle sur un champ qui dit "ce champ n'accepte que ces mots précis". Pour la priorité, on n'accepte que 'high', 'medium', 'low'. Si on essaie de mettre autre chose, la base refuse automatiquement.
🎤 "Qu'est-ce qu'un ENUM et pourquoi l'utiliser ?"
Un ENUM est une liste de mots autorisés directement dans la base de données. On l'utilise pour éviter les fautes de frappe ou les erreurs : si le code JavaScript envoie "urgent" au lieu de "high", la base refuse et on voit tout de suite qu'il y a un problème. Sans ENUM, la mauvaise valeur serait sauvegardée et la couleur du badge ne s'afficherait pas.

Création automatique des tableaux

🎤 "Comment votre base de données est-elle préparée ?"
Au démarrage du serveur, le code crée automatiquement les tableaux s'ils n'existent pas encore. Il vérifie aussi si des colonnes Kanban existent et crée les 3 colonnes par défaut (À faire, En cours, Terminé) si la base est vide. L'application s'installe donc toute seule sans manipulation manuelle.

📡 Partie 3 — L'API (la boîte aux lettres du serveur)

C'est quoi une API ?

Une API, c'est comme un serveur dans un restaurant. Toi (le navigateur), tu es le client à table. La cuisine (la base de données), c'est là où les données sont stockées. Le serveur (l'API) prend ta commande, va en cuisine, et te rapporte le résultat. Tu ne vas jamais directement en cuisine — tu passes toujours par le serveur.

🎤 "C'est quoi la différence entre 400 et 401 ?"
Le 400 veut dire que la demande est mal faite — par exemple, le titre de la tâche est vide. Le 401 veut dire que l'utilisateur n'est pas connecté ou que son ticket est expiré. Ce sont deux problèmes différents : l'un concerne les données envoyées, l'autre concerne les droits d'accès.

⚡ Partie 4 — La Partie Visible (Frontend)

Les étapes quand on se connecte

Étape 1 : L'utilisateur tape email + mot de passe → clique "Se connecter" Étape 2 : JavaScript envoie la demande au serveur (POST /api/auth/login) Étape 3 : Le serveur vérifie l'email dans la base → compare le mot de passe avec bcrypt Étape 4 : Si c'est correct → le serveur crée un ticket JWT et le renvoie Étape 5 : JavaScript sauvegarde le ticket dans la mémoire du navigateur Étape 6 : La page bascule vers le tableau Kanban (index.html) Étape 7 : À chaque action suivante, le ticket est envoyé automatiquement
📄 authFetch() — La fonction clé (api.js)
function authFetch(url, options = {}) {← notre fonction
const token = localStorage.getItem('token');← récupérer le ticket
options.headers = {← ajouter le ticket
Authorization: 'Bearer ' + token← dans chaque demande
};
return fetch(url, options);← envoyer la demande
}
🎤 "Où est sauvegardé le ticket JWT dans le navigateur ?"
Dans le localStorage — c'est un espace de mémoire du navigateur qui reste même si on ferme l'onglet. On le récupère avec localStorage.getItem('token') et on l'efface avec localStorage.clear() quand l'utilisateur se déconnecte.

authFetch() — La fonction qui envoie le ticket automatiquement

Plutôt que d'écrire le code d'envoi du ticket dans chaque fichier JavaScript, on a créé une seule fonction qui le fait tout le temps automatiquement. Elle prend le ticket dans la mémoire du navigateur et l'ajoute à chaque demande envoyée au serveur.
🎤 "Pourquoi avoir créé authFetch ?"
Pour ne pas répéter le même code partout. Sans authFetch, il faudrait écrire la même chose dans chaque fichier (tasks.js, columns.js, team.js…). Si on devait changer quelque chose, il faudrait modifier partout et risquer d'en oublier. Avec authFetch, on modifie un seul endroit et tout le site est mis à jour.

Vitesse d'affichage — defer et CSS en parallèle

🎤 "Qu'est-ce que defer sur les scripts ?"
defer dit au navigateur : télécharge ce fichier JavaScript sans bloquer l'affichage de la page, et exécute-le seulement quand la page est prête. Sans defer, le navigateur s'arrêterait d'afficher la page à chaque fichier JavaScript rencontré. Avec defer, la page apparaît plus vite à l'écran.
🎤 "Pourquoi plusieurs fichiers CSS séparés et pas un seul gros fichier ?"
Avec des fichiers séparés déclarés dans le HTML, le navigateur les télécharge tous en même temps. Si on utilisait @import dans un seul fichier CSS, le navigateur devrait les télécharger un par un — beaucoup plus lent. Le chargement en parallèle améliore la vitesse d'affichage.

♿ Partie 5 — L'Accessibilité

C'est quoi l'accessibilité web ?

L'accessibilité web, c'est construire un site qui peut être utilisé par tout le monde, y compris les personnes malvoyantes, non-voyantes, ou qui ne peuvent pas utiliser une souris. Ces personnes utilisent des logiciels qui lisent la page à voix haute, ou naviguent uniquement avec le clavier.
Un bâtiment accessible a une rampe en plus des escaliers. Un site accessible a des descriptions pour les images et des boutons qu'on peut atteindre au clavier en plus de la souris. C'est la même idée appliquée au web.
🎤 "C'est quoi WCAG 2.1 ?"
WCAG (prononcer "wuh-cag") est un ensemble de règles internationales pour rendre les sites web accessibles à tous. La version 2.1 niveau AA est la norme la plus courante. Elle dit que le site doit être : visible et audible, utilisable au clavier, compréhensible, et compatible avec les outils d'aide.

Les lecteurs d'écran

Un lecteur d'écran est un logiciel qui lit à voix haute tout ce qui est à l'écran. Les plus connus sont NVDA (gratuit, Windows) et VoiceOver (intégré dans Mac et iPhone). Ces logiciels lisent le HTML dans l'ordre et annoncent le type de chaque élément : "bouton Connexion", "champ Email obligatoire", "titre niveau 2 Tableau de bord"...
🎤 "Comment une personne aveugle utilise votre site ?"
Elle utilise NVDA qui lit chaque élément à voix haute. Elle navigue avec la touche Tab pour passer d'un bouton à l'autre, et avec la touche H pour sauter entre les titres. Grâce aux descriptions sur les boutons (aria-label), quand elle arrive sur le bouton de suppression d'une tâche, le logiciel dit "Supprimer la tâche Finaliser le design" au lieu de juste "bouton poubelle". Le lien d'évitement lui permet de sauter directement au Kanban sans repasser par tout le menu.

🎤 "Pourquoi utiliser des boutons <button> et pas des <span> ?"
Un bouton HTML est automatiquement accessible : on peut le cibler avec Tab, l'activer avec la touche Entrée, et le lecteur d'écran l'annonce comme "bouton". Un span est juste un conteneur de texte — invisible pour le clavier et les logiciels d'aide. Il faudrait ajouter beaucoup de code supplémentaire pour lui donner les mêmes fonctions, et ça marche moins bien.

🎤 "Expliquez comment fonctionne votre application du début à la fin."
L'utilisateur ouvre login.html. Il entre ses identifiants. JavaScript envoie la demande au serveur Node.js. Le serveur vérifie dans MySQL, crée un ticket JWT et le renvoie. JavaScript sauvegarde le ticket et redirige vers index.html. Là, les fichiers JavaScript chargent les colonnes et les tâches en envoyant le ticket avec chaque demande. Le serveur vérifie le ticket à chaque fois, interroge MySQL, et renvoie les données. JavaScript affiche tout sans recharger la page.
🎤 "Pourquoi avoir séparé la partie visible et le serveur ?"
Séparer ce que l'utilisateur voit (HTML, CSS, JavaScript) du serveur (Node.js, MySQL) permet de modifier l'un sans casser l'autre. On pourrait aussi créer une application mobile qui utilise le même serveur — elle enverrait les mêmes demandes et recevrait les mêmes réponses.
🎤 "Qu'est-ce que Swagger dans votre projet ?"
Swagger génère automatiquement une page accessible à l'adresse /api-docs. Elle liste toutes les adresses de l'API, montre ce qu'elles attendent, et permet de les tester directement depuis le navigateur. C'est très utile pour vérifier que tout fonctionne pendant le développement, sans outil supplémentaire.
🎤 "C'est quoi CORS ?"
CORS est une règle de sécurité des navigateurs qui bloque par défaut les demandes vers un autre serveur. Sans activer CORS dans Express, toutes les demandes du navigateur vers l'API seraient bloquées automatiquement. On l'active avec une ligne de code qui autorise les navigateurs à communiquer avec notre serveur.
🎤 "C'est quoi Lighthouse ?"
Lighthouse est un outil gratuit intégré dans Chrome qui analyse une page web et donne des notes sur 100 : performance, accessibilité, bonnes pratiques, et référencement. Sur la page de connexion de Lumina Pro : 99 en Performance, 93 en Accessibilité, 100 en SEO. Le score de 93 (et non 100) en accessibilité s'explique par quelques contrastes et attributs ARIA encore à affiner — un point assumé et honnête à mentionner à l'oral plutôt qu'à cacher.

👤 Partie 6 — Mon Profil (profile.js)

C'est quoi cette page ?

"Mon Profil" est une fenêtre modale simple qui affiche les informations du compte connecté : nom, email, rôle et un statut "En ligne". Une fonctionnalité de modification du profil existait à une étape du projet puis a été volontairement retirée (commit « Suppression complète de la fonctionnalité d'édition de profil ») pour garder un code minimal — le profil est aujourd'hui en lecture seule.

localStorage — Récupérer l'utilisateur connecté

Après la connexion, les informations de l'utilisateur (nom, email, rôle, id) sont sauvegardées dans le navigateur via localStorage. La page Profil n'a pas besoin de redemander ces informations au serveur : elle les relit directement depuis la mémoire du navigateur.
📄 showProfile() (profile.js)
function showProfile() {← affiche la fenêtre profil
const user = JSON.parse(localStorage.getItem('user'));← relit l'utilisateur sauvegardé
// ... affichage de user.name, user.email, user.role, user.id
}
🎤 "D'où viennent les informations affichées dans le profil ?"
Elles ne viennent pas d'une nouvelle demande au serveur : elles sont déjà sauvegardées dans le localStorage du navigateur depuis la connexion (login.html). showProfile() les relit simplement avec JSON.parse(localStorage.getItem('user')) et les affiche dans une fenêtre modale.

escapeHTML() — Même principe de sécurité que partout ailleurs

Le nom, l'email et le rôle affichés dans le profil passent par la même fonction escapeHTML() que le reste de l'application, avant d'être insérés dans le HTML. C'est la même protection XSS vue en Partie 4 : même si ces données viennent du localStorage (donc du navigateur de l'utilisateur lui-même), on applique la règle systématiquement plutôt que de faire une exception.
🎤 "Pourquoi une page aussi simple pour le profil ?"
Une fonctionnalité de modification du profil (changer son nom, son email) avait été développée, puis retirée volontairement pour réduire la surface de code à maintenir et à sécuriser dans le temps imparti à la certification. Le profil actuel est en lecture seule : c'est un choix de périmètre assumé, pas un oubli.
🎤 "Que se passe-t-il sur mobile quand on ouvre le profil ?"
Si le menu latéral est ouvert et que la largeur de l'écran est ≤ 900px, showProfile() referme automatiquement le menu avant d'afficher la fenêtre du profil, pour ne pas superposer deux panneaux à l'écran.

🎤 Questions pièges — Ce que le jury peut vraiment demander

🎤 "Vous parlez de logs d'audit dans votre dossier — y a-t-il une interface pour les consulter ?"
Non. Un module de journal d'audit a réellement été développé (table logs, route dédiée), mais je l'ai volontairement retiré lors d'un nettoyage du code pour recentrer le projet sur un cœur Kanban simple et entièrement maîtrisé. Il n'existe donc aujourd'hui aucune interface de consultation des logs — c'est un choix de périmètre assumé, pas un oubli, et il est noté dans mes évolutions futures si le besoin s'en fait sentir.
🎤 "Si vous deviez refaire ce projet, que changeriez-vous ?"
Honnêtement, je pense que je m'organiserais mieux au début — j'ai un peu foncé dans le code avant d'avoir bien fini toute la conception, du coup j'ai dû revenir en arrière plusieurs fois. Je ferais sûrement aussi des tests au fur et à mesure au lieu de tout tester à la fin, ça m'aurait fait gagner du temps. Et niveau code, je sais que je devrais apprendre à écrire des tests automatiques (Jest), là je n'ai testé qu'à la main faute de temps.
🎤 "Votre application est-elle protégée contre les attaques dans les champs de texte ?"
Oui. Toutes les demandes à la base de données utilisent des espaces réservés (points d'interrogation) que la bibliothèque mysql2 remplace de façon sécurisée. Si quelqu'un essaie d'écrire du code dans un champ, il sera traité comme du texte normal et non comme une instruction — la base ne sera pas touchée.
🎤 "Pourquoi JavaScript simple et pas React ou Vue ?"
Pour ce projet, JavaScript simple est suffisant et plus facile à comprendre et expliquer. React et Vue ajoutent des outils supplémentaires qui ne sont pas nécessaires pour une application Kanban de cette taille. Le code peut être lu directement dans le navigateur sans étape supplémentaire.
🎤 "Comment gérez-vous les rôles admin et utilisateur normal ?"
Le rôle est sauvegardé dans la table users (admin ou user). Il est inclus dans le ticket JWT à la connexion. Côté navigateur, si le rôle est admin, le menu "Équipe" apparaît et permet de gérer les membres. Les utilisateurs normaux ne voient pas ce menu.
🎤 "Votre site fonctionne-t-il sur mobile ?"
Oui. En dessous de 900px de largeur (tablettes et mobiles), le menu latéral se cache et un bouton burger ☰ apparaît pour l'ouvrir. Un fond sombre s'affiche derrière le menu ouvert, et un bouton ✕ permet de le fermer. On peut aussi fermer le menu en tapant sur le fond sombre. Les colonnes Kanban défilent horizontalement sur les petits écrans.
🎤 "Comment fonctionne le déplacement d'une tâche entre colonnes ?"
Chaque tâche note dans quel colonne elle se trouve (un numéro de colonne). Les boutons ⬅️ et ➡️ sur chaque carte changent ce numéro en envoyant une demande de modification au serveur. Express met à jour le numéro en base. Ensuite, toutes les tâches sont rechargées et réaffichées à leurs nouvelles positions.
🎤 "C'est quoi un ticket JWT concrètement, qu'est-ce qu'il contient ?"
Un ticket JWT est une longue suite de caractères composée de 3 parties séparées par des points. La première partie dit quel type de ticket c'est. La deuxième contient les informations : l'identifiant de l'utilisateur, son rôle, et quand le ticket expire. La troisième est une vérification calculée avec une clé secrète — si quelqu'un modifie le ticket, la vérification échoue et le serveur refuse.
🎤 "Quelle est la hiérarchie des titres dans votre site ?"
h2 pour le titre de la page (dans la barre du haut), h3 pour chaque colonne du Kanban, h4 pour le titre de chaque tâche. C'est important de ne pas sauter de niveau — un lecteur d'écran utilise ces titres comme un plan pour naviguer dans la page.
