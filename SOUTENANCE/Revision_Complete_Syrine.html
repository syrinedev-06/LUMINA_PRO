🔒 Partie 1 — La Sécurité

bcrypt — Comment on protège les mots de passe

Quand tu crées un compte, ton mot de passe n'est jamais sauvegardé tel quel dans la base de données. bcrypt le transforme en une longue suite de lettres et chiffres impossibles à lire. Cette transformation ne peut pas être annulée — même le développeur ne peut pas retrouver le vrai mot de passe.
Ton mot de passe "chat123" est écrit sur une feuille. bcrypt la passe dans un broyeur. Ce qui ressort ressemble à "$2b$10$Xk8mN...". Impossible de recoller les morceaux. Quand tu te reconnectes, le nouveau "chat123" est broyé et on compare les deux résultats — s'ils sont pareils, c'est le bon mot de passe.
📄 Le code bcrypt (server.js)
const hash = await bcrypt.hash(password, 10);← broyer le mot de passe
// 10 = niveau de difficulté du broyage
const ok = await bcrypt.compare(password, hash);← vérifier à la connexion
// ok = true si le mot de passe est correct
🎤 "Pourquoi vous n'avez pas juste sauvegardé le mot de passe ?"
Si un pirate accède à la base de données, il ne voit que des suites de caractères incompréhensibles — jamais le vrai mot de passe. Même si la base est volée, les comptes restent protégés. bcrypt ajoute aussi un morceau aléatoire avant de broyer, donc deux personnes avec le même mot de passe auront des résultats différents en base.
🎤 "Pourquoi bcrypt et pas une autre méthode ?"
D'autres méthodes (comme MD5) sont trop rapides — un ordinateur puissant peut tester des milliards de combinaisons par seconde pour trouver le mot de passe. bcrypt est fait exprès pour être lent : tellement de calculs pour transformer un seul mot de passe que chercher le bon deviendrait impossible même avec un très bon ordinateur.

JWT — Le ticket de connexion

JWT veut dire "ticket numérique". Après connexion, le serveur crée ce ticket et le donne au navigateur. À chaque fois que l'utilisateur veut faire quelque chose (voir ses tâches, créer une tâche…), il montre ce ticket. Le serveur vérifie que le ticket est valide, et si oui, il répond. Le ticket expire après 24 heures.
C'est comme un bracelet de festival. À l'entrée (connexion), le staff (serveur) te donne un bracelet. Toute la journée, pour accéder aux scènes (les données), tu montres ton bracelet. Le staff vérifie juste que le bracelet n'est pas faux — il n'a pas besoin de te demander qui tu es à chaque fois.
📄 Le code JWT (server.js)
const token = jwt.sign(← créer le ticket
{ id: user.id, role: user.role },← ce qu'on met dedans
process.env.JWT_SECRET,← la clé secrète
{ expiresIn: '24h' }← expire en 24h
);
jwt.verify(token, process.env.JWT_SECRET);← vérifier le ticket
🎤 "Comment fonctionne le JWT dans votre application ?"
Quand l'utilisateur se connecte, le serveur vérifie les identifiants. Si c'est correct, il crée un ticket JWT avec l'identifiant et le rôle de l'utilisateur, et l'envoie au navigateur. Le navigateur le sauvegarde dans sa mémoire (localStorage). Ensuite, à chaque action, le ticket est envoyé avec la demande. Le serveur le vérifie grâce à une clé secrète — si quelqu'un a essayé de modifier le ticket, la vérification échoue.
🎤 "Que se passe-t-il si quelqu'un vole le ticket JWT ?"
Si quelqu'un vole le ticket, il peut se faire passer pour l'utilisateur jusqu'à ce que le ticket expire (24h chez nous). Pour réduire ce risque, on pourrait raccourcir la durée d'expiration ou stocker le ticket dans un espace que JavaScript ne peut pas lire — mais c'est plus compliqué à mettre en place.

Le filtre de sécurité (verifyToken)

C'est un "videur" placé devant chaque action protégée. Avant que la demande n'arrive, le videur vérifie le ticket. Si le ticket est valide → il laisse passer. Sinon → il renvoie une erreur "non autorisé" tout de suite.
📄 Le filtre de sécurité (server.js)
function verifyToken(req, res, next) {← le videur
const token = req.headers.authorization;← récupérer le ticket
if (!token) return res.status(401).json(...);← pas de ticket = refus
jwt.verify(token, SECRET);← vérifier le ticket
next();← ticket OK = laisser passer
}
🎤 "Toutes vos pages sont-elles protégées ?"
Non, pas toutes. La page de connexion et la page d'inscription sont libres — on ne peut pas demander un ticket pour se connecter puisqu'on n'en a pas encore. Toutes les autres actions (voir les tâches, créer, modifier, supprimer) passent par le filtre de sécurité et nécessitent un ticket valide.

LEFT JOIN — Voir toutes les tâches même les non assignées

Imagine une liste de classe avec les notes. Sans LEFT JOIN (= INNER JOIN) : la liste ne montre que les élèves qui ont une note. Avec LEFT JOIN : la liste montre TOUS les élèves, et si un élève n'a pas de note, on écrit "aucune" à la place. Dans Lumina Pro, on veut voir TOUTES les tâches, même celles qui ne sont assignées à personne.
📄 La requête LEFT JOIN (server.js)
SELECT tasks.*, users.name← prendre les tâches + le nom
FROM tasks← tableau principal
LEFT JOIN users← relier avec les utilisateurs
ON tasks.id_assigned = users.id;← via l'identifiant
🎤 "Pourquoi LEFT JOIN ?"
Sans LEFT JOIN, si une tâche n'est assignée à personne, elle disparaît complètement — l'utilisateur ne la verrait plus dans le Kanban. LEFT JOIN retourne toutes les tâches, qu'elles soient assignées ou non. Pour les non-assignées, on affiche "Non assigné" à la place.

ON DELETE CASCADE — Suppression automatique

C'est comme supprimer un dossier sur l'ordinateur : tous les fichiers à l'intérieur sont supprimés en même temps automatiquement. Supprimer une colonne Kanban → toutes ses tâches disparaissent aussi, sans qu'on ait besoin d'écrire du code pour ça.
🎤 "Que se passe-t-il si vous supprimez une colonne ?"
MySQL supprime automatiquement toutes les tâches qui appartiennent à cette colonne. Sans cette règle, les tâches resteraient en base mais liées à une colonne qui n'existe plus — des tâches perdues qui peuvent faire planter l'application.

ENUM — Liste de valeurs autorisées

ENUM est une règle sur un champ qui dit "ce champ n'accepte que ces mots précis". Pour la priorité, on n'accepte que 'high', 'medium', 'low'. Si on essaie de mettre autre chose, la base refuse automatiquement.
🎤 "Qu'est-ce qu'un ENUM et pourquoi l'utiliser ?"
Un ENUM est une liste de mots autorisés directement dans la base de données. On l'utilise pour éviter les fautes de frappe ou les erreurs : si le code JavaScript envoie "urgent" au lieu de "high", la base refuse et on voit tout de suite qu'il y a un problème. Sans ENUM, la mauvaise valeur serait sauvegardée et la couleur du badge ne s'afficherait pas.

Création automatique des tableaux

🎤 "Comment votre base de données est-elle préparée ?"
Au démarrage du serveur, le code crée automatiquement les tableaux s'ils n'existent pas encore. Il vérifie aussi si des colonnes Kanban existent et crée les 3 colonnes par défaut (À faire, En cours, Terminé) si la base est vide. L'application s'installe donc toute seule sans manipulation manuelle.

Le serveur (l'API) prend ta commande, va en cuisine, et te rapporte le résultat. Tu ne vas jamais directement en cuisine — tu passes toujours par le serveur.

🎤 "Où est sauvegardé le ticket JWT dans le navigateur ?"
Dans le localStorage — c'est un espace de mémoire du navigateur qui reste même si on ferme l'onglet. On le récupère avec localStorage.getItem('token') et on l'efface avec localStorage.clear() quand l'utilisateur se déconnecte.

authFetch() — La fonction qui envoie le ticket automatiquement

Plutôt que d'écrire le code d'envoi du ticket dans chaque fichier JavaScript, on a créé une seule fonction qui le fait tout le temps automatiquement. Elle prend le ticket dans la mémoire du navigateur et l'ajoute à chaque demande envoyée au serveur.
🎤 "Pourquoi avoir créé authFetch ?"
Pour ne pas répéter le même code partout. Sans authFetch, il faudrait écrire la même chose dans chaque fichier (tasks.js, columns.js, team.js…). Si on devait changer quelque chose, il faudrait modifier partout et risquer d'en oublier. Avec authFetch, on modifie un seul endroit et tout le site est mis à jour.

Vitesse d'affichage — defer et CSS en parallèle

🎤 "Qu'est-ce que defer sur les scripts ?"
defer dit au navigateur : télécharge ce fichier JavaScript sans bloquer l'affichage de la page, et exécute-le seulement quand la page est prête. Sans defer, le navigateur s'arrêterait d'afficher la page à chaque fichier JavaScript rencontré. Avec defer, la page apparaît plus vite à l'écran.
🎤 "Pourquoi plusieurs fichiers CSS séparés et pas un seul gros fichier ?"
Avec des fichiers séparés déclarés dans le HTML, le navigateur les télécharge tous en même temps. Si on utilisait @import dans un seul fichier CSS, le navigateur devrait les télécharger un par un — beaucoup plus lent. Le chargement en parallèle améliore la vitesse d'affichage.

♿ Partie 5 — L'Accessibilité

C'est quoi l'accessibilité web ?

L'accessibilité web, c'est construire un site qui peut être utilisé par tout le monde, y compris les personnes malvoyantes, non-voyantes, ou qui ne peuvent pas utiliser une souris. Ces personnes utilisent des logiciels qui lisent la page à voix haute, ou naviguent uniquement avec le clavier.
Un bâtiment accessible a une rampe en plus des escaliers. Un site accessible a des descriptions pour les images et des boutons qu'on peut atteindre au clavier en plus de la souris. C'est la même idée appliquée au web.
🎤 "C'est quoi WCAG 2.1 ?"
WCAG (prononcer "wuh-cag") est un ensemble de règles internationales pour rendre les sites web accessibles à tous. La version 2.1 niveau AA est la norme la plus courante. Elle dit que le site doit être : visible et audible, utilisable au clavier, compréhensible, et compatible avec les outils d'aide.

Les lecteurs d'écran

Un lecteur d'écran est un logiciel qui lit à voix haute tout ce qui est à l'écran. Les plus connus sont NVDA (gratuit, Windows) et VoiceOver (intégré dans Mac et iPhone). Ces logiciels lisent le HTML dans l'ordre et annoncent le type de chaque élément : "bouton Connexion", "champ Email obligatoire", "titre niveau 2 Tableau de bord"...
🎤 "Comment une personne aveugle utilise votre site ?"
Elle utilise NVDA qui lit chaque élément à voix haute. Elle navigue avec la touche Tab pour passer d'un bouton à l'autre, et avec la touche H pour sauter entre les titres. Grâce aux descriptions sur les boutons (aria-label), quand elle arrive sur le bouton de suppression d'une tâche, le logiciel dit "Supprimer la tâche Finaliser le design" au lieu de juste "bouton poubelle". Le lien d'évitement lui permet de sauter directement au Kanban sans repasser par tout le menu.

Un bouton HTML est automatiquement accessible : on peut le cibler avec Tab, l'activer avec la touche Entrée, et le lecteur d'écran l'annonce comme "bouton". Un span est juste un conteneur de texte — invisible pour le clavier et les logiciels d'aide. Il faudrait ajouter beaucoup de code supplémentaire pour lui donner les mêmes fonctions, et ça marche moins bien.

🎤 "C'est quoi CORS ?"
CORS est une règle de sécurité des navigateurs qui bloque par défaut les demandes vers un autre serveur. Sans activer CORS dans Express, toutes les demandes du navigateur vers l'API seraient bloquées automatiquement. On l'active avec une ligne de code qui autorise les navigateurs à communiquer avec notre serveur.
🎤 "C'est quoi Lighthouse ?"

📊 Partie 6 — Statistiques (profile.js)

C'est quoi cette page ?

"Statistiques" remplace l'ancienne page "Mon Profil" (modification de profil retirée, puis la consultation de profil elle-même remplacée par cette vue). Promise.all() — Charger deux ressources en parallèle

La page a besoin des tâches (pour les compter par priorité) et des utilisateurs (pour le nombre de membres). Plutôt que d'attendre les deux requêtes l'une après l'autre, Promise.all() les lance en même temps et attend que les deux soient terminées.

🎤 "D'où viennent les informations affichées dans les statistiques ?"
D'un nouvel appel au serveur à chaque ouverture de la page : Promise.all() interroge /api/tasks et /api/users en parallèle. Les statistiques (total, urgentes, non assignées, membres) sont ensuite calculées côté client avec Array.filter() sur les données reçues — aucune route serveur dédiée aux statistiques n'existe.

Camembert SVG — Sans bibliothèque

Le graphique circulaire est dessiné à la main avec de la trigonométrie (Math.cos/Math.sin) pour calculer les coordonnées de chaque part, sans Chart.js ni aucune autre bibliothèque de graphiques. C'est la fonction creerCamembert() dans profile.js.
🎤 "Pourquoi ne pas avoir gardé une route serveur dédiée aux statistiques ?"
Une route serveur (routes/stats.js) avait été développée puis retirée volontairement pour simplifier le périmètre d'examen. La version actuelle recalcule les statistiques côté front à partir de données déjà chargées (/api/tasks, /api/users) : plus simple, sans exposer de nouvelle route serveur, au prix d'un calcul refait à chaque ouverture plutôt qu'agrégé en base.

🎤 "C'est quoi Array.filter() ?"
C'est une méthode JavaScript qui parcourt un tableau et ne garde que les éléments pour lesquels la condition est vraie. Ici, on garde une tâche si son titre ou sa description contient le texte recherché. Le tableau d'origine (allTasks) n'est pas modifié.

📚 Concepts clés — Explications simples

Node.js — Le moteur du serveur

Node.js permet d'exécuter JavaScript en dehors du navigateur, directement sur l'ordinateur serveur. Sans Node.js, JavaScript ne pouvait fonctionner que dans un navigateur. Grâce à Node.js, on peut créer un serveur web entier en JavaScript.
Avant Node.js, si tu savais JavaScript, tu ne pouvais coder que la partie visible d'un site. Node.js, c'est comme donner à un cuisinier (JavaScript) l'accès à toute la cuisine (le serveur), pas seulement à la salle.

Express.js — La simplification de Node.js

Express.js est une bibliothèque qui s'installe par-dessus Node.js et qui simplifie énormément la création d'API. Sans Express, créer une seule route demanderait 30 lignes de code. Avec Express, c'est 3 lignes.
📄 Sans Express vs Avec Express
// SANS Express (Node.js pur) :
http.createServer((req, res) => {← 30 lignes pour une route
if (req.url === '/api/tasks' && req.method === 'GET') { ... }
// AVEC Express :
app.get('/api/tasks', (req, res) => { ... });← 1 ligne

npm — Le gestionnaire de bibliothèques

npm (Node Package Manager) est un outil qui permet d'installer des bibliothèques en une seule commande. Au lieu de télécharger chaque bibliothèque à la main, on écrit npm install express et npm télécharge Express avec toutes ses dépendances automatiquement.
C'est comme une liste de courses automatique. Au lieu d'aller chercher chaque ingrédient dans des magasins différents, tu donnes la liste à npm et il ramène tout à la maison.

Git — La machine à remonter le temps du code

Git sauvegarde chaque version du code avec un message expliquant ce qui a changé (un "commit"). Si une modification casse quelque chose, on peut revenir exactement à la version précédente. GitHub est le service en ligne qui stocke ces versions accessibles depuis n'importe où.
C'est comme Ctrl+Z illimité, mais pour tout le projet et avec des notes explicatives. Chaque Ctrl+Z (commit) a un message : "Ajout de la date d'échéance" — on sait exactement ce qu'on annule.
🎤 "Combien de commits a votre projet ?"
Le projet Lumina Pro compte 33+ commits. Chaque commit a un message explicite qui décrit ce qui a été ajouté ou modifié. Certains commits ont volontairement supprimé des fonctionnalités (audit trail, notifications, drag & drop) pour recentrer le projet sur un cœur solide avant la soutenance.

🔒 Corrections de sécurité — Ce que j'ai amélioré et pourquoi

Ces corrections ont été apportées après une relecture complète du code. Tu dois pouvoir expliquer chaque changement au jury — il prouve que tu comprends la sécurité, pas juste que le code "marche".

Correction 1 — Faille IDOR dans DELETE /api/tasks/:id

Problème avant la correction : n'importe quel utilisateur connecté pouvait supprimer la tâche de quelqu'un d'autre en envoyant DELETE /api/tasks/42 — même si cette tâche ne lui appartient pas. Il suffit de deviner ou de connaître un ID. C'est la faille IDOR (Insecure Direct Object Reference) — la n°1 du classement OWASP Top 10.
Correction : Le code vérifie maintenant QUI fait la demande (req.user, injecté par verifyToken) et À QUI appartient la tâche (id_assigned en base). Seul un admin OU la personne à qui la tâche est assignée peut la supprimer. Les autres reçoivent un 403 Forbidden.
❓ "C'est quoi IDOR ?"
IDOR = Insecure Direct Object Reference. C'est quand une API permet d'accéder à ou de modifier une ressource d'un autre utilisateur en changeant juste l'ID dans l'URL, sans vérifier si l'utilisateur en a le droit. Exemple : DELETE /api/tasks/42 — si le serveur ne vérifie pas que la tâche 42 appartient bien à l'utilisateur qui fait la demande, c'est une faille IDOR. La correction : toujours vérifier la propriété OU le rôle avant d'agir.

Correction 2 — Faille IDOR dans DELETE /api/users/:id

Problème avant : un utilisateur avec le rôle "user" pouvait envoyer DELETE /api/users/3 et supprimer le compte d'un autre membre de l'équipe — même un admin. Aucune vérification de rôle n'existait.
Correction : La route vérifie maintenant que req.user.role === 'admin'. Un utilisateur standard reçoit immédiatement un 403 Forbidden sans que la requête SQL ne soit même exécutée.
❓ "Quelle est la différence entre 401 et 403 ?"
401 Unauthorized = tu n'es pas connecté (token manquant ou expiré). 403 Forbidden = tu es connecté mais tu n'as pas le droit de faire cette action. Dans Lumina Pro : si le token JWT manque → 401. Si le token est valide mais que tu n'es pas admin et que tu essaies de supprimer un utilisateur → 403.

Correction 3 — Inscription : 500 → 409 pour email déjà pris

Problème avant : quand quelqu'un essayait de créer un compte avec un email déjà existant, le serveur répondait HTTP 500 (Internal Server Error = "le serveur a planté"). C'était faux — le serveur n'avait pas planté, c'est juste que l'email était déjà pris.
Correction : On capture spécifiquement l'erreur MySQL ER_DUP_ENTRY (violation de contrainte d'unicité) et on renvoie HTTP 409 Conflict — qui signifie exactement "la ressource existe déjà". Le message d'erreur précise que l'email est déjà utilisé.
❓ "C'est quoi ER_DUP_ENTRY ?"
C'est le code d'erreur MySQL qui indique qu'on essaie d'insérer une valeur en doublon dans une colonne UNIQUE. La table users a email UNIQUE NOT NULL — MySQL refuse deux lignes avec le même email et lève une erreur ER_DUP_ENTRY. En JavaScript, on attrape cette erreur avec if (err.code === 'ER_DUP_ENTRY') pour envoyer la bonne réponse HTTP au lieu de laisser remonter une erreur 500.

Correction 4 — Validation d'entrée sur l'inscription

Problème avant : un appel à POST /api/auth/register avec un body vide {} créait un utilisateur sans nom, sans email, et avec un hash de chaîne vide comme mot de passe. Pas de vérification côté serveur.
Correction : Trois vérifications ajoutées : nom/email/password obligatoires (400 Bad Request si manquant), format email vérifié par une regex simple, et mot de passe d'au moins 6 caractères. Ces vérifications doublonnent le formulaire HTML côté client — mais c'est indispensable car un attaquant peut appeler l'API directement sans passer par le formulaire.
❓ "Pourquoi valider côté serveur si vous validez déjà côté client (HTML required) ?"
La validation HTML (required, type="email"...) protège l'utilisateur normal. Mais un attaquant n'utilise pas le formulaire — il envoie des requêtes directement à l'API avec des outils comme Postman, curl, ou un script. Si le serveur ne revalide pas les données, il accepte n'importe quoi. La règle est : ne jamais faire confiance aux données qui arrivent du réseau, quelle que soit leur source apparente.

Correction 5 — schema.sql : incohérence corrigée (3 → 4 tables)

Problème avant : le commentaire dans database/schema.sql disait "3 tables" et ne contenait pas la table logs, alors que server.js crée bien 4 tables dont logs, et que les routes y écrivent à chaque CRUD. Contradiction directe entre deux fichiers du projet.
Correction : Le commentaire dit maintenant "4 tables". La table logs a été ajoutée dans schema.sql avec ses colonnes et commentaires pédagogiques. Les deux fichiers (schema.sql et server.js) sont maintenant cohérents.

🧱 Concepts que le jury peut creuser — Node.js et Express

❓ "C'est quoi un middleware exactement ? Quels sont ses paramètres ?"
Un middleware est une fonction qui s'exécute entre la réception d'une requête et l'envoi de la réponse. Express les enchaîne dans l'ordre où ils sont déclarés. Chaque middleware reçoit 3 paramètres : req (la requête entrante — contient les données, les headers, le body), res (la réponse à envoyer — permet de répondre avec res.json(), res.status()...), et next (une fonction à appeler pour passer au middleware suivant). Si on n'appelle pas next(), la requête reste bloquée. Dans Lumina Pro, verifyToken est un middleware : il vérifie le JWT, injecte req.user, et appelle next() si tout va bien — sinon il répond 401 ou 403 sans appeler next().
❓ "C'est quoi CORS et pourquoi en avez-vous besoin ?"
CORS (Cross-Origin Resource Sharing) est un mécanisme de sécurité des navigateurs qui bloque par défaut les requêtes JavaScript d'un domaine vers un autre domaine. Sans CORS configuré, si le frontend tourne sur localhost:5500 et le backend sur localhost:3000, le navigateur bloquerait les appels fetch(). app.use(cors()) dans server.js ajoute les bons headers HTTP (Access-Control-Allow-Origin) pour autoriser ces appels. CORS protège les utilisateurs — il empêche un site malveillant de faire des appels à votre API en se faisant passer pour votre frontend.
❓ "C'est quoi l'event loop de Node.js ?"
Node.js fonctionne avec un seul thread (un seul fil d'exécution) mais il peut gérer des milliers de connexions simultanées grâce à l'event loop. Quand Node.js doit faire une opération lente (lire une base de données, lire un fichier), il ne reste pas bloqué à attendre — il confie l'opération au système d'exploitation et continue à traiter d'autres requêtes. Quand l'opération est terminée, le système signale Node.js qui exécute la fonction callback. C'est pourquoi le code Node.js utilise des callbacks, des Promises et async/await — pour gérer ces opérations asynchrones. PHP en revanche crée un nouveau thread pour chaque requête — plus simple à comprendre mais plus lourd en ressources.
❓ "Pourquoi JWT dans localStorage plutôt que dans un cookie httpOnly ?"
localStorage est plus simple à implémenter (une ligne pour lire, une pour écrire) et ne nécessite pas de configuration CORS spéciale. Son risque : si un script malveillant s'exécute dans la page (faille XSS), il peut lire le token. Les cookies httpOnly ne sont pas accessibles par JavaScript, ce qui les rend plus sûrs contre le XSS — mais ils nécessitent HTTPS et une configuration CORS plus stricte (credentials: 'include'). Pour Lumina Pro, localStorage est un choix adapté au contexte de formation, protégé par escapeHTML() qui empêche l'injection de scripts. En production avec des données vraiment sensibles, je choisirais les cookies httpOnly + HTTPS.
❓ "C'est quoi express.json() et pourquoi c'est nécessaire ?"
Quand un client envoie des données en JSON dans le corps d'une requête POST ou PUT, ces données arrivent sous forme de texte brut. express.json() est un middleware qui lit ce texte, le parse en objet JavaScript, et le met dans req.body. Sans express.json(), req.body serait undefined et on ne pourrait pas lire les données envoyées par le client. C'est une ligne essentielle dans server.js : app.use(express.json()).
❓ "Pourquoi votre DELETE /api/tasks/:id fait d'abord un SELECT avant de supprimer ?"
Parce qu'on a besoin de savoir à qui la tâche est assignée pour décider si l'utilisateur a le droit de la supprimer. On ne peut pas vérifier la propriété d'une tâche sans d'abord la lire. C'est le pattern "check before act" (vérifier avant d'agir) — indispensable pour éviter les failles IDOR. Oui, ça fait deux requêtes SQL au lieu d'une. C'est un compromis de sécurité acceptable : la performance est légèrement réduite mais la protection est réelle.
❓ "Pourquoi les flèches plutôt que le drag and drop pour déplacer les tâches ?"
C'est un choix d'accessibilité délibéré. Le drag & drop natif HTML5 n'est pas utilisable au clavier et n'est pas correctement annoncé par les lecteurs d'écran — ce qui exclut les utilisateurs qui naviguent sans souris. Les boutons fléchés sont accessibles au clavier (Tab + Entrée), ont un aria-label qui les décrit ("Déplacer vers la colonne suivante"), et fonctionnent pour tous. C'est exactement ce que recommande WCAG 2.1 — toute fonctionnalité doit être utilisable au clavier. Ce choix vient directement de ma veille sur l'accessibilité.
