1. Contexte et enjeux de l'accessibilité
Qu'est-ce que l'accessibilité web ?

L'accessibilité web consiste à rendre les sites et applications utilisables par toutes les personnes, quelles que soient leurs capacités. Cela inclut notamment les personnes malvoyantes ou non-voyantes qui utilisent des lecteurs d'écran (logiciels comme NVDA, JAWS ou VoiceOver) pour naviguer sur le web à la place de leurs yeux.

Un lecteur d'écran lit le contenu de la page à voix haute. Il dépend entièrement des informations présentes dans le code HTML : si un bouton n'a pas de texte descriptif, le lecteur annoncera simplement « bouton » sans expliquer à quoi il sert. Si un champ de formulaire n'est pas lié à son étiquette, l'utilisateur ne sait pas ce qu'il doit saisir.

Le standard WCAG 2.1

Les WCAG (Web Content Accessibility Guidelines) sont les recommandations internationales publiées par le W3C. Elles définissent les critères à respecter pour rendre un site accessible. Le niveau AA est le niveau minimal exigé en France (loi RGAA).

WCAG 1.1.1 — Niveau A
Contenu non textuel
Tout contenu non textuel (image, icône, emoji) doit avoir une alternative textuelle compréhensible par un lecteur d'écran, ou être marqué comme décoratif.
WCAG 1.3.1 — Niveau A
Information et relations
Les relations entre éléments (label → input) doivent être visibles dans le code, pas seulement visuellement. Un lecteur d'écran doit comprendre que le label correspond au champ.
WCAG 2.1.1 — Niveau A
Navigation clavier
Toutes les fonctionnalités doivent être accessibles au clavier (Tab, Entrée, Espace). Les éléments interactifs doivent être des éléments HTML natifs ou avoir les bons rôles ARIA.
WCAG 4.1.2 — Niveau A
Nom, rôle, valeur
Chaque composant d'interface (bouton, champ, dialog) doit avoir un nom accessible, un rôle correct et une valeur lisible par les technologies d'assistance.
Outil de mesure : Google Lighthouse

Lighthouse est un outil intégré aux DevTools de Chrome qui audite automatiquement l'accessibilité d'une page. Il attribue un score de 0 à 100 basé sur les critères WCAG. Le score initial de Lumina Pro était de 97/100.

Score initial (avant corrections)
97
Score final (après corrections)

2. Corrections appliquées — Tableau récapitulatif
Fichier : login.html
Problème détecté Impact pour un malvoyant Correction appliquée
✗ Labels non liés aux champs
Ex : <label>Email</label> sans <for>		 Le lecteur d'écran ne sait pas quel champ correspond à quelle étiquette. L'utilisateur ne sait pas ce qu'il doit saisir. ✓ Ajout de for="id" sur chaque label + id correspondant sur chaque input.
✗ Bouton 👁️ = <span> cliquable Un <span> n'est pas focusable au clavier. Un utilisateur ne peut pas activer le bouton "afficher le mot de passe" sans souris. Le lecteur annonce l'emoji sans contexte. ✓ Remplacé par un vrai <button type="button"> avec aria-label="Afficher ou masquer le mot de passe". Emoji masqué avec aria-hidden="true".
✗ Champs obligatoires non signalés Un lecteur d'écran ne détecte pas qu'un champ est requis si seul l'attribut HTML required est présent, sans son équivalent ARIA. ✓ Ajout de aria-required="true" sur tous les champs obligatoires.
✗ Section d'inscription sans annonce Quand l'utilisateur clique sur "S'inscrire", la section change mais le lecteur d'écran ne l'annonce pas automatiquement. ✓ Ajout de aria-live="polite" sur la section inscription → le lecteur annonce le changement.
Fichier : index.html
Problème détecté Impact pour un malvoyant Correction appliquée
✗ Bouton FAB = "+" Le lecteur annonce « bouton + ». L'utilisateur ne sait pas que ce bouton sert à créer une tâche. ✓ Ajout aria-label="Ajouter une nouvelle tâche" + aria-haspopup="dialog".
✗ Bouton menu = "☰" sans description Le lecteur annonce un caractère incompréhensible. L'utilisateur ne sait pas que c'est un menu de navigation. ✓ Ajout aria-label="Ouvrir ou fermer le menu" + aria-expanded="false" + aria-controls="sidebar".
✗ Avatar = <div> cliquable Un <div> n'est pas focusable au clavier. L'accès au profil est impossible sans souris. ✓ Remplacé par <button> avec aria-label="Voir mon profil". SVG marqué aria-hidden="true".
✗ Emojis dans le menu (📊 👥 👤) Les lecteurs d'écran lisent les emojis de façon verbeuse : "signe de graphique à barres en croissance". Distraction pour l'utilisateur. ✓ Emojis encapsulés dans <span aria-hidden="true">. Texte des liens enrichi avec aria-label descriptif.
✗ Modales sans rôle dialog Quand une modale s'ouvre, le lecteur d'écran ne l'annonce pas. L'utilisateur ne sait pas qu'une fenêtre est apparue. ✓ Ajout role="dialog" + aria-modal="true" + aria-labelledby="modal-title" sur les 2 modales.
✗ Labels non liés dans la modale Même problème que login.html : les champs "Titre", "Description", "Priorité", "Assigné à" ne sont pas liés à leurs labels. ✓ Ajout for/id sur tous les labels et champs du formulaire de tâche.
✗ Zone dynamique sans annonce Quand le contenu change (Kanban → Équipe → Profil), le lecteur d'écran n'annonce pas le nouveau contenu. ✓ Ajout aria-live="polite" sur #content-area.
Fichier : style.css
Ajout Rôle pour l'accessibilité
.skip-link Lien invisible "Aller au contenu principal" qui apparaît quand l'utilisateur appuie sur Tab. Permet de sauter le menu de navigation pour aller directement au contenu — standard sur tous les sites accessibles.
:focus-visible Contour de focus visible (bordure de 3px) sur tout élément focusé par le clavier. Permet à un utilisateur naviguant au clavier de savoir où il se trouve sur la page à tout moment.

3. Extraits de code — Avant / Après
Liaison label → input (login.html)

Sans l'attribut for, le lecteur d'écran ne sait pas que le label "Email" correspond au champ de saisie juste en dessous.

AVANT — Non accessible
<!-- Le label n'est pas lié au champ --> <label>Email</label> <input type="email" placeholder="votre@email.com" required>
APRÈS — Accessible
<!-- Le label est lié au champ via for="id" --> <label for="login-email">Email</label> <input type="email" id="login-email" placeholder="votre@email.com" required aria-required="true">
Bouton "Afficher le mot de passe" (login.html)

Un <span> n'est pas un élément interactif. Il n'est pas focusable au clavier et le lecteur d'écran lit l'emoji brut.

AVANT — Non accessible
<!-- Span non focusable au clavier, emoji lu brut --> <span onclick="togglePassword('login-password', this)" style="cursor: pointer;">👁️</span>
APRÈS — Accessible
<!-- Vrai bouton, navigable au clavier, emoji masqué --> <button type="button" onclick="togglePassword('login-password', this)" aria-label="Afficher ou masquer le mot de passe"> <span aria-hidden="true">👁️</span> </button>
Déclaration d'une modale (index.html)

Sans role="dialog", le lecteur d'écran ne sait pas qu'une fenêtre modale vient de s'ouvrir.

AVANT — Non accessible
<div id="task-modal" class="modal"> <div class="modal-content"> <h2 id="modal-title">Nouvelle Mission</h2> ...
APRÈS — Accessible
<div id="task-modal" class="modal" role="dialog" aria-modal="true" aria-labelledby="modal-title"> <div class="modal-content"> <h2 id="modal-title">Nouvelle Mission</h2> <!-- aria-labelledby pointe vers ce h2 -->

4. Fonctionnalités avancées ajoutées
Lien d'évitement (skip link) — style.css + index.html

Un utilisateur malvoyant navigant au clavier doit appuyer sur Tab de nombreuses fois pour traverser le menu avant d'atteindre le contenu. Le lien d'évitement apparaît au premier appui sur Tab et permet de sauter directement au contenu principal.

CODE — index.html
<!-- Premier élément du body : lien invisible sauf au focus --> <a href="#content-area" class="skip-link"> Aller au contenu principal </a>
CODE — style.css
.skip-link { position: absolute; top: -100%; /* Caché hors de l'écran */ background: var(--accent); color: white; padding: 10px 18px; z-index: 9999; } .skip-link:focus { top: 0; /* Visible seulement au focus clavier */ }
Focus clavier visible — style.css

Par défaut, certains navigateurs masquent l'indicateur de focus pour des raisons esthétiques. Cela rend la navigation au clavier impossible pour un utilisateur malvoyant partiel. La pseudo-classe :focus-visible force l'affichage d'un contour visible uniquement lors de la navigation clavier.

CODE — style.css
:focus-visible { outline: 3px solid var(--accent); outline-offset: 2px; border-radius: 3px; /* Contour visible uniquement à la navigation clavier */ }
5. Conclusion

L'audit initial Lighthouse révélait un score de 97/100 : la majorité des bonnes pratiques était déjà en place (contraste des couleurs, structure HTML sémantique, attribut lang="fr", balises alt sur les images). Les 3 points manquants correspondaient à des problèmes de liaison formulaires et d'éléments interactifs non natifs.

Les corrections apportées permettent à un utilisateur utilisant un lecteur d'écran (NVDA, VoiceOver, JAWS) de :

  • Remplir les formulaires de connexion et d'inscription en sachant quel champ correspond à quelle étiquette
  • Activer le bouton "afficher le mot de passe" via le clavier
  • Être informé de l'ouverture d'une modale et de son titre
  • Naviguer dans le menu avec une description claire de chaque lien
  • Sauter le menu de navigation pour accéder directement au tableau Kanban
  • Voir où se trouve le focus clavier à tout moment grâce au contour visible
Score final Lighthouse — Accessibilité : 100/100
Toutes les recommandations WCAG 2.1 Niveau AA appliquées aux formulaires, boutons, modales et navigation.
