1 Présentation du projet

1.1 Contexte et entreprise

Lumina Pro est un projet personnel développé dans le cadre du titre professionnel Développeur Web et Web Mobile (DWWM) à La Plateforme_, école de formation au numérique à Marseille.

Il s'inscrit dans un contexte de reconversion professionnelle. Ce projet représente la mise en pratique de l'ensemble des compétences acquises durant la formation : développement frontend, développement backend, conception de base de données et sécurité applicative.

1.2 Contexte du marché

La gestion de projet en équipe est un besoin universel dans les entreprises numériques. Des outils comme Trello, Jira ou Asana dominent le marché. Ces solutions sont souvent complexes, coûteuses, ou surdimensionnées pour les petites équipes.

Lumina Pro se positionne comme une alternative légère, open-source et auto-hébergeable, centrée sur l'essentiel : créer des tâches, les organiser visuellement, les assigner aux bons membres.

1.3 Besoin identifié

Le besoin principal est de permettre à une petite équipe de :

  • Visualiser l'état d'avancement d'un projet sur un tableau Kanban
  • Créer, modifier, déplacer et supprimer des tâches facilement
  • Distinguer les priorités (URGENT, MOYEN, NORMAL)
  • Assigner des tâches à des membres spécifiques
  • Gérer les droits d'accès (admin vs utilisateur)

1.4 Historique du projet

Le projet a été développé de manière itérative, en commençant par les fondations (authentification, base de données) puis en ajoutant progressivement les fonctionnalités métier (CRUD, déplacement des tâches, gestion des colonnes, rôles). L'ensemble du code est versionné sur GitHub avec des commits réguliers.

Fonctionnalités livrées : Authentification JWT, tableau Kanban dynamique, CRUD complet tâches et colonnes, déplacement par boutons directionnels, tri par priorité, assignation, gestion des rôles admin/user, responsive mobile, documentation Swagger, logs d'audit.

7.2 Modèle Logique des Données (MLD)

Traduction du MCD en tables relationnelles :

7.3 Cardinalités

RelationCardinalitéSignification
users → tasks (assignation)1 à N (optionnel)Un utilisateur peut avoir 0 ou plusieurs tâches assignées. Une tâche peut n'être assignée à personne (NULL).
columns → tasks (appartenance)1 à N (obligatoire)Une colonne contient 0 ou plusieurs tâches. Chaque tâche appartient à exactement une colonne.

7.4 Propriétés ACID

MySQL InnoDB garantit les 4 propriétés ACID pour chaque opération :

  • Atomicité : tout ou rien — si un INSERT échoue à mi-chemin, rien n'est enregistré
  • Consistance : les contraintes (UNIQUE, FOREIGN KEY, ENUM) sont toujours respectées après chaque transaction
  • Isolation : deux transactions simultanées ne se perturbent pas
  • Durabilité : une fois un commit validé, les données survivent à un redémarrage serveur

8.1 Requêtes SQL de création (MPD)

CREATE TABLE IF NOT EXISTS users ( id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(255) NOT NULL, email VARCHAR(255) UNIQUE NOT NULL, password VARCHAR(255) NOT NULL, -- hash bcrypt, jamais en clair role ENUM('admin','user') DEFAULT 'user' ); CREATE TABLE IF NOT EXISTS columns ( id INT AUTO_INCREMENT PRIMARY KEY, title VARCHAR(255) NOT NULL, position INT DEFAULT 0 -- ordre d'affichage gauche → droite ); CREATE TABLE IF NOT EXISTS tasks ( id INT AUTO_INCREMENT PRIMARY KEY, title VARCHAR(255) NOT NULL, description TEXT, priority ENUM('high','medium','low') DEFAULT 'medium', id_assigned INT, -- NULL si non assignée id_col INT, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, FOREIGN KEY (id_col) REFERENCES columns(id) ON DELETE CASCADE -- ON DELETE CASCADE : si une colonne est supprimée, -- toutes ses tâches sont automatiquement supprimées );

9 Mission 1 — Authentification et gestion des rôles

Introduction

La première mission couvre tout le système d'authentification : inscription, connexion, génération et vérification des tokens JWT, et gestion des droits selon le rôle (admin ou user). C'est le socle de sécurité de l'application.

Tables concernées

Table users (id, name, email UNIQUE, password HASH, role ENUM).

Diagramme de séquence — Connexion

ÉtapeNavigateur (auth.js)Serveur (auth.js)MySQL
1 Soumet email + password → POST /api/auth/login Reçoit req.body
2 SELECT * FROM users WHERE email = ? →Cherche l'utilisateur
3 bcrypt.compare(password, hash) ←Retourne la ligne
4a ← 401 "Identifiants incorrects" ← Si isMatch = false → res.status(401)
4b Si isMatch = true → jwt.sign({id, role}, SECRET, 24h)
5 Reçoit { token, user } → localStorage → index.html ← res.json({ token, user })

Code — Inscription (bcrypt)

// backend/routes/auth.js — POST /api/auth/register router.post('/register', async (req, res) => { const { name, email, password } = req.body; // Hachage irreversible avec sel automatique (10 rounds) const hashedPassword = await bcrypt.hash(password, 10); // Requête préparée → protection injection SQL const sql = "INSERT INTO users (name, email, password) VALUES (?, ?, ?)"; req.db.query(sql, [name, email, hashedPassword]); });

Code — Connexion (JWT)

// backend/routes/auth.js — POST /api/auth/login const isMatch = await bcrypt.compare(password, user.password); // compare() : recrée le hash à partir du mot de passe saisi // et le compare avec le hash stocké → true ou false const token = jwt.sign( { id: user.id, role: user.role }, // payload (données publiques) "LUMINA_SECRET_2024", // clé de signature HMAC-SHA256 { expiresIn: '24h' } // expiration automatique );

Code — Middleware verifyToken

// backend/middleware/security.js function verifyToken(req, res, next) { const authHeader = req.headers['authorization']; // Format attendu : "Bearer eyJhbGci..." if (!authHeader || !authHeader.startsWith('Bearer ')) return res.status(401).json({ error: "Token manquant" }); const token = authHeader.split(' ')[1]; try { const decoded = jwt.verify(token, SECRET_KEY); req.user = decoded; // { id: 1, role: 'admin' } disponible dans les routes next(); // token valide → on continue } catch { res.status(403).json({ error: "Token invalide ou expiré" }); } }

Gestion des rôles

// frontend/js/kanban.js — affichage conditionnel selon le rôle const user = JSON.parse(localStorage.getItem('user')); if (user.role === 'admin') { document.getElementById('nav-team').style.display = 'block'; } else { document.getElementById('nav-team').style.display = 'none'; } // Note : la vraie sécurité est côté serveur (verifyToken). // Ce code est uniquement pour l'expérience utilisateur.
Bilan Mission 1 : Authentification complète avec hachage bcrypt (irréversible + sel aléatoire), tokens JWT (signés, expiration 24h), middleware verifyToken sur toutes les routes protégées, gestion des rôles admin/user.
10 Mission 2 — Tableau Kanban (CRUD tâches et colonnes)

Introduction

La deuxième mission couvre le cœur fonctionnel de l'application : afficher le tableau Kanban, créer/modifier/supprimer des tâches et des colonnes, déplacer les tâches entre colonnes, et trier par priorité.

Tables concernées

Tables tasks et columns. Les tâches référencent les colonnes via la clé étrangère id_col.

Requête SQL principale — GET /api/tasks

SELECT tasks.*, users.name AS assigned_name FROM tasks LEFT JOIN users ON tasks.id_assigned = users.id -- LEFT JOIN : garde les tâches même si id_assigned est NULL -- INNER JOIN les ferait disparaître si non assignées ORDER BY id_col ASC, FIELD(tasks.priority, 'high', 'medium', 'low') ASC, -- FIELD() retourne 1 pour high, 2 pour medium, 3 pour low -- → URGENT s'affiche en haut de chaque colonne created_at DESC;

Code — Rendu du tableau (renderBoard)

// frontend/js/kanban.js function renderBoard(columns, tasks) { columns.forEach(col => { // filter() : ne garde que les tâches de cette colonne const colTasks = tasks.filter(t => t.id_col === col.id); // map() : transforme chaque tâche en HTML // join('') : colle sans virgule // escapeHTML() : protection XSS sur chaque valeur affichée const html = colTasks.map(task => ` <div class="task-card"> <h5>${escapeHTML(task.title)}</h5> <p>${escapeHTML(task.description || '')}</p> </div> `).join(''); }); }

Code — authFetch() : le principe DRY appliqué

// frontend/js/api.js // Sans authFetch() : copier-coller le header dans CHAQUE fetch() // Avec authFetch() : une seule définition, utilisée partout async function authFetch(url, options = {}) { const token = localStorage.getItem('token'); options.headers = options.headers || {}; if (token) options.headers['Authorization'] = `Bearer ${token}`; if (options.body) options.headers['Content-Type'] = 'application/json'; const response = await fetch(url, options); if (response.status === 401) { localStorage.clear(); window.location.href = 'login.html'; // session expirée } return response; }

13 Sécurité

13.1 Injection SQL — Requêtes préparées

Toutes les requêtes SQL utilisent des placeholders ?. Le driver mysql2 échappe automatiquement les valeurs, rendant toute injection impossible.

// ❌ DANGEREUX — concaténation directe const sql = `SELECT * FROM users WHERE email = '${email}'`; // Si email = "' OR '1'='1" → retourne tous les utilisateurs // ✅ SÉCURISÉ — requête préparée const sql = "SELECT * FROM users WHERE email = ?"; req.db.query(sql, [email]); // mysql2 échappe les guillemets

13.2 Faille XSS — escapeHTML()

Toutes les données utilisateur injectées dans le DOM passent par escapeHTML().

// frontend/js/api.js function escapeHTML(str) { return str.toString() .replace(/&/g, '&amp;') .replace(/</g, '&lt;') // <script> → &lt;script&gt; .replace(/>/g, '&gt;') // ne s'exécute plus .replace(/"/g, '&quot;') .replace(/'/g, '&#39;'); } // Utilisé sur : task.title, task.description, user.name, user.email...

13.3 Hash des mots de passe — bcrypt vs chiffrement

Important : bcrypt est un hachage, pas un chiffrement. Le chiffrement est réversible (avec la clé). Le hachage est irréversible — on ne peut pas retrouver le mot de passe depuis le hash.

// bcrypt.hash() : irréversible + sel aléatoire unique "Lumina1!" → "$2b$10$xK9mPqwerty..." ← impossible de revenir en arrière // bcrypt.compare() : recrée le hash et compare bcrypt.compare("Lumina1!", "$2b$10$xK9mP...") → true

13.4 CSRF — Protection par JWT dans le header

L'application est naturellement protégée contre le CSRF car le token JWT est stocké dans le localStorage et envoyé dans le header Authorization. Un site malveillant ne peut pas lire le localStorage d'un autre domaine ni injecter des headers — ce que les cookies de session permettraient.

13.5 Contrôle des accès

Le middleware verifyToken est appliqué sur toutes les routes protégées dans server.js :

app.use('/api/users', verifyToken, require('./routes/users')); app.use('/api/tasks', verifyToken, require('./routes/tasks')); app.use('/api/columns', verifyToken, require('./routes/columns')); // /api/auth reste public (pas de verifyToken)

13.6 Gestion des erreurs

Chaque route retourne un code HTTP sémantique et un message d'erreur JSON. Les logs d'activité (table logs) tracent chaque opération CRUD avec l'heure automatique via TIMESTAMP DEFAULT CURRENT_TIMESTAMP.
